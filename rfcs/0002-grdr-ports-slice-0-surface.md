## Summary
Slice 0 adds the first public types and traits to `grdr-ports` and `grdr-ports-testkit`: identifiers, the tenant contexts and object paths, the Blobs, Jobs (leases), Bus, Relational and Events ports, and the conformance kit with a reference adapter and a suite per port. This RFC states every signature and its semantics in full, sets twelve rules every port follows, assigns the error codes, says how an adapter from outside the workspace is tested, verified and selected, and enters both crates as `experimental`. Who may mint a tenant context, implement a port, build a fence or act for an organisation in a given lifecycle state or under a delegation is held by types: sealed port traits, a mint authority that never leaves the `tenant` module and that runners reach only through purpose-bound handles, and one check at every store operation of the organisation's current lifecycle answer, the context's delegation and its expiry. Fifteen properties state what every relational adapter and tenancy table holds, whatever its back end: isolation under a binding set at open that no declared statement can change, writes only under a write binding, tenancy rules the store holds itself and checks at start and while it runs, a statement check at build and a reply check at run, delegation and bounds enforced in the store, and revocation, confirmation and restore for each replica's copy (sections 2 and 9). Each names its kit case on the reference adapters, or the store test every relational adapter item carries. How one back end holds them is that adapter's item: #2002 for PostgreSQL. A register check over macro-expanded code keeps `unsafe` away from the code that holds these types. It changes no spine text and proposes amendments to design/03, design/20 and design/21 (section 14).

## Motivation
`grdr-ports` is the seam P6 and P14 rest on. The release-gating adapters of each profile and every contrib or embedder adapter meet the product only through these traits, and they are admitted only by passing the test kit (design/03 extension points; design/20 extension point 1). Every server target in slice 0 calls them; `grdr-daemon` links the crate only for what RFC 0008 defines. A public crate changes only by RFC (D-61, design/30 R7), and `experimental` sets the break rules, not the route (ruling on #1535).

The eight items (#281, #297, #298, #299, #300, #1535, #312, #313) were specified one at a time. Read together they disagree in places a later adapter would turn into a defect: two fence rules, an unfenced lake write path, one error variant with two classes, a `Set` context that reaches a per-organisation lake read, methods with no semantics, and no rule for how Events rows cross the port. Review also found barriers that held only where a source scan ran or a caller kept a convention: who may mint a context, who may implement a port, who may build a fence, where an organisation's lifecycle state and a provider's delegation are checked, and what a test hook may run. This RFC puts each of those in a type wherever a type can hold it. If nothing changes, nine implementers build against conflicting signatures and the first adapter items (#1546, #1547, #1554) inherit the conflicts.

## Design

### 1. Rules for every port
Terms used below:
- A **tenant witness** is a value only a tenant context can produce (Rule 3).
- A **deployment-scoped** method works on a resource that belongs to no organisation: leases, bus partitions and offsets, bucket maps, migrations, a partition's flush. `architecture.toml` lists each one (section 14).
- A **port trait** is what module code calls; an **adapter trait** is what an adapter implements; `Admitted<A>` joins them (Rule 12).
- The **mint authority** is `tenant`'s private `MintAuthority`, issued once per process by `tenant::start` with the process's tenancy table, clock and limits (section 2). No other crate can name it. The **composition root** is the module of `grdr-server` that builds the adapters from configuration, calls `tenant::start`, admits the adapters, builds the runners' handles and starts the runners. `architecture.toml` names it and the modules that may name each handle.
- A **handle** is a value `tenant` builds, inside `tenant::start`, for one runner's purpose. It mints only within the scope it was built for (section 2).
- A **fence** is a lease name and the fencing token one `Leases::acquire` call granted. No caller builds one (section 7).
- A **call token** is `PortsCall<S>` (section 2), a value branded with the type `S` whose method takes it. It has no public constructor, and only the `tenant` module of `grdr-ports` builds one. An adapter can implement a method that takes one. Code outside `grdr-ports` can neither call that method nor pass a token it received to another type's method, because the brand differs.
- A **work kind** is an `OrgWork` value and an **answer** an `Admission` value: what an organisation's lifecycle state allows for that work (section 2).
- A **capability type** is a type whose value carries a power: `Setup` and the handles (`TokenMinter`, `Consumer`, `ConsumerSubscription`, `MemberReadAuthority`, `JobSteps`, and `KitAuthority` in a build with the `kit` feature), `JobRecord`, `PortsCall`, `Admitted`, `AdmittedTx`, `AdmittedStream`, `Fence`, `Lease`, `Holder`, the contexts and the other tenant witnesses of Rule 3. Code outside `grdr-ports` gets a value of one only from a function section 2 or 7 names.
- **ARCH-nnn** is a rule of the architecture lint: registered in design/03 section 2, configured in `architecture.toml`, run by `cargo run --locked -p grdr-archlint -- check` (#1580, #1582). Until design/03 section 2 is amended, new numbers come from the register comment on #1688: this RFC's rules are ARCH-029 `context-mint` (the handle rule, section 2), ARCH-030 `transaction-type` (section 2), ARCH-031 `testkit-scan` (section 5) and ARCH-032 `forbid-unsafe` (Rule 12), each with its own exemptions and failure name.
- A **protected change** is a change to a path on the protected-path list of `docs/team/06` section 2.1, such as `architecture.toml`, `surfaces.toml`, `dist.toml`, `limits.toml` or `.github/`. It is its own issue whose write set names the path, worked by `lead-agent-kit` or the chief architect, and it lands after `eval-security` and an evaluator on the other model pass (D-63). Review and CI hold it, not a session permission (ADR-0035).
- **`rfc-required`** is the check of design/30 section 3, which #1741 builds: it fails a pull request that touches an RFC-gated surface unless the pull request names an RFC whose state on its base is `Accepted` or `Implemented` (RFC 0001, "What holds the rule").

Rule 1. **Dependencies.** `grdr-ports` depends on `grdr-model` and `grdr-schema` and on no other crate, third-party crates included. The privileged daemon links it, so whatever it links is in the daemon's closure. design/03 section 8 allows Cargo features only in layers 3 and 4, plus `fips` in `grdr-crypto` and `jit` where YARA-X is linked. This RFC adds one more, `grdr-ports`'s `kit`, which adds `KitAuthority` and `Setup::for_kit` and nothing else (section 2), and which only `grdr-ports-testkit` enables (section 14). `for_kit` takes a `grdr_ports_kitkey::KitKey` from `grdr-ports-kitkey`, a layer 2 crate with no dependencies. `grdr-ports` does not re-export it, and only `grdr-ports` (as the `kit` feature's optional dependency) and `grdr-ports-testkit` may depend on it, so a program that calls `for_kit` names the key crate in its own manifest. It is published beside `grdr-ports` with `surface = "internal"` in its `[package.metadata.grdr]`, so that `grdr-ports` can be published with that optional dependency, and it promises nothing to anyone else who depends on it. ARCH-007 ("a `public` crate exposes no `internal` type") reads a crate's default features, as `cargo public-api` does, so `for_kit`, which exists only under `kit`, is outside it; `architecture.toml` names `for_kit` as the one item of a public crate that names an internal type. Cargo unifies features across the packages one invocation selects, so a build that selects `grdr-ports-testkit` beside a program compiles `grdr-ports` with `kit` for that program too. So every release and distribution build builds each program in a cargo invocation of its own (`cargo build -p <program>`), never with `--workspace` or at the root; neither `grdr-ports-testkit` nor `grdr-ports-kitkey` is in `default-members`, so a plain `cargo build` at the root selects neither; #1580's closure check reads the resolve of each program's own invocation in each release or distribution build's own environment, its target triple, its `RUSTFLAGS`, its `--config` and its features (`cargo tree -p <program> --target <triple>` under that environment), once more the full resolve over every target (`--target all`), and once more with every feature (`--all-features`), and refuses `grdr-ports-testkit` or `grdr-ports-kitkey` anywhere in the program's normal closure, and `grdr-ports` resolved with `kit`. It cannot look, and fails, when it reads no release environment or a resolve fails, so it never passes on an empty list. A manifest rule of the same graph check reads every package of the full resolve with every feature enabled, not only the workspace's members, resolves renamed dependencies, and refuses `kit` on a dependency on `grdr-ports` in any dependency table of any package but the workspace's own `grdr-ports-testkit`, target-specific tables and `[features]` entries included, a dependency on `grdr-ports-kitkey` from any package but the workspace's own two, and a normal or build dependency on any package named `grdr-ports-testkit`. It tells the workspace's own packages by package id, never by name. And a `cargo-deny` bans entry, `deny = [{ crate = "grdr-ports-kitkey", wrappers = ["grdr-ports", "grdr-ports-testkit"], reason = "only grdr-ports, for its kit feature, and grdr-ports-testkit hold the kit key (RFC 0002 Rule 1)" }]`, fails the gates' `cargo deny check` for any other dependent, a registry or git crate included. Its wrappers are a copy of `architecture.toml`'s edges into `grdr-ports-kitkey`, which are the one allow-list, and an archlint drift check fails when the two differ or the entry has no reason (section 14). The entry names its wrappers, so it cannot tell a package outside the workspace that takes the testkit's name from the testkit, and it reads the dev graph, which needs the testkit; the manifest rule and the closure check hold those two routes (section 15). A workspace-wide build, such as the gates' `cargo clippy --workspace` and `cargo test --workspace`, does compile `kit` into the programs it builds. No artefact of one ships, a program there cannot make a key without naming the key crate (`grdr-ports` has no path to it: E0433), and the manifest rule and the closure check refuse a program that names it, in any table (section 13). `grdr-ports-testkit` may also depend on the Arrow crates #1532 admits, at the same pins, for `MemEvents`, once #1475 has landed (Rule 12). It is never in the normal-dependency closure of a layer 4 program under any feature set a release or distribution build enables. An adapter crate may expose a `testkit` feature for its own tests, which adds only its fixture and the hook statements of section 5, and which is the only thing that brings `grdr-ports-testkit` into the crate's normal dependencies; no program and no `dist.toml` enables it. The distribution build runs an adapter's conformance tests in a cargo invocation of their own, never in the program build, so feature unification cannot carry `testkit` into a program (section 12).

Rule 2. **Async shape.** Every port and adapter trait has `Send + Sync` as supertraits. A method that reaches a back end is declared `fn name(&self, ...) -> impl Future<Output = Result<T, E>> + Send`, which an implementation may write as an `async fn`. A stream is a pull method of the same shape, not a `Stream` trait. No `async-trait`, no boxed futures and no `futures` crate in `grdr-ports`. The storage traits are therefore not dyn-compatible; section 12 says how a build selects an adapter. `Clock` and `Entropy` have the shapes RFC 0008 gives them. Until #1959 is decided, a storage adapter builds a `RetryState`, with its own `Health`, only inside its constructor `connect`, for its connection set-up before it accepts any call, and keeps only the `ClassReading` it copied; every call it serves after that returns its error to its caller unretried, whether its instance serves one organisation or many (RFC 0008 revision 8, section 4; section 5, "Retries"). There is no second, non-`Send` shape: the storage ports serve server targets only, and a WebAssembly host passes `now` and `Entropy` to the engine as values (layers 0 and 1 take them as arguments), so it implements none of these traits.

Rule 3. **Tenant witnesses.** A tenant witness is `&SingleCtx`, `&TenantCtx`, `&SetCtx`, an `OrgRead`, a `TenantPath`, a `ReadPath`, a `ListPrefix`, a `Planned` Events plan, an `OrgRows` result stream, a relational transaction, an `OrgBatch` or a `LakeBatch`. Every port method that takes tenant data in takes a witness derived from a `SingleCtx`. Every method that returns tenant data to module code takes a witness or returns the data inside one. A read takes the widest context its store can bind: `&TenantCtx` for the relational port, whose row-level security binds a `Set` through `delegation_snapshot`, and an `OrgRead` for Events and Blobs, whose keys are per organisation. An `OrgRead` comes from a `SingleCtx` or from a `MemberCtx`, the read-only context for one organisation of a delegation snapshot (section 2), so a provider's cross-organisation lake read is one plan per member and never holds a write witness. A deployment-scoped method takes no context. Two of them handle tenant data, `Subscription::fetch` and `Events::flush`. `flush` hands none out. `fetch` takes a call token, so only `grdr-ports` calls it: `bus::fetch_batches`, which takes the `ConsumerSubscription` a consumer runner's handle opened and returns the messages inside `OrgBatch` values, and the `Admitted` and `Dispatch` forwarders (section 8). `ResultStream::next` takes one too, called only by `OrgRows` and the forwarders (section 10). Where module code passes an adapter's own value back in, the port takes it inside a type only `tenant` builds: `Events::execute` takes `Planned<Self::Plan>`, and `Events::append` takes a `LakeBatch` (section 2). Section 14 gives the reading of D-35 this rests on.

Rule 4. **No organisation in inputs.** No input type of a port method has an organisation field. The organisation, and the delegation a context carries, come from the context, and the adapter writes them: the bus `org` header and the delegation stored beside it (section 8), the lake's `organisation_id` column (section 10), the `org=` segment of every path (section 2). The one exemption is `MemberCursor`, a page cursor over a snapshot's organisations, which names no organisation the caller acts for; `architecture.toml` lists it.

Rule 5. **Fences.** A fence is current while its token equals the newest token issued for its lease. Tokens only grow, and every `acquire` that returns `Held` issues a new one (section 7), so a fence names one acquisition, not one holder or one process. A fenced commit takes one of two forms, and every fenced commit on the surface names its form:
- *Lease-checked*, where the commit runs in the store that holds the lease table: the commit of a transaction opened with `Relational::write_fenced`, each migration's transaction inside `Migrator::apply`, and the catalogue transaction of `Events::flush`. Inside that transaction the adapter takes a lock on the lease row that `acquire` and `renew` conflict with, holds it until the commit ends, and commits only if the fence is current. The admitted locks are `SELECT ... FOR SHARE` on the lease row in PostgreSQL, the single writer (`BEGIN IMMEDIATE`) in SQLite, and the shared hold in `MemLeases`. An isolation level is not a substitute for the lock: under SERIALIZABLE, a read of the lease row followed by another holder's `acquire` is one read-write dependency, which PostgreSQL does not abort, so the stale commit would land.
- *Row-stamped*, for the bus, whose tables may live in another database (design/20 section 7, `bus.database`). `Bus::subscribe` stamps each claimed partition's consumer row with the claim's fence and holder in one compare-and-set that never lowers the stored fence, and returns the committed position from the same statement. `Bus::commit` succeeds only while the row holds the caller's fence, in one conditional row update (section 8).

Neither form trusts a caller's token. A fence comes only from a lease grant: no caller can build a `Fence`, a `FencingToken` or a `Lease`, and only `Setup` and the kit's handle build a `Holder`, which has no constructor from an id and which nothing parses (section 7). The fence of a claim or a commit must be of the partition's own lease, which `Admitted` checks before the adapter sees it (section 8). `Leases::check` is a point-in-time read. It protects no commit by itself; it lets a holder stop early. A superseded fence has one code wherever it is found (section 11), and no error carries a token.

Rule 6. **Nothing without a reference and a case.** Every method and every enum variant on the surface has a reference implementation in the test kit and at least one named conformance case. Where the variants of a data enum behave the same at the port, the port section says so and one case covers them. A method or query node whose semantics are not yet specified is not declared; it enters with its item by amendment (section 12). Each port section names the caller of each method and says when that caller is not in slice 0.

Rule 7. **Bounds are parameters.** Page and fetch limits, lease terms, query limits, stream byte bounds, flush thresholds, deadlines, cleanup grace, the age past which a replica's tenancy copy is stale and its confirmation interval, the lives of a relational and of a `Set` read transaction, the intervals, windows and resource limits of a store adapter's own checks, identifier lengths and bucket maps are values the caller passes or the adapter is built with, read from `limits.toml` (#279). No port type or reference adapter holds a tunable bound (ARCH-019). The storage format has two fixed ceilings, which are part of the format and not tunables: an identifier is at most 255 bytes, and each additional-data field at most 65,535 bytes (section 2).

Rule 8. **Errors.** Each port module has one error enum, and `Coded` (built by #278, RFC 0007) binds each variant to one registered code (section 11). Faults of the back end itself are one shared type, `StoreFault`, which every port error carries as `Store(StoreFault)`, so a full disk or a serialisation failure has one code whichever port met it. An operation that the check of section 2 does not admit, for the organisation's current state, the context's delegation or its expiry, is one shared value, `Refusal`, which every port error carries as `Refused(Refusal)`. Callers act on the code's class, never on the variant, so error enums are `#[non_exhaustive]`. Errors carry structural values only (keys, offsets, ids, byte indexes) and implement `LogSafe` (RFC 0009); an error about a rejected identifier carries the fault and the byte index, never the rejected text. An error logs as its `Code` (RFC 0009 R6), so the port name and any byte index are fields of their own that the log site writes, `log_record!(.., "port" => port, "error" => error, "index" => Count::new(..))`, with the port as a `wire_enum!` word. The port and the error are loggable by type and need no marker. The `index` field carries a marker that states its origin, a byte offset the adapter computed, and that it is not an identifier, unless the log-gate scan (#1989) traces it to a length or count of a standard collection. No port type holds a person-facing string. Each code's sentence is the `code.<code>.message` and `code.<code>.fix` language tokens of design/03 section 10, and a key or name inside it reaches the reader as a typed argument rendered in a left-to-right isolate (UX6), never by `Display` concatenation. Test kit types have no code of their own and hold no free text: a fixture that cannot open reports the `StoreFault` it met (section 5). They are listed in the ARCH-017 exemption list of `architecture.toml` (section 14), so the lint reads data and special-cases no name.

Rule 9. **Exhaustive data enums.** `TenantCtx`, `TenantScope`, `OrgRead`, `SetPurpose`, `Lifecycle`, `OrgWork`, `Admission`, `StateRead`, `DelegationRead`, `Dispatch`, `StorageClass`, `Partition`, `LeaseState`, `Acquire`, `Renew`, `Grant`, `Renewal`, `Stream`, `ProcessStream`, `Access`, `ValueType`, `Value`, `RefusedReason`, `Bound`, `StoreProperty`, `LakeTable`, `QueryIr`, `Direction`, `Comparison`, `Literal`, `Step`, `StepKind`, `ExpandKind`, `Completion`, `LimitReason`, `Coverage`, `StopPoint` and `Fault` are exhaustive, so a new variant fails every adapter's build until it handles it. Adding one is an amendment with its suite cases.

Rule 10. **Identifiers are ASCII.** `ObjectName`, `LeaseName`, `ConsumerGroup`, `ViewName`, `ColumnName`, `CheckpointRef` and `RuleName` hold 1 to `max` bytes, each a lower-case ASCII letter, an ASCII digit, `-`, `_` or `.`, and are neither `.` nor `..`. `max` comes from `limits.toml` and may not exceed 255. Anything else fails `parse` with `IdentError` (code `GRDR-TENANT-0001`): no normalisation, no case folding, no width folding. Ids from grdr-model (`OrgId`, `DelegationId`, `DelegationSnapshotId`, `DeviceId`, `SessionId`) render as ASCII by their own format (RFC 0009 section 4). A name a person chooses (an organisation, a device, a group named in Arabic or Japanese) lives in a relational column and never in a path, a key or additional data. This keeps the bytes the additional data authenticates identical across adapters, file systems and locales.

Rule 11. **Order is numeric or byte-wise.** Every order on the surface compares integers and times numerically and strings, identifiers and object keys by their bytes, never by a locale's collation. That covers `Blobs::list`, `Relational::snapshot_members`, the Events orders and positions, and `Lt`, `Le`, `Gt` and `Ge` on text literals. A PostgreSQL adapter sets `COLLATE "C"` on these comparisons; its fixture runs the ordering cases on a database whose default collation is `ja-JP` (section 5).

Rule 12. **Sealed ports.** The traits in sections 6 to 10 are port traits. Each has the supertrait `seal::Sealed`, whose module is private to `grdr-ports`, so no other crate implements one, by hand or through a macro. An adapter implements the adapter trait of the same port, in `grdr_ports::adapter`: `BlobsAdapter`, `LeasesAdapter`, `BusAdapter`, `SubscriptionAdapter`, `RelationalAdapter`, `ReadTxAdapter`, `WriteTxAdapter`, `MigratorAdapter`, `EventsAdapter` and `ResultStreamAdapter`. An adapter trait has its port trait's methods and semantics, except that its associated types are the adapter's own types under the matching adapter traits, `LeasesAdapter::acquire` and `renew` return plain grant values (section 7), and `ReadTxAdapter` and `WriteTxAdapter` have no `statements`: each is its transaction's statement runner, with `StatementRunner` as a supertrait (section 9).
- `grdr-ports` implements every port trait for `Admitted<A>`, where `A` implements the adapter trait, and for nothing else. The implementations live in the trust-core `tenant::admit`. They forward each call to `A` and wrap each associated type: a store's in `Admitted`, a transaction in `AdmittedTx` and a result stream in `AdmittedStream`; build every `Lease` from a grant (section 7); refuse a claim or a commit whose fence is not of the partition's own lease (section 8); and run the check of section 2 on every witness before `A` sees the call.
- `Setup::admit` and the kit's handle are the only ways to build an `Admitted`, so only the composition root, inside `tenant::start`, and the kit admit an adapter (section 2). The generated dispatch of section 12 implements the adapter traits and is admitted like any adapter.
- No `unsafe` reaches the types. A type barrier holds only where no `unsafe` reaches the code that holds the type, since a zeroed call token or a transmuted context passes any type check. The barrier is the register check of SP-9 (design/35 section 2.4, #1475), and it covers every capability type. It reads each crate after macro expansion and name resolution, on the workspace and on the distribution build's resolved closure. Every crate in the dependency closure of a crate that depends on `grdr-ports`, build and proc-macro dependencies included, holds and emits no `unsafe`, or `security/unsafe-register.toml` lists it for what it holds or emits; the toolchain's crates are one entry. Every `unsafe` block, `unsafe fn`, `unsafe impl`, `unsafe extern` block, unsafe attribute and inline or global assembly in a crate the register does not list fails the build, whatever produced its tokens: the crate's source, another crate's macro or derive, or a proc macro. `#![forbid(unsafe_code)]`, which ARCH-032 `forbid-unsafe` requires of every workspace crate other than the OS adapter crates and `grdr-ffi`, and the distribution build's compile of each closure crate that depends on `grdr-ports` with `unsafe_code` forbidden and lint capping off, stay as a first check. They are not the barrier, because the lint does not see what another crate's macro emits. Until #1475 has landed, no crate that names a capability type or an item of `tenant`, `storage` or `adapter`, judged by ARCH-029 on its source, takes a registry dependency or a proc macro. The daemon names only RFC 0008's `clock`, `entropy` and `retry`, so this interim rule does not reach it; if it ever names one of those items, the rule does.

Data classes (P8): every type on the surface is `structural`, except the ids the contexts log, which are `identifier` and log as `LogValue::Id` (RFC 0009), payload bytes (blob objects, bus payloads, the archive bytes of a `LakeBatch`, `ArrowIpc`), which carry the classes of what they hold and are never logged, and positions, predicate literals and a statement's parameters and rows (`Value`), which carry their columns' classes. The port records no per-object data class. `StorageClass`, with the lane for archive objects, is enough for slice 0: retention is by class and lane, erasure of content is by destroying the root session's content key, and reduction rewrites by lane (design/04 section 10), so none needs a class inside an object. A per-object class that must be authenticated would be a new additional-data tag (section 2), which is the costly kind of change and needs its own RFC.

Assurance effect (P1): none. No action class changes `visibility`, `control`, `on_failure` or `tamper`.

`OrgId`, `DelegationId`, `DelegationSnapshotId`, `ProviderId`, `HolderId`, `IdError`, `Timestamp` and `UploadedLane` are grdr-model types (RFC 0009). The five ids are `Clone`, `Eq`, `Ord` and `Hash`, parse from and render to ASCII (`as_str`), and carry no authority: holding an id builds no context or `Holder`. The server takes `UploadedLane`, the lanes that leave the device; each lane is declared once (RFC 0009 section 5). `PageLimit` is `grdr_ports::storage::PageLimit` (section 6). `TenantScope` is named so because RFC 0007 (#1710, decided) states `grdr_schema::limits::Scope`, and #1710 AC-3 refuses a type name that RFC 0002 and RFC 0007 both state; RFC 0002 renames its own while it is in review.

Contexts:
- No code outside `grdr-ports` constructs `SingleCtx`, `SetCtx`, `MemberCtx`, `JobRecord`, `OrgBatch`, `LakeBatch`, `Planned`, `OrgRows` or `PortsCall`, and none builds an `Admitted`, an `AdmittedTx`, an `AdmittedStream` or a handle: only `tenant` does. Fields are private, and none implements `Default`, `Deserialize` or a `From` from a string or an id. The handles' mint methods, `tenant::members` and `tenant::mint::fetch_batches` are the only places that build a context.
- Every minting site is under `crates/grdr-ports/src/tenant/`, which `security/trust-core.paths` lists. `PortsCall`, `Admitted`, `AdmittedTx`, `AdmittedStream`, `Dispatch`, `OrgBatch`, `LakeBatch`, `fetch_batches`, `Planned`, `plan_query`, `OrgRows` and `run_query` live in `tenant::mint`, the port trait implementations for `Admitted` in `tenant::admit`, and their constructors are visible only inside `tenant` (`pub(in crate::tenant)`). `storage`, `storage::bus` and `storage::events` re-export the public items, so their paths in sections 6, 8 and 10 are unchanged. A change to the token, the seal, the forwarders, the grouping that keeps a batch to one organisation, the pairing of a plan with its organisation, the lifecycle table or any constructor therefore takes the trust-core review.
- There is no conversion from `SetCtx`, `MemberCtx` or `TenantCtx` to `SingleCtx`, and no way to change a context's work kind: other work needs its own mint. A write takes `&SingleCtx` or a value built from one, so a `Set` or member context calling a write does not compile.
- `TenantCtx::scope` returns the organisation or the snapshot id; adapters bind storage with its `as_str` form (a relational adapter's binding, which no statement can change, section 9; object prefixes). A `SetCtx` exposes no organisation list. Its members come only from `tenant::members` (below).
- `TenantKey<K>` compares and hashes on `(OrgId, K)`, so a cache keyed by it cannot return one organisation's entry for another.
- The contexts are `Send + Sync + Clone + Debug + LogSafe`. They print and log only the organisation id or the snapshot id (as `LogValue::Id`, data class `identifier`, RFC 0009) and implement neither `Serialize` nor `Deserialize`, so a context cannot be written out and read back. A clone kept inside the process is safe only because every store operation checks it again (Lifecycle, below), against the organisation's current state, the context's delegation and, for a set or member context, its expiry by the authority's clock.
- The contexts will also carry the acting principal and the purpose from the token (D-35), behind private fields filled from the token's claims. Adding them changes no port signature. The accessors the audit and usage-ledger adapters read arrive with the audit item by amendment (section 12).

Minting boundary. The mint authority never leaves `tenant`: it is `pub(crate)`, it lives in a private static of `tenant`, and no public item takes or returns it. Every other way to a context is a handle that `tenant` built for one purpose. The boundary stops module code that is mistaken or unreviewed. Hostile code compiled into the server process is ADV-9 (design/02), which dependency admission and the trust-core evaluators answer, not this boundary.
- **Start.** `tenant::start(table, clock, limits, setup)` succeeds once per process and fails `AlreadyIssued` (`GRDR-TENANT-0009`) after that. It binds the process's one tenancy table, its `Clock` (RFC 0008) and its `TenancyLimits`, which the composition root builds from `limits.toml`: every mint, every check below and `tenant::members` read them from the authority, and no function takes a table or a `now`. It runs `setup` once with a `Setup` and returns what `setup` returns. The composition root calls it before any other code of the program runs, with the replica's table, which answers `Unknown` until it has loaded. The server does not start if `start` fails, so code that started first stops the start rather than holding the authority unseen.
- **Setup.** `Setup` admits adapters (Rule 12) and builds the process's `Holder` (section 7) and the handles. Its lifetime ends when `setup` returns, and it is neither `Send` nor `'static`, so the compiler keeps it out of a `static`, a spawned task, a `'static` boxed closure and any value `setup` returns. The composition root builds every handle in `setup` and starts the runners after `start` returns; inside `setup` its own code holds the authority, which is why it is a trust-core path.
- **Handles.** Each handle mints within one scope that `tenant` fixed when it built it, so a handle erased to a trait object, kept in a `static`, returned as an opaque type or carried in another crate's extension map gives nothing beyond that scope:
  - `TokenMinter<V>`, for the authentication middleware of `api` and `ingest`: a `SingleCtx` or a `SetCtx` for a token its verifier `V` accepts, as the API itself would, and only for a work kind in the list it was built with, which the composition root takes from #312's trust-core registry of each site's work kinds; another work kind fails `WorkNotListed` (`GRDR-TENANT-0014`), and a token `V` refuses fails `TokenRefused`;
  - `Consumer<B>`, for a partition consumer runner: a `Process` context for each message `fetch_batches` takes from one consumer group and one `ProcessStream` of the store's admitted bus, a stream other than `Control`; a `control` consumer gets its handle with the amendment that adds its runner;
  - `MemberReadAuthority<A>`, for D-35's workbench read path: a `MemberCtx` for each member of a set's snapshot in the store's admitted `Relational` whose delegation passes;
  - `JobSteps`, for J-1's job runner: a step's context for a `JobRecord` J-1's claim returned;
  - `KitAuthority`, for `grdr-ports-testkit` only: every mint and admission, in a test process. It and `Setup::for_kit` exist only with `grdr-ports`'s `kit` feature, and `for_kit` takes a `KitKey`, which only `grdr-ports-kitkey` makes and only the kit may depend on (Rule 1). A program built in its own invocation, as every release and distribution build builds it, has no `for_kit` (E0599), a qualified `<Setup<'_>>::for_kit` included; in a workspace-wide build a program that does not name the key crate cannot reach the key (E0433, because `grdr-ports` does not re-export it); and the manifest rule, the closure check and the `cargo-deny` bans entry refuse a program that reaches it, in any dependency table, in any release build's environment and through any crate of the resolve (eval-adversarial K1 to K10b; section 13).
- **Where handles appear.** ARCH-029 `context-mint` is a syntactic check of each crate's source as written, on the pinned stable toolchain, with no macro expansion and no typed front end. It follows `mod` declarations, `#[path]` and every `include!` of a literal path, and fails an `include!` of any other, so generated code such as the dispatch of #1593 is read as the file it is. A module fails when:
  - it names `tenant::start`, `Setup` or a handle type outside the modules `architecture.toml` lists for that name, by a path or by a name that a `use`, a re-export, a glob import of any module or a type alias anywhere in the crate brought in;
  - it glob-imports `tenant::authority`, or re-exports or type-aliases one of those names, listed or not;
  - a `macro_rules!` body in it names one, listed or not, since the macro can be invoked anywhere;
  - a struct field in it has a handle type outside the listed modules, or is a public field of one inside them;
  - the identifier `for_kit` or `KitAuthority` appears in it, in any form, outside `grdr-ports-testkit`.

  The lists are these: `tenant::start`, `Setup` and every handle type but `KitAuthority` the composition root, which builds the handles, and the kit; also `TokenMinter` the middleware; `Consumer` and `ConsumerSubscription` the partition consumer runners; `MemberReadAuthority` the workbench read path; `JobSteps` the job runner; `KitAuthority` and `Setup::for_kit` the kit. Every module on these lists is a trust-core path, and the lint fails a listed module that no glob of `security/trust-core.paths` covers (section 14). A handle that reaches an unlisted module by inference, through a listed module's function, or erased into a trait object still mints only in its scope (Handles), and a macro of a crate outside the workspace that emits a path naming a handle does the same; until #1475 no crate that names these items takes a registry dependency or a proc macro (Rule 12). A macro-made call of `tenant::start` costs a failed start, not the authority (Start). The compiler, not the lint, keeps the authority itself out of every other module.
- **Stored records.** `fetch_batches` (section 8) takes a `ConsumerSubscription`, and with J-1 `single_for_step` takes `JobSteps`. A claimed job yields a `JobRecord`, whose only use is that handle; it exposes no value another mint accepts. Outside the kit there is no mint from a bare organisation id.
- **Delegation snapshots.** `tenant::members` takes the `SetCtx` and a `MemberReadAuthority`, which `Setup::member_reads` builds over the store's own admitted `Relational` and which does nothing else: it admits no adapter, mints no single context and opens no `ConsumerSubscription`. So member ids come from the store's snapshot rows only, the authority's table decides which are in force, and a row whose delegation the table records for another organisation, or for a provider other than the set's, is withdrawn (below).

No adapter is a minting site: adapters return plain ids and `grdr-ports` mints, so adding an adapter needs no protected change.

Adapter-defined witnesses. `Events::Plan`, `Events::Results`, `Relational::ReadTx`, `Relational::WriteTx` and `Bus::Subscription` are types the adapter chooses. The port closes each by type:
- An Events plan reaches `execute` only inside `Planned<P>`, which only `plan_query` builds: it calls the adapter's `plan` under the context and pairs the result with the context's organisation. `Planned` gives no `&mut` to the plan, and `execute` takes `Planned<Self::Plan>`, so a plan module code builds itself, from the adapter's own type, does not reach the adapter (E0308), and a `Planned` it builds does not compile (E0451). `execute` serves the organisation of `Planned::org` and no other (section 10).
- Rows reach module code only through `OrgRows<R>`, which only `run_query` builds, from the stream the adapter's `execute` returned for a `Planned`. `ResultStream::next` takes a call token, so a stream module code builds itself cannot be read (E0624), and an `OrgRows` it builds does not compile (E0451).
- A subscription is held as `Admitted<S>`, which gives module code no access to `S`, and `fetch_batches` accepts only a `ConsumerSubscription`, which only a `Consumer` handle opens over the store's bus.
- A transaction is held as `AdmittedTx<T>`, a type apart from the store's `Admitted<A>` and a result stream's `AdmittedStream<R>`, so only a transaction carries a transaction's state. A repository reaches the adapter's transaction type `T`, which is its statement runner, through `ReadTx::statements` or `WriteTx::statements` (section 9). Code that holds a `&mut T` could put another `T` in its place, which matters only if it can build one bound to another organisation, and could reach the session if `T` gave it. So ARCH-030 `transaction-type` checks, on the adapter crate's source, that a type an adapter names as its `ReadTx` or `WriteTx` has no public field, no public function that returns it outside its adapter trait implementation, none of `Default`, `Deserialize`, `From`, `TryFrom` and `FromStr`, and no public method that takes SQL text (`&str`, `String` or `Cow<str>`) or returns or borrows a session or connection type `architecture.toml` lists for its driver. An enum each of whose variants holds such a type passes, which covers the generated dispatch's transaction enums. The slice-0 lint item has a case for each: a `WriteTx` with a public field fails, one that implements `Default` fails, and a generated two-variant enum passes.

Forwarders. Generated code holds no token, so a generated dispatch cannot pass `PortsCall<Dispatch>` on to an adapter. Every adapter trait with a method that takes `PortsCall<Self>` is therefore implemented for `Dispatch` in `tenant::mint`, and the generated dispatch names `Dispatch` as that type, nested for more than two adapters. In slice 0 these are `SubscriptionAdapter` and `ResultStreamAdapter`. A generated Events dispatch passes a plan on with `Planned::split`, which keeps the plan's organisation. The RFC that adds a later token-taking method adds its `Dispatch` implementation in the same text. J-1's claim method is the first: its amendment either puts the method on an associated type that `Dispatch` implements, or implements the Jobs adapter trait for `Dispatch` in `tenant::mint`, and the lead of J-1 plans that forwarder.

Lifecycle. Every `SingleCtx` carries the work kind it was minted for and the organisation's lifecycle state as its minting site read it from the replica's `TenancyTable`, which the minting site uses to choose its response; every store operation reads the state again (below). `TenancyTable` is the replica's in-memory copy of each organisation's state and of each delegation's state and epoch, refreshed by bus notification as design/21 section 5 refreshes delegation epochs. It reads each delegation's row and revocation marker together and keeps its copy with `DelegationRead::merge`. A change the replica reads from the tenancy history moves the copy to `Floor { epoch }`, and the replica then reads the row and the marker (Revocation, below). `merge` keeps the read with the higher epoch, the one not in force at an equal epoch, a `Current` at or above a floor over the floor, the higher of two floors, and any of these over `Stale` or `Unknown`, so a copy never moves to a lower epoch, and a rebinding comes into force when the read on its notification finds the row in force at the new epoch; how it reads the rows is otherwise question 3. It is not a port. The server implements it over that copy, and the composition root binds that one implementation in `tenant::start`, so every mint and every check reads the same table. By the trait's contract, an implementation that answers `Stale` or `Unknown` raises the replica's Degraded health, with `GRDR-TENANT-0008` for `Unknown`; the server item that builds the table has the case, and `MemTenancy` counts the answers.
- `StateRead::Current(s)` mints with `s`. `Stale`, a copy the replica has not confirmed within the `limits.toml` bound `tenancy.copy-life` (Revocation, below), mints with `Unconfirmed`, which is not a state of design/21 section 13: it counts as the most restrictive state that still serves P4, so its row defers every work but reads, and the replica raises Degraded. `Unknown` fails `LifecycleUnknown` (`GRDR-TENANT-0008`) at a mint and at every store operation, and the replica raises Degraded with that code, so a replica that holds no state for the organisation refuses the work and shows it; it never assumes one.
- The work kind comes from the minting site: the kind the request's route declares, as data, at the middleware; `Process` at `fetch_batches`, for every consumer of admitted messages; the kind the job's kind declares at J-1's step, which J-1's job-kind registration records.
- `Lifecycle::answer(work)` reads the table below. `grdr-schema` generates it as a constant from `schema/tenancy/lifecycle.toml`, and generation fails on a missing, extra or unparseable cell, so `answer` is total and the table is data (P14).
- Every store operation runs one check, in `Admitted`, which keeps the authority's table and clock. Each port method that takes a witness, each use of a relational transaction (`statements` and `commit`, section 9) and each `OrgRows::next` run it before the adapter sees the call. Every witness carries the organisation, work kind (`Read` for a member context), delegation and expiry of the context it was built under:
  - an expiry the authority's clock has passed fails `Expired`;
  - a delegation is judged in the order below ("Provider work and delegations");
  - the state is read from the table as a mint reads it, so a state the table does not hold fails `LifecycleUnknown`; a read needs the state's answer for the work kind to be `Allowed`, and a write also a work kind that writes (every kind but `Read` and `Export`).

  A failure is the port's `Refused(Refusal)`. A `Set` read names no organisation and no delegation, so its check is the expiry and its transaction's shorter bound. The snapshot binding of design/21 section 2, as section 14 amends it, drops a member from the rows it reaches at the next statement once the member's delegation is revoked, expired or rebound, or the member is `shredded` (section 9). A context, path, plan or transaction kept past a change of state or delegation therefore reads and writes nothing the new state or delegation refuses, except rows `append` already buffered (section 10) and, after a change of state, a borrow of a relational transaction already taken, which the transaction's bound ends; after a revocation that borrow's next statement is refused in the store, which counts the marker (section 9). `Bus::append` to the `usage` stream needs only the current answer to be `Allowed`, whatever the kind, because a usage record meters work that was allowed to start.
- A minting site reads `SingleCtx::answer` to choose its response, and nothing branches on `Lifecycle`: `ingest` answers `Deferred` with a spread `retry_after_ms` and `Refused` with the code; `api` refuses with the code, for reads as for changes; a consumer handles its batch as below.

Process is a consumer handling messages that `ingest` already admitted. Maintain is retention, compaction, reduction, erasure and the purge, which D-57 requires in every state that holds data. `key_unavailable` refuses a change because every change writes its `audit.admin` record through the outbox into the checkpoint chain (design/21 section 12), which waits for the key, and a change with no record never exists. The proposals go to design/21 (section 14).

Consumers. A batch whose answer for Process is `Allowed` is processed. One that is `Deferred` is skipped as design/20 section 4 step 7 skips an organisation whose key cannot be unwrapped: the consumer records the skipped device ranges and lets the partition advance, and `ingest` rewinds those lanes once the answer is `Allowed` again. One that is `Refused` is skipped and counted: a `migrated` or `shredded` organisation's data has no home here. A batch whose context failed to mint is handled as `Deferred` for `LifecycleUnknown` and `DelegationUnconfirmed` and as `Refused` for `DelegationNotActive`, and the consumer reports the code. A consumer that writes a non-allowed batch anyway is refused by the port, so the rule fails closed.

Provider work and delegations. Work that writes into several organisations, such as a baseline rollout ring by ring (D-11), runs as one job per organisation; no cross-organisation write context exists. A context carries the delegation and epoch of the token its work began under, and every way work reaches a store checks them against the authority's table, whose answer is a `DelegationRead`:
- `Current` for the context's organisation at the recorded epoch with the delegation in force (`active` or `expiring`, design/21 section 5) passes.
- `Current` for another organisation, or at the recorded epoch and not in force, or at an epoch above the recorded one, fails `DelegationNotActive` (`GRDR-TENANT-0005`): the delegation is not this organisation's, or was revoked, expired or rebound after the work began, so the work is refused.
- `Floor { epoch }` fails `DelegationNotActive` for a record below its epoch, which the revocation ended.
- `Current` at an epoch below the recorded one, `Floor` at or below it, `Stale` (a copy not confirmed within its `limits.toml` bound) and `Unknown` fail `DelegationUnconfirmed` (`GRDR-TENANT-0012`), so the work is deferred: the replica cannot confirm the delegation, and a delegated read does not serve P4.

A copy that holds a revocation marker newer than its row reads as `Current` at the marker's epoch and not in force, so a record at the old epoch is refused.

The checks are these:
- `TokenMinter::single` checks the token's delegation, as the API checks epochs on each request.
- The bus stores the context's delegation with each message it appends (Rule 4), and `fetch_batches` checks it before it mints the batch's context. A provider's command still queued on the `control` stream when the owner revokes is not dispatched.
- With J-1, a job records the delegation of the context that enqueued it, and `JobSteps::single_for_step` checks it at every step. Revocation increments the epoch, so it takes effect at the job's next step, as it does at the API's next request (design/21 section 5: "Revocation by the organisation owner is immediate").
- Every store operation under a delegated context, or a path, plan, batch or transaction built from one, checks it (Lifecycle, above), so a kept context, a running step's included, fails at its next call.
- A delegated relational transaction runs where each statement reads the latest committed revocation, and the store reads its delegation's revocation marker when it opens, at every statement and as a write commits. It takes no lock on the delegation (Property 9, section 9).
- `tenant::members` checks each member's delegation (below).

Revocation. Revocation, expiry and any rebinding of a delegation append its revocation marker with the new epoch and update the delegation row (design/21 section 5), and every reader counts the marker. From the commit, the token exchange and the snapshot writer issue nothing for the delegation, and every relational open, statement of a delegated transaction, commit step and `Set` statement refuses it, because each reads the marker in the store (Property 9, section 9). Three properties hold for every tenancy table and every store that holds tenant data, whatever its back end. The server item that builds the table and each store adapter item hold them, and how is their design (#2002 for PostgreSQL).
- **Property 13, revocation is one commit.** Revocation, expiry and rebinding are one commit of marker, row and change, and every lifecycle move appends its change in its own commit, so a replica brings its whole copy, states and delegations, up to date by one read. No change waits on another organisation's change. The revoking call's outcome is that commit: it returns once the commit is visible, also when the commit waits on synchronous replication. A notification is a hint sent after the commit. No replica uses its payload, and its failure neither undoes nor holds back the change: a replica it fails to wake confirms the change at its next read, within `tenancy.copy-life`. Only the tenancy-change path notifies, a declared statement cannot send a notification (Property 7), and a forged one costs a replica one read and changes nothing. Cases: a revocation paused at `RevokeBeforeCommit` changes nothing until it commits; an idle or paused change of one organisation holds back no other organisation's; a lost or forged notification changes nothing; the change of a revocation whose notification fails is still read.
- **Property 14, complete confirmation.** A replica confirms its copy only by a read that returns every change committed before that read began, whatever order numbers and commits took. On each notification, and at least every `tenancy.confirm-interval`, it reads the changes since its last confirmation, holds each delegation change as a floor at the change's epoch, reads the row and the marker, applies changes to a subject in their commit order, each at most once, and never lowers an epoch (`merge`). Its copy is confirmed from when that read was sent, on the authority's `monotonic` clock. A copy not confirmed within `tenancy.copy-life` answers `Stale` for every state and delegation, which defers the work and raises Degraded. Cases: a change begun first and committed last is returned by the first read after it commits; two changes to one subject leave the replica with the later commit's state; a change read twice changes nothing; a replica that loses one notification and receives a later one reads both changes.
- **Property 15, restore** (SR-50). After the store is restored to an earlier point, or fails over to a copy that may have lost commits, every revocation and rebinding after that point is replayed with its epoch before the store takes traffic (design/20 section 9). A replica that finds the store's history behind its copy drops its whole copy and its read cursor, confirms nothing until a full read completes, and raises Degraded (`GRDR-TENANT-0016`). Test: the restore case of the server item that builds the table, and each store adapter item's restore scenario (design/20 section 12).

`tenancy.copy-life` and `tenancy.confirm-interval` are `limits.toml` rows (Surfaces changed). So a Blobs, Bus or Events operation under a revoked delegation passes on a replica for at most `tenancy.copy-life` after the commit, and a relational one not at all, a kept transaction's next statement included (Property 9). The one residual in the store is a delegated write whose commit read the marker before the revocation committed: it passed its check and becomes visible as that commit completes. A revocation whose own commit waits on synchronous replication takes effect when that commit becomes visible.

A job the organisation itself enqueued records no delegation. When `erase` arrives (section 12) it takes `&SingleCtx` only.

Member contexts. `tenant::members` calls `Relational::snapshot_members` (section 9) for the members of the snapshot, read under the set's binding, each with the delegation and epoch the snapshot recorded, and checks each delegation as above. It also withdraws a member whose delegation the table records for a provider other than the set's, the token's `prv` (design/21 section 5). It mints a `MemberCtx` with the set's snapshot id and expiry for each member that passes, lists in `withdrawn` those that fail `DelegationNotActive` and in `unconfirmed` those that fail `DelegationUnconfirmed`, so the reader shows "could not look" for them rather than nothing. A `MemberCtx` holds the delegation as its page read it, and every operation under it checks that delegation again, so revocation stops a provider read at its next call, and a result stream at its next batch. A `SetCtx` and each `MemberCtx` carry the workbench token's expiry (a life of 5 minutes, design/21 section 5), and every path, prefix and plan built under them carries it too. `tenant::members` and every operation under them fail `Expired` (`GRDR-TENANT-0011`) once the authority's clock has passed it, and no caller supplies the time, so a context kept past its token reads nothing more.

Each check stops one thing:
- the seal and the mint authority stop module code from minting at all;
- the authority's one table stops work the state does not permit, where the work starts and at every store operation, however long ago the context was minted;
- the delegation checks stop a provider's queued, running, stored or kept work after revocation, wherever it is picked up;
- the `Set` and member contexts stop a provider read from writing.

The middleware item and J-1 each carry their cases (section 13).

Who looked (P8, D-35). Reads through the port record nothing. The read audit entry is written above the port by `api` and `query`. A read under a `MemberCtx` records the snapshot id the context carries, which is the cross-organisation case a person most needs to see.

Paths:
- `TenantPath::new` is the only way to a writable path, and the organisation segment comes from `ctx`. A path and a prefix keep their context's work kind, delegation and expiry, which every Blobs call checks (Lifecycle, above). `ReadPath::new` builds the same key from an `OrgRead`; `TenantPath::read` returns the `ReadPath` of a writable path.
- `ReadPath::new` and `ListPrefix::partition` fail `ClassForMember` for `Content` and `Archive` under an `OrgRead::Member`: content never forwards through a delegation (design/21 section 4), and an archive segment holds content fields until its reduction.
- `AggDaily` takes only `Partition::Month`; every other class takes only `Partition::Day`; a mismatch is `PathError::PartitionForClass`.
- The rendered key is `org=<id>/class=<class>/day=<yyyy-mm-dd>/<name>`, `org=<id>/class=agg_daily/month=<yyyy-mm>/<name>`, or `org=<id>/class=archive/lane=<lane>/day=<yyyy-mm-dd>/<name>`. Class names render as `decision`, `activity`, `content`, `observable`, `agg_daily` and `archive`; lanes as `decision`, `spine`, `bulk` and `evidence`. The path vectors of #313 pin one key per class and lane, which is the case Rule 6 needs for each `StorageClass` variant.
- `ListPrefix::partition` renders the partition directory with its trailing `/`, so retention, cleanup and restore list one partition, never a whole organisation. A `Set` context cannot reach a prefix. `ObjectKey::under` turns a key an adapter listed into an `ObjectKey`, and returns `None` for a key outside the prefix or one that breaks Rule 10, so a listing cannot return a key from another organisation's prefix.
- `Date::parse` accepts exactly `YYYY-MM-DD` and `YearMonth::parse` exactly `YYYY-MM`, in ASCII digits `0` to `9` on the proleptic Gregorian calendar; Arabic-Indic or full-width digits fail with `DateFault::Format`. `Date::from_timestamp` takes the UTC date. A partition date is UTC, and retention arithmetic runs on UTC dates. It is never shown to a person as the event's local date; a view converts the event's time to the viewer's zone (D-69).
- `KeyId::parse` accepts 1 to 65,535 bytes of printable ASCII (`0x21` to `0x7E`), so a KMS key id or ARN fits and `for_object` is total.

Additional data. `Aad::for_object` produces `org_id ‖ class ‖ partition ‖ key_id` of design/21 section 2: the 11 ASCII bytes `grdr-aad-v1`, one `0x00` byte, then the organisation id, the class field, the partition value and the key id, each as a 2-byte big-endian length followed by its bytes. The class field is the class name, and for `Archive { lane }` it is `archive.<lane>`, for example `archive.decision`, so a segment does not authenticate under another lane's path. Lane decides retention (13 months for `decision`, 184 days for the others; values from configuration, read by R-3) and reduction. The partition value is `yyyy-mm-dd`, or `yyyy-mm` for `AggDaily`. Test vectors shared with `grdr-tenancy-ref` pin the bytes (#311, #313).

The object key layout, the identifier rule of Rule 10 and this encoding are a storage format. Changing any of them needs an RFC, a new tag (`grdr-aad-v2`), readers that accept the old tag for the longest retention (13 months), and a rewrite job that ships in the same release. These strings are format constants of the code namespace `grdr`, not brand strings, and do not change under a rebrand.

Callers in slice 0: the composition root calls `tenant::start`, admits the adapters and builds the handles; the authentication middleware mints through its `TokenMinter`, and `ingest` and `api` act on the answer; `store` fetches through its `Consumer` handle and writes paths (#1547); the lake read path (#1554) builds read paths and prefixes, and `query` reads through `plan_query` and `run_query`. The provider workbench read path (D-35) and J-1, which are not in slice 0, call `tenant::members` and `JobSteps::single_for_step`; the minting boundary is declared whole now so the trust-core review sees every minting site once.

This section amends RFC 0008 section 5 (#1924), whose `Case`, `Failure`, `Suite`, `Outcome`, `CaseResult`, `Report` and runner rules stand. It adds `kind` to `Case` and `CaseResult`, the outcome `NotApplicable(Fault)` and the storage suites. `passed()` stays true when no case failed, so a `NotApplicable` case, which names its fault, does not fail a report. `to_toml` writes a case's kind and a `NotApplicable` fault by their snake-case names.

Rules of the kit:
- A storage suite is generic over a `Fixture` whose `Adapter` implements its port's adapter trait. The suite admits it with the kit's authority and drives it through the port trait, so every case also exercises the `Admitted` forwarder. Cases share the fixture's store. Each case isolates itself with organisation ids, names and lease names drawn fresh from `SeededEntropy` seeded by `seed`, and none assumes an empty store, so a suite runs against a shared PostgreSQL database or bucket. The report records the seed, so a failure replays.
- `open` builds the adapter with the statement sets it is given, as the composition root builds a relational adapter with every repository's set, and returns a handle over the fixture's durable state. A suite whose adapter runs no declared statement passes `&[]`; the relational and Events suites pass the kit's probe set and, for the statement cases, sets of their own (section 9). A second call models a process restart, or a second process where the fixture keeps the first handle open. `leases` returns the lease store the adapter's fenced commits check: for Events and Relational it is the lease table in the same store (Rule 5).
- No fixture method takes or returns a tenant context. Each `RelationalFixture` method writes the store by the adapter's own SQL behind its `testkit` feature: `snapshot` the rows of a delegation snapshot for its provider, `delegation` an in-force delegation row, `revoke` the revocation of design/21 section 5 (marker, row and change in one commit, with `RevokeBeforeCommit` inside it, and the notification after it), and `set_state` an organisation's state, revoking its delegations in the same transaction when it moves to `shredded`. `MemRelational`'s fixture is the reference. Every negative `Set` case runs beside a positive one, in which a live member's rows are returned. The suite mints every context a case uses with `kit()`, the kit's handle, whose table is `tenancy()`, the kit's `MemTenancy`, and whose clock is `clock()`, the kit's one `ManualClock`, which it hands out as an `Arc` from a kit-private `OnceLock<Arc<ManualClock>>`, so a reference adapter's `RetryState::new` takes it. A case sets in the table the states and delegations it needs, sets each expiry from the clock's reading, and advances the clock to pass one. `unknown_answers` counts the `Unknown` answers the table gave, which stand for the replica's Degraded signal in a case. `Suite::run` holds the clock with the arming state, so no other suite moves it.
- `block_on`, `spawn` and `settle` run futures on the adapter's own executor. The in-memory fixtures use the kit's `block_on` with their own poll bound; a network adapter uses its runtime. `Stalled` means the future did not finish within the fixture's own wait bound.
- `stop_at` arms one point in the adapter's next operation that reaches it. `Crash` makes that operation return at the point and leaves durable state as a process kill there would, with no clean-up; the case then calls `open` again. `Pause` holds the operation at the point until `resume`. The bus points sit just before the stamping statement of `subscribe`, after any read the adapter makes, and just before the conditional update of `commit`, so a case can place a second operation inside the first. `FlushBeforeNotify` sits in a flush after its catalogue commit is visible and its rows are dropped from the buffer, and before any file-list cache learns of the commit. `TailBeforeRead` sits in a holder's answer to a tail read after it reads its buffer and before it checks its fence and reads its floor (section 10). A Crash case uses only `Crash`; a Contract case may use `Pause`.
- Arming lives in the kit. `stop_at` arms a point through `arm`, or returns `CannotStop` for a point the adapter has no hook for. `reach` is the kit's hook function: while its point is unarmed it is ready on its first poll with `Ok(())` and changes nothing; armed with `Pause` it waits for `resume`; armed with `Crash` it returns `Reached`, which the kit converts into each port's error as `Store(StoreFault::Unavailable)`. Arming is per process, and `Suite::run` holds it for the whole run, so two suites in one test process do not see each other's points.
- An adapter crate's `testkit` feature may add only two things:
  - the fixture, in a module named `testkit`;
  - hook points. A hook point is the one statement `::grdr_ports_testkit::reach(StopPoint::<point>).await?`. The leading `::` names the extern crate, so no local module or `use ... as` alias of that name can stand in for the kit, and the only argument is the point.

  ARCH-031 `testkit-scan` fails any other use of the feature, judged on macro-expanded code and on `cargo metadata`:
  - in the crate, a `cfg` or `cfg_attr` on any other item or statement, `cfg!(feature = "testkit")` in an expression, or a hook statement of any other form;
  - in its manifest, a build script, since one can turn the feature into a `cfg` the source never names and no reading of the script tells reliably whether it does; an entry of `[features] testkit` other than an optional dependency, or a feature of one, that only the `testkit` module and the hook statements use; and a dependency named `grdr-ports-testkit` that is renamed or is not the release's own `grdr-ports-testkit` package.

  It runs on the workspace and on the distribution build's resolved closure. A crate that needs a build script moves it into a crate without the feature.
- The first case of every suite is `unarmed_reach_is_inert`: with nothing armed, `reach` is ready on its first poll with `Ok(())` for every `StopPoint`, and the kit's arming state is unchanged afterwards. The case shows that the kit's `reach` is inert, and the scan shows that every hook statement calls that `reach`; together they show that an unarmed hook does nothing. Neither says anything of the fixture module (section 12). Every report, a contrib adapter's included, must pass it.
- `induce` creates a fault the adapter must map: the in-memory references inject it; a filesystem or SQLite fixture creates the real condition (a small full volume, a read-only directory, a file held by another process). A fixture that cannot create a fault returns `CannotInduce`, and the case returns `NotApplicable(fault)` as its outcome. `OtherIsolation` makes the next delegated or `Set` transaction open at an isolation where a statement would not read the latest committed revocation, which the case expects to fail `Isolation`; `MemRelational` simulates it, and so does a fixture whose adapter can be told to. `WatchdogStopped` stops what enforces the adapter's bounds, its watchdog, after which a new delegated or `Set` open fails `Unwatched` while a single-organisation open with no delegation still works. `StalledStatement` holds the next statement in the store past its transaction's bound, which the case expects to end with `Stalled` and the transaction ended in the store. `Unsafe(property)` breaks, in the store, one rule of the adapter's rule data that holds that property, after which `check_compatible` fails `Unsafe` with that property and the rule's name, and, once the adapter is built, every open and the next statement of every open transaction fail it after the next check (Property 4). `RecheckStalled` stops the adapter's re-check, after which, once its last run is older than twice its interval, every open and every statement fail `Unchecked`. `ForeignReply` makes the next statement's reply one that is not a data statement's, as a server would answer a text the build check missed, which the case expects to fail `Reply` with the transaction ended; a fixture of a real store returns `CannotInduce` for it. `lift` ends a fault `induce` created, so a case can show the adapter recover; a fixture that cannot lift a fault it induced returns `CannotInduce` for it. `MemRelational` simulates each of these. A release-gating adapter's item names the faults its fixture must induce, and the `dist.toml` entry of every adapter lists the faults its fixture cannot induce, `not_applicable`. That list may name only the faults that `crates/grdr-ports-testkit/data/optional-faults.toml` lists as optional for the port, the faults of a mechanism a store may not have, and never a `Store` fault; the kit item writes that file and the distribution build reads it; the report states how many cases were not applicable; and the distribution build refuses an adapter whose report has a `NotApplicable` case for a fault its entry does not name (section 12).
- A fixture error carries a `StoreFault`, a stop point, a fault, a `StatementRefused` or a set-up `ClassReading`, and never text, as RFC 0008's `Failure` does, so a driver error that echoes a connection string never reaches a report or a CI log (SD-11).
- Retries (RFC 0008 revision 8, section 4, R9, R11 and R12). Until #1959 is decided, a storage adapter uses the executor only for its connection set-up. Its constructor is `connect`, in its crate's `src/setup.rs`, and the `RetryState` lives only inside that function's body, with its own `Health`. Before `connect` returns, built or failed, it copies the state's `ClassReading` and drops the state, and the adapter keeps that reading, never the state. `connect` builds its set-up policy with the `PeerAccess` of its back end (RFC 0009): the reference adapters `InProcess`, SQLite `OwnFile` for a path on a local disk, and PostgreSQL, the object store and the bus over any socket `Connection`, so their set-up tables are `peer = "remote"`. For `grdr-server`, only the composition root, `src/compose.rs` and `src/compose/**`, calls `connect`, never a settings revision (RFC 0008 constraint 1m); another program's start-up modules, `src/start.rs` and `src/settings_loader.rs`, call its storage adapters' `connect` (the lists of section 14); a fixture's `testkit` module calls it in test code. A same-machine adapter's set-up table has a `max_elapsed` within a `limits.toml` row, 5 s by default, which its item adds, and a local error of class `input` or `policy` ends the set-up at its first attempt with no sleep (RFC 0008 constraint 2a). Every call after construction, a request handler's or any other, returns its error to its caller unretried, whether the adapter's instance serves one organisation or many, so no `Refused(Refusal)` and no call's error ever reaches the executor. The codes still decide what a caller does, and #1959's decision reads them: every `Refusal` code is `retryable` with `failed_precondition`, which `faults_peer` does not count, and a per-tenant limit or throttle of a back end is `StoreFault::Throttled`, coded `policy` with `resource_exhausted` (section 11). The connect returns each error to the executor with its code, as `Fail` or `Retry` and never as `Done`.
- The construction cases. `setup_reading` returns the `ClassReading` a built adapter kept, and `FixtureError::Open` carries the one of a construction that failed, so every storage suite runs three cases on the set-up. `error_codes_spare_the_breaker`: construction connects that `induce` fails with an input error, and with `Throttled`, leave the set-up breaker unchanged while the class counter counts each attempt; the case then walks `codes::ALL` for the port's areas and asserts `faults_peer` for each code against section 11's table. `health_call_fails_with_its_calls`: with `induce` failing every connect attempt and the adapter's health call, the reading in `FixtureError::Open` shows the breaker open, and after `lift` the construction completes and the built adapter's reading shows it closed. `errors_return_unretried`: once the adapter is built, a call under an induced `Store(StoreFault::Unavailable)` returns that error from its first attempt, and the kit's clock records no sleep for it. A fixture that cannot induce the fault fails the first two for a release-gating adapter. The reference adapters build their set-up state over the kit's `clock()`, a `SeededEntropy` and RFC 0008's `ScriptedHealth`, which their fixture's `induce` turns unhealthy and `lift` healthy again, so the cases run on them too. Each adapter keeps a connection, handle or slot for its health call alone, makes it again after an unhealthy verdict, and its item tests both (RFC 0008 R13). The Events adapter builds no state for its catalogue writes and lake objects, which go through `Relational` and `Blobs`.
- Relational cases that rest on the store. The relational suite drives through the kit what rests on a store's own mechanisms: the statement sets `open` takes (`Undeclared` and every `StatementRefused` reason), `OtherIsolation`, `WatchdogStopped`, `StalledStatement` and `Unsafe(property)` (section 9). What the kit cannot drive for every adapter, the store tests that section 9's properties name, each relational adapter item's store tests cover, against its real store in CI (section 13). They are that adapter's tests, not admission evidence, and a contrib relational adapter's report shows the kit's cases only (section 12).
- A Differential case drives one operation sequence generated from the seed through the adapter and through the port's reference adapter (built by the suite over its own `ManualClock` and `MemLeases`) and compares every observable result. Opaque values such as offsets are compared by the pattern of equality and order they show, not by value.

- `put` writes an object; a `get` of that path afterwards returns exactly those bytes. The port promises nothing about a second `put` to the same path. Conditional put is used where a store has it and never required (design/20 section 3); callers name every immutable object uniquely.
- `get` returns the bytes last written; a path never written, or deleted, fails `NotFound`.
- `get_range` returns exactly the bytes `[start, end)`; an `end` beyond the object's length fails `Range` and returns no bytes.
- `list` returns at most `limit` keys under the prefix, in ascending byte order of the rendered key, strictly after `after`, with `next` set when more remain. The adapter builds each key with `ObjectKey::under`, so it never returns another organisation's key.
- `delete` removes the object: afterwards `get` and `get_range` fail `NotFound` and `list` omits the key. Deleting a path that does not exist succeeds, so a restarted job repeats no visible side effect. Noncurrent versions a versioned bucket keeps for backup expire by the bucket's lifecycle within the backup window (design/20 section 9) and are not reachable through the port. Erasure of content is by key destruction, never by `delete` alone.
- Every method runs the check of section 2 on its path or prefix and fails `Refused` before the adapter sees the call.
- Object bytes are opaque and never logged. Errors carry the rendered key only.
- Whole objects pass as `Vec<u8>`, which fits slice 0's flush outputs (32 MB); a streaming put is an amendment with L-4.
- Deployment-scoped objects (`state-log/`, `ephemeral/detect/`, the content repository) are not on this trait (question 1).

Callers in slice 0: `store` writes lake files and archive segments (#1547, `put`); the lake read path reads Parquet footers and pages (#1554, `get`, `get_range`); `store` removes objects an interrupted flush left unreferenced (#1547, `list`, `delete`).

Cleanup of unreferenced objects. Holders of different bus partitions write into the same `org=/class=/day=` prefix, so a lister sees objects another holder has written and not yet committed. `store` therefore removes an object only when no catalogue row references it and it is older than a grace from `limits.toml`, which must exceed the largest flush deadline plus the lease term. The age is measured by a clock the writer does not set, because a writer whose wall clock runs behind would otherwise name a new object old and see it deleted before its commit; #1547 chooses between an intent row written before the object and the store's own modification time, which would need a Blobs amendment.

Suite `storage::blobs::conformance`, reference adapter `MemBlobs`: one case per bullet above, `put` under a path built while the organisation was active and used after it moved to `key_unavailable` among them; `put` and `get` through paths built under a delegated context, after its delegation is revoked, and `get` and `list` through a member context's path and prefix after the kit's clock passes its expiry, each `Refused`; a cross-organisation case (objects under organisation A are never returned by a read or list under B); every `StoreFault` the fixture can induce maps to `Store` with that fault; listing order with keys that differ only in byte order. A property test in #297 compares `MemBlobs` with a `BTreeMap` model over generated sequences.


- Each lease name is in one `LeaseState`, the type every adapter and `MemLeases` store per name. A name never acquired is `Free { last: 0 }`. `release` and expiry move to `Free` with `last` set to the newest token issued, so the high-water mark survives every transition; an adapter never deletes a lease row. No boolean "held" flag exists.
- `acquire` returns `Held` with a new token, strictly greater than `last` or the held token, when the name is free, expired, or already held by the same holder. `Busy` is returned when another holder holds it unexpired. Re-acquiring by the same holder therefore supersedes that holder's earlier `Lease`: a task restarted inside one process, which shares the process's `Holder`, gets a fence its stalled predecessor does not have.
- `renew` returns `Renewed` with a later `expires_at` and the same token while the caller's token is the newest and unexpired, and `Lost` once a newer token was issued or the lease expired.
- `release` frees the name only if the caller's token is the newest; releasing a lost lease does nothing.
- `expires_at` comes from the store's own clock and `LeaseTerm::ttl`; no method takes the caller's wall time. The 5 s renewal and 15 s expiry are `limits.toml` values the caller passes.
- `check` fails `StaleFence` unless the fence's token equals the newest token issued for the name (Rule 5). `acquire` and `renew` wait while a lease-checked commit holds the row.
- No caller builds a `Fence`, a `FencingToken` or a `Lease`. The adapter returns a `Grant` or a `Renewal`, `Admitted` builds the `Lease` from it with the name and holder the call named, and a fence comes only from `Lease::fence`. An adapter receives fences and reads their name and token. `JobsError::StaleFence`, like every `StaleFence`, carries no token.
- `Holder` holds the process's `HolderId`, RFC 0009's `hld_` id, minted once per process start through grdr-model's id constructor (ARCH-020). Only `Setup::holder` and the kit's handle build a `Holder`, and it has no constructor from a `HolderId`, so only the composition root, and in a test process the kit, makes one. Nothing parses one: an adapter stores its id's text and compares it, and returns the stored text as a `HolderLabel`, which names the process for `Busy` and which no method accepts.
- A holder whose fence is superseded moves to `Lost` and re-enters `acquire`. That is normal after a sleep or a failover; the job runner (J-1) raises health only when it repeats past a `limits.toml` bound, so a laptop that slept shows no false alert.
- Leases belong to no organisation (a bus partition and a singleton serve every organisation on them), so the methods take no context and are deployment-scoped. The composition root hands a Leases port only to the runners that hold leases. The tenant-scoped Jobs methods (`enqueue`, `claim`, `step`, `complete`) are J-1's amendment.

Callers in slice 0: the partition consumer runner (`store` on each `events` partition) and the `migrate` lease of `Migrator::apply`.

Suite `storage::jobs::conformance`, reference adapter `MemLeases` over an injected `Clock`. `MemLeases` clones cheaply and shares its state, so the other references check fences against it. Cases: one per bullet above; many tasks racing to acquire one name, after which exactly one is `Held`; a holder that pauses past expiry while a second acquires, after which the first's `check` and `renew` fail and the second's succeed; two tasks with one `Holder`, the second acquiring while the first holds, after which the first's `check` fails and its lease-checked commit does not land; release then acquire, and expiry then acquire, each giving a token strictly greater than any before; module code that builds a `Fence`, a `Lease` or a `Holder`, or passes a `HolderLabel` to `acquire`, does not compile (compile-fail doctests in `grdr-ports`).

`Headers` is a closed struct with one typed field per header of design/20 section 4 step 4 other than `org`, `received_at` among them, and no free key (#299). The bus writes `org` and the delegation itself and returns them only as `StoredMessage::org` and `StoredMessage::delegation`.

- `append` writes every message to the one partition the current `BucketMap` gives the bucket, and returns that partition and the first and last offsets, contiguous and ascending in input order. A bucket at or above the map's length fails `Bucket`. Each stored message carries the context's organisation as its `org` header and the context's delegation, if it has one, beside it. Only the Bus adapter's `append` writes the log, and the log refuses a message whose organisation, delegation or epoch is not the appending context's, so no other statement writes a message for an organisation, and no message under a delegated context is stored without that delegation. The bus log holds Properties 1 to 3 and 9 of section 9 as a tenant table does, and its adapter item says how (#2002 for the log on PostgreSQL). When the stream's byte bound (a value the adapter is built with) would be exceeded, `append` fails `Full`, stores nothing, and names the stream and partition so `ingest` can answer with a spread `retry_after_ms`.
- Offsets within a partition are strictly increasing in the order appends become visible: a consumer never sees offset n+1 before n. A partition's offsets count every organisation's messages in it, so a caller of `append` learns how many messages entered the partition between two of its appends. That count is a residual of the Bus port; slice 0's caller is `ingest`.
- The fence of every claim and of every commit must be of the partition's own lease, `partition_lease(group, stream, partition)`, which renders `<group>.<stream>.<partition>` and fails `IdentError` when that would pass 255 bytes. `Admitted` refuses any other fence with `StaleFence` before the adapter sees it, so the fence of one partition's lease cannot claim or commit another partition. A runner acquires that name for each partition it consumes, and a `Claim` comes only from `Claim::new(partition, &lease)`.
- `subscribe` handles each claim as one compare-and-set on the partition's consumer row `(group, stream, partition)`: create the row with fence 0 if absent, then set `fence` and `holder` to the claim's where the stored fence is at or below the claim's, returning the committed position from the same statement. In PostgreSQL that is `UPDATE bus_consumer SET fence = :f, holder = :h WHERE ... AND fence <= :f RETURNING committed_offset, checkpoint`. Zero rows updated means a greater fence is stored, and `subscribe` fails `StaleFence`; claims stamped earlier in the same call stay stamped, which is harmless because each names its own acquisition. A read followed by a separate update is not this rule: at READ COMMITTED a lower fence would overwrite a higher one. `positions` returns the positions read, and the subscription starts each partition after its committed offset.
- `fetch` returns at most `max` stored messages in offset order per partition, each with the organisation from its `org` header or `None` if it has none, and the delegation stored with it. It takes a call token, so module code cannot call it: module code holds the subscription only as `Admitted<S>`, the token is zero-sized, neither `Clone` nor `Copy`, and branded `PortsCall<Self>`, and a token a wrapper receives is branded with the wrapper's type, which the inner `fetch` does not accept. The forwarding implementations are `Admitted`'s and `Dispatch`'s, inside `grdr-ports`; the generated dispatch uses `Dispatch` as its subscription type, nested for more than two adapters (section 2, "Forwarders").
- A partition consumer runner calls `fetch_batches` with the `ConsumerSubscription` that `Consumer::subscribe` opened over the store's admitted bus, for the group and stream its `Consumer` handle was built for. `fetch_batches` builds the token, calls `fetch`, and groups consecutive messages of one partition, one organisation and one delegation into `OrgBatch` values, built inside `grdr-ports`, so a batch never mixes organisations whatever the adapter returns. Each batch carries the context `fetch_batches` minted for it, only from rows that passed that policy, with work `Process`, the state the authority's table holds and the delegation checked (section 2), or the `MintError` that stopped it. The first message of a partition with no organisation comes back in `unattributed` with its partition and offset (`GRDR-BUS-0005`). Nothing at or after it on that partition is returned; the batches before it, and the other partitions' batches, are. The consumer stops on that partition and reports the code, because committing past a message nobody attributed would lose it (design/21 section 2).
- `commit` records the offset and the optional checkpoint in one conditional update of the consumer row: `SET committed_offset = :o, checkpoint = :c WHERE ... AND fence = :f AND (committed_offset IS NULL OR committed_offset <= :o) AND :o <= <the partition's last offset>`. A new group's row has no committed offset, so its first commit lands at any offset up to the last. When no row is updated the adapter reads the row and the partition's last offset once to say which condition failed: another fence is `StaleFence`, a higher committed offset is `Regress`, an offset past the last appended one is `BeyondLog`; none changes the row. `detect` puts its snapshot's object name in `checkpoint`, so the offset and the snapshot key move together (design/20 section 7); `store` passes `None`.
- Why the row-stamped form is safe. Between a new holder's `acquire` and its `subscribe`, the old holder's commits still land. Each one records progress the old holder made under its own fenced writes, since its lake flush is lease-checked (section 10). The new holder reads the position in the statement that stamps it, so it never starts below a commit that landed, and the old holder's later commits fail. Two `subscribe` calls with different fences end with the greater one stored, in either order. The rule other consumer groups follow is the same: commit only progress a lease-checked write or an idempotent effect has confirmed. The bus checks no lease, so `bus.database` may stay a separate instance.
- A serialisation failure, where an adapter runs these statements at a stricter isolation level, is `Store(StoreFault::Conflict)` and retryable.
- `lag` gives, per partition, the `received_at` of the oldest message after the committed offset, or `None` when the group is caught up.
- `set_bucket_map` accepts only a version greater than the current one, else `MapVersion`. Earlier versions are kept as design/20 section 6 keeps them. Removing a partition from a stream is not on the surface.

- `read`, `write` and `write_fenced` are the only ways to open a transaction. The adapter binds the context when it opens the transaction (Property 2). `ReadTx` has no write method, its runner runs only statements declared `Read`, and the adapter ends every read and `Set` transaction without committing it, so nothing it did, its binding included, outlives it (Property 3).
- A repository runs statements only through the runner `statements` returns, so the transaction is the witness. The runner's interface is `StatementRunner` in `grdr_ports::adapter::statements`: the supertrait of `ReadTxAdapter` and `WriteTxAdapter` and the bound on `ReadTx::Statements` and `WriteTx::Statements`, so a repository in any crate is written once, generic over `R: Relational`, and never names an adapter type. `run` takes a declared `&'static Statement` and its parameters as `Value`s and returns `Rows`, or `Undeclared` (`GRDR-REL-0010`) for a statement the runner did not prepare, `Reply` (`GRDR-REL-0015`) for a reply that is not the declared statement's own result, `Refused`, `Timeout`, `Stalled`, `Unsafe`, `Unchecked`, `Constraint` or `Store`. After every statement the runner checks the reply. On any other reply it ends the transaction unfinished and never reuses its session, so no statement follows it (Property 8). `ValueType`'s and `Value`'s variants behave the same at the port, each passed to the store as its declared type, so one case covers them: a value of each `ValueType`, `Null` included, written and read through the kit's probe set comes back equal. Where module repository traits live is question 2.
- Who writes SQL text. A repository declares the name, access and parameter types of every statement it runs in one `StatementSet`, and holds no SQL. The text of each is the adapter crate's, one text per dialect (design/20's relational row), keyed by repository and statement name in the adapter's source as its migrations' SQL is keyed by `MigrationId`, and written in the item that adds the statement as a change to each relational adapter crate, under that crate's review. So no query is built outside an adapter crate (ARCH-015, kept and restated in section 14), and one dialect's text never reaches another dialect's adapter. The composition root's start-up module passes every repository's set to each relational adapter's `connect`, and the kit passes sets to `Fixture::open` (section 5). `connect(settings, sets, clock, entropy) -> Result<Adapter, ConnectError>` takes no SQL text: the crate's statement text is a table of `(repository, name, text)` constants in `src/statements/text/`, which holds data only, keyed by the repository's `NAME`. Since `connect` refuses two sets with one `NAME` (below), each `NAME` belongs to one marker type, so the texts a set receives are its marker's own. A fixture adds the kit's table through a crate-private entry that only the crate's `testkit` module calls. Each relational adapter keeps those texts outside the trust-core paths, because the store properties hold whatever a text says, and names its runner and its statement check for them (section 14).
- The runner runs only what it prepared. When it is built, the adapter looks up each declared statement's text, fails to build with `StatementRefused` (`GRDR-REL-0011`) on the first that has no text (`NoText`), whose name another statement of its repository already has or whose repository's `NAME` another set given to `connect` already has (`Duplicate`, naming the repository), or that its statement check refuses (Property 7), and prepares each once. A statement's identity is its repository, its name, unique within that repository, and the hash of its text, never the address of the declared value. A repository is a marker type private to its module, `Statement<R>` and its set carry it, and the runner keys what it prepared by the marker's `TypeId` and the name, so no other module can name the marker, build a statement of that repository or run one, and two repositories may use one statement name. `run` accepts a statement whose repository and name it prepared and whose declared access and parameter types equal the prepared one's: a declaration used through a `const` runs; a statement of an unregistered marker type that copies a registered repository's `NAME` fails `Undeclared`, registering its set beside that repository's fails `connect` with `Duplicate`, and a statement that differs in its declaration fails `Undeclared`. `StatementSet::statements` returns each statement's `StatementDecl`, its declaration without the marker, for the build check and the kit; `run` takes only a `&'static Statement<R>`, so a declaration read from a set cannot be run. The runner holds its session privately: ARCH-030 `transaction-type` refuses, on the adapter crate's source, a public method of the runner that takes SQL text or returns or borrows a session or connection type, which `architecture.toml` lists per driver.
- `commit` makes the writes visible. A transaction opened with `write_fenced` holds its fence from the start and its `commit` is lease-checked by Rule 5, so code that holds the transaction cannot skip the check. On `StaleFence` the transaction rolls back and is consumed, so no stale write can be committed afterwards. Request handlers use `write`. The J-1 step API hands each step a handle whose only way to open a write is `write_fenced` with the step's fence, so a job step cannot skip it either (design/20 section 8, "every write checks").
- A delegated transaction, one opened under a context that carries a delegation, and a `Set` read transaction run where each statement reads the latest committed revocation: an open at another isolation fails `Isolation` (`GRDR-REL-0009`), and so does its commit. A delegated open fails `Refused(Refusal::DelegationNotActive)` when the store holds a revocation newer than the context's epoch, or does not hold the delegation row in force at exactly that epoch. Every statement of a delegated transaction counts both the revocation and that row, so a kept transaction reads and writes nothing of the organisation once either refuses it. A delegated or fenced write's commit fails with the same refusal unless the delegation is in force at the context's epoch as the commit runs, or `StaleFence` unless the fence is current. No reader holds a lock a revocation waits on. Each `Set` statement applies the snapshot binding (design/21 section 2, as section 14 amends it) to the latest revocation and delegation row (Property 9).
- A transaction opened by `read`, `write` or `write_fenced` ends within the `limits.toml` row `relational.transaction-life`, and a `Set` read transaction within `relational.set-transaction-life` (Surfaces changed). The composition root builds `TenancyLimits` from them for `tenant::start` and builds the adapter with the same values. The adapter enforces them where no statement inside the transaction can lift them (Property 10), and its item names the further bounds it is built with. An adapter that cannot currently enforce its bounds fails a delegated or `Set` open with `Unwatched` (`GRDR-REL-0013`) and raises Degraded with that code until it can. `AdmittedTx` reads the opening time from the authority's clock's `monotonic` and fails `statements` and `commit` past the bound with `Timeout(bound)` (`GRDR-REL-0008`), which names the bound: the caller used up the transaction's life between statements. A statement the store was still running when the adapter ended its transaction fails `Stalled(bound)` (`GRDR-REL-0014`). A migration's transaction is deployment-scoped, carries no token and runs under the `migrate` fence, so these rows do not bound it.
- `read`, `write`, `write_fenced`, `snapshot_members`, every `statements` and `commit` run the check of section 2, against the context the transaction was opened under, and fail `Refused` before the adapter acts. A transaction, held as `AdmittedTx`, is `Open` until its first refusal, `Timeout` or `Stalled`, which ends it: `AdmittedTx` rolls it back, and every later use fails with that error. A revocation or a change of state therefore stops a transaction at its next use. A borrow already taken stops at its next statement after a revocation, and at the transaction's bound after a change of state.
- A dropped `WriteTx` makes none of its writes visible. The adapter may finish the rollback when the connection is next used, because `Drop` cannot await.
- `Constraint` is a constraint violation and carries no row data. A serialisation failure is `Store(StoreFault::Conflict)` and retryable.
- `snapshot_members` returns the members of the set's delegation snapshot, each with the delegation and epoch the snapshot recorded, read under the set's binding, in ascending byte order of `OrgId`, strictly after `after`, at most `limit`. Module code that needs a `MemberCtx` calls `tenant::members`, which checks each delegation and wraps each id (section 2). It takes no call token: a direct call returns only the members of the snapshot the caller's `SetCtx` already names, and ids carry no authority.
- A store that binds one organisation only (SQLite in `embedded`, D-34) fails `SingleOrganisation` for `snapshot_members`, for `read` with a `Set` context, for a `SingleCtx` of a second organisation, and for a context that carries a delegation, rather than serving any of them unisolated; it holds the multi-organisation, store-identity and delegation properties by that refusal, and Properties 3, 7, 8, 10 and 12 for its one organisation.
- `MigrationPlan::new` refuses duplicate ids, ids out of ascending order, a `Contract` whose `of` is not an `Expand` in the plan, and a `Contract` whose release is below its `Expand`'s release plus 2 (release N adds, N+1 reads the new form, N+2 drops the old). The SQL of each migration lives in the adapter crate, keyed by `MigrationId` (ARCH-015). `ExpandKind`'s variants behave the same at the port: the plan rules do not depend on the kind, so one case covers them.
- `MigrationPlan::check_compatible` is pure. It accepts recorded ids that are all in the plan, or whose ids outside the plan all belong to `binary_release + 1` and are all `Expand` steps (the previous binary runs on the new schema). Any other id outside the plan fails `SchemaTooNew { id }`.
- `Migrator::apply` applies, in order, each migration not yet recorded. Migrations belong to no organisation, so the adapter runs each in its own deployment-scoped transaction inside its crate, never a `WriteTx`. That transaction records the migration's id and commits by the lease-checked form of Rule 5 under the `migrate` fence. Before it commits, the adapter runs its schema check inside it and rolls the migration back with `Unsafe` if a store property no longer holds (Property 4).
- `Migrator::check_compatible` reads the recorded migrations once and calls the pure function. The server runs it once at start, before it serves anything; when it passes it costs one read and blocks nothing after. When it fails the server does not start, so a binary rolled back onto a newer schema is refused with `GRDR-REL-0007`, never run silently.
- `Migrator` is deployment-scoped. Tables without an organisation (runtime settings and the operator realm, D-70) need a deployment-scoped transaction for module code, which this trait does not offer (question 3).

Store properties. Every relational adapter holds these twelve properties, whatever its back end, and Properties 13 to 15 of section 2 hold for the tenancy history. Each names the case that tests it on `MemRelational` and on every adapter's fixture, or, where the kit cannot drive it, the store test every relational adapter item carries against its real store in CI. How an adapter holds them is its item's design: #2002 for PostgreSQL, #301 for SQLite. - **Property 1, isolation.** A statement under a binding reads and writes only its binding's rows: one organisation's, or for a `Set` the rows of the snapshot's members whose delegation passes the `Set` rule (design/21 section 2, as section 14 amends it). - **Property 2, binding at open** (ruling R14-1). Each transaction is bound to its context when it opens. No declared statement, and nothing a statement or its store identity can reach, sets, changes or clears a binding, in that transaction or in a later one on the same connection. An unbound transaction reads and writes no tenant row. Kit: `MemRelational`'s binding, fixed at open, and the `NotData` cases of `REFUSALS`. Store test: every path a statement identity has to the binding, each refused.
- **Property 3, writes need a write binding.** Nothing written in a read or `Set` transaction is kept, whatever the statement's declared access or text. Every write is checked against the binding as it is made, and read and `Set` transactions end without a commit. Kit: the write-under-`Read`, dropped-transaction and `ReadWrites` cases below.
- **Property 4, store-held rules** (ruling R13-1). - **Property 6, check independence.** The schema check's result depends on nothing that an identity it checks, or any identity other than the store's administrator, can change: no code, relation, setting or connection state. Store test.

Delegated and `Set` transactions run where each statement reads the latest committed revocation, and anything else fails `Isolation`. `SessionId`, `DeviceId`, `Epoch` and `Seq` are grdr-model types (RFC 0009). The adapter takes the lake column manifest (#510's type, in `grdr-schema`, settled by #1852) and a `Clock` when it is built.

Rows cross the port as Arrow IPC. `ArrowIpc` holds one Arrow IPC stream: Arrow columnar format 1.x, a schema message and then record batches, with no dictionary deltas and no body compression. Its schema is the column manifest of the batch's table, or of the plan's projection. The contract is the Arrow format, a published standard (P10), not an arrow-rs release, and `grdr-ports` links no Arrow (Rule 1). The cost is one encode and one decode per batch.

Write path:
- A `LakeBatch` is one bus message of the `events` stream, built only by `OrgBatch::lake_batch` from a message of that batch. It carries the batch's context, the message's offset as `source`, its headers, and its bytes unchanged as the archive, with the message's lane and the UTC date of its `received_at`; the bytes keep the device-side pseudonyms the batch was signed with (D-39). `store` supplies only the rows of each table, decoded from those bytes, flattened by the column manifest, with server pseudonyms in place of device-side ones (D-51), and with no `organisation_id` column (Rule 4). The adapter adds `organisation_id` from the batch's context. It refuses with `BatchSchema` a batch whose columns differ from the manifest, `organisation_id` included, and with `BatchHeader` a row whose device, epoch, lane or sequence number lies outside the message's headers, so rows decoded from one message cannot be written under another. Bytes that are not a valid Arrow IPC stream of that profile fail `BatchUnreadable`.
- `append` takes the fence of the `store` lease on the bus partition the batch came from. It fails `StaleFence` if that fence is already superseded when called (a point-in-time check), and otherwise buffers the rows and the archive batch. A row whose key `(device, epoch, lane, seq)` is already appended or committed adds nothing; `Buffered` counts added and duplicate rows. Before `append` returns, the adapter has durably recorded the partition (its fence's lease name) in its partition record for the organisation, if it was not there yet. Once `append` returns, an `execute` that starts afterwards returns the added rows.
- `flush` commits the buffers that are due, one organisation at a time. `Thresholds` takes each organisation with a table buffer past the size or age the adapter was built with; `All` takes every organisation, and runs at the partition's bus retention bound and on lease release. For each organisation it writes the archive segments of the due batches first (`org=<id>/class=archive/lane=<lane>/day=<date>/<uuidv7>.seg`), then one Parquet object per table, then one catalogue transaction, lease-checked by Rule 5, that records the lake files, their statistics and data key ids, and the segments in `lake_archive_segment`. Only after that commit is visible does it drop the committed rows from the buffer.
- A flush that cannot seal an organisation's rows, because its key is unavailable or destroyed, drops that organisation's buffer, records its device ranges as skipped (design/20 section 4 step 7) and lets `committed_through` pass them, so one organisation never stops its partition.
- `flush` takes no witness and does not check again: it commits rows `append` admitted. A batch appended before its organisation moved to a state that refuses Process, such as `migrated`, is committed after the move by the next due flush; a `shredded` organisation's buffer is dropped as above, its key destroyed. No tenant is crossed: each row was appended under its own batch's context, from which the adapter writes `organisation_id` and the `org=` segment, and each commit covers one organisation.
- A crash anywhere before that commit leaves no catalogue row; the objects written before it are unreferenced and uniquely named, and `store` removes them after the grace of section 6. A crash after it leaves rows, files and segments all visible. No batch is ever committed without its archive segment.
- `flush` stops starting new organisation commits once `deadline` passes on the adapter's clock, and returns what committed. What it did not commit stays buffered or, on release, is dropped; the bus delivers it again because the bus offset never passes `committed_through`. Closing a laptop lid therefore never hangs the daemon on a flush.
- `committed_through` is the greatest offset `o` such that every batch appended under this fence with `source <= o` has its rows and segment committed or recorded as skipped, or `None`. `store` commits the bus offset to that value (design/20 section 5.2). It is not the sensor-facing `durable_through` of design/20 section 9, which is later and also needs backup health.
- A flush under a superseded fence fails `StaleFence` and drops that fence's buffers; the bus delivers the rows again to the new holder. A crash or forced power-off loses only buffered rows, which the bus still holds.
- `LakeTable` has no `Content` variant until content sealing (L-3) exists, so no path can write content unsealed (D-51; #1546 R5).
- Pseudonyms. `ArrowIpc` columns carry the pseudonym class, and the port cannot tell a device-side value from a server one. The guarantee that the lake holds server pseudonyms only is #1690's test (no stored `decision` or `activity` value equals its device-side source). The Events conformance suite does not claim it.

Read path:
- `plan` validates the query against the manifest and prepares it; it reads no catalogue snapshot and no buffer. An unregistered view fails `View`, an unregistered column `Column`; a predicate fails `Predicate` when a literal's kind differs from its column's manifest type, when `Eq` to `Ge` do not have exactly one value, or when `In` has none or more than `in_values`. `TimeBounds::new` fails `TimeBounds` unless `from < to`; bounds are half-open `[from, to)` on `observed_time`.
- Module code plans and reads through `tenant::mint` (section 2): `plan_query` calls `plan` and returns the plan inside `Planned`, paired with the context's organisation, work kind, delegation and expiry, which `execute` and each `next` check again (section 2); `run_query` calls `execute` with it and returns the stream inside `OrgRows`, whose `next` builds the call token `ResultStream::next` takes. `execute` serves the organisation of `Planned::org` and no other: the adapter's plan holds no organisation it reads, so a plan prepared for another organisation, paired with this one, returns this one's rows.
- `Scan` orders on `(observed_time, device_id, epoch, lane, seq)` and `Timeline` on `(epoch, monotonic_ns, lane, seq)` within its root session, ascending or descending per `order`, compared by Rule 11. `after` returns only rows strictly after `after.position` in that order.
- `execute` returns the plan's organisation's rows from committed lake files and from rows appended but not yet flushed, de-duplicated on `(device, epoch, lane, seq)`, merged in the query's order. The union is inside the port, so no caller can forget it. Buffered rows come from the adapter's own buffers and, where the buffer lives in another process, from the tail source the adapter was built with (`grdr.internal.v1alpha1.StoreTail` in `distributed`, design/20 section 5.2).
- `execute` asks for buffered rows on every partition in the adapter's partition record for the organisation: every partition under whose fence a row of the organisation was appended. `append` writes the record before it returns, so a row appended before `execute` starts is on a partition the record names. `execute` reads the record where it is written: in one process from the adapter's own state, otherwise from the catalogue's primary (`lake_org_partition`, design/20 section 5.4), never from a cache, because a cached record from before a partition's first row for the organisation would not ask that partition and no answer could say so. Removing a partition from a stream is not on the surface (section 8), so no partition leaves a record in slice 0. The amendment that adds removal also removes a drained partition from each record, in the flush commit that empties it, and keeps that commit's version as a floor of every later read.
- `execute` reads the buffered rows first, then fixes the catalogue snapshot it selects files from. A flush drops rows from its buffer only after its catalogue commit is visible.
- Each answer, from the adapter's own buffers or from the tail source, carries a floor for that organisation. A floor belongs to one fence, never to a `Holder`, so a holder that re-acquires (section 7) starts a new one. It is the greater of two catalogue versions (`lake_org_head` snapshots, design/20 section 5.4):
  - the newest one whose commit dropped rows from that fence's buffer;
  - the one the fence's holder read on the catalogue's primary, where commits are made, after its `acquire` returned. The holder reads it the first time it answers for the organisation under that fence.

  Rule 5 makes every lease-checked commit under an earlier fence end before `acquire` returns, so the second version covers every row an earlier holder, or an earlier tenure of the same holder, committed.
- A holder answers in this order: it reads its buffer, checks its fence with `Leases::check`, then reads its floor. A fence that is no longer the newest answers as a failed tail, so an answer from a holder that has lost its lease never counts. The floor is read after the buffer, or in the same step, because a drop between a floor read and a later buffer read would leave the row in neither.
- The snapshot `execute` fixes is at or after the greatest floor among the answers. A cached file list (design/20 section 5.8) at or after that floor may serve as the snapshot. A source older than the floor, such as a cache whose invalidation has not arrived or a catalogue replica that lags, is not used, and `execute` reads the file list from the catalogue's primary. The floor is internal to the adapter and its tail source; no port type carries it.
- A partition with no holder, whose holder does not answer, or whose holder's fence was superseded before it answered, is a failed tail, so the read ends `WithoutTail` (below).
- A row appended before `execute` starts is therefore in the buffer read or in the files selected, never missing from both. That holds whenever `plan` ran, however late a cache learns of a commit, whichever holder committed the row, and whichever partition the organisation was on. The one exception is a row whose holder lost its lease before committing it. That holder drops its buffers, and the row is on the bus only until the next holder appends it again. The window opens when the old fence is superseded and closes when the new holder has re-appended everything up to the old holder's last appended offset; a read inside it can end `Full` without that row. `Bus::lag` shows the window, and a read run after it returns the row.
- Coverage. An ending's `coverage` is `Full` when the buffered rows of every partition were read. It is `WithoutTail` when the tail source failed or passed its own budget, or when a partition had no holder or no holder under a current fence, and in that case the stream still returns the lake rows. The ending holds its coverage once, in `Ending::coverage`. `Ending::resume` returns `Resume { position: last, coverage }` for a `Limited` ending that returned a row and `None` otherwise, so the position and the coverage a caller resumes with come from one value. A read resumed from a `Resume` whose coverage is `WithoutTail` also ends `WithoutTail`, because buffered rows before the resume position were never returned. A paging that missed the tail on any page therefore ends `WithoutTail` on its last page and never reports `Full` for rows it skipped. A caller that keeps a `Resume` between requests keeps both its fields; the console's page token (#1555) carries the whole `Resume`. The caller shows "could not look" for unflushed events (P9), and a run from the start fills them in once the tail is back.
- Limits. Reaching `rows`, `bytes` or `wall_time` ends the stream `Limited { reason, last }`, where `last` is the position of the last row returned, or `None` if no row was returned. The caller continues with `after: ending.resume()`, and the projection does not need the key columns. When `last` is `None` the read returned nothing and skipped nothing, so the caller retries with the `Resume` it already held. A limit and a missed tail are reported together: the reason in `completion`, the tail in `coverage`.
- A read with `after: Some(r)` returns every row strictly after `r.position` that is present when it executes. A row that arrives later with a position before it is not returned; re-run from the start to see it.
- After `End`, `next` returns the same `End` again and does no work.
- `Timeline` and `Scan` are the only query nodes until the amendments of section 12 are accepted. `retain`, `erase`, `hold` and `manifest` are not declared: a `NotSupported` default would let an adapter pass the kit without erasure (D-57).

Callers in slice 0: `store` builds lake batches, appends and flushes (#1546, #1547); `query` plans and reads `Scan` and `Timeline` through `plan_query` and `run_query` (#1554) for the CLI and console reads (#1555), including resume.

### 12. Stability, adapter selection and later change
Stability:
- Both crates enter `surfaces.toml` as `experimental` (ADR-0020; design/03 section 7: every surface starts there), through the protected-change item #1688 R3 files after acceptance, unless RFC 0008's entered them first.
- `experimental` allows a break in any release, and every change still goes by RFC: a signature, a semantic, a variant, a suite case, a lifecycle cell, the key layout, the identifier rule or the additional-data encoding is an amendment. An amendment is a new RFC that names RFC 0002 and goes through the same route; RFC 0002's text does not change after its decision, because an accepted RFC never returns to `Review` and a later change is a new RFC (RFC 0001, "RFC states"; design/30 section 3). Its pull requests name that RFC for `rfc-required`. One amendment may carry every change that is ready at the same time. `cargo public-api` and `cargo semver-checks` run against the class once the entry exists.
- What an adapter author can rely on: two versions describe the surface, the crates' semver and the kit version, and each server release names both. Every amendment is listed in the release notes, as `breaking` when it breaks. There is no compatibility window while the class is `experimental`. An adapter pins a kit version and moves when it moves to a new server release.
- The storage ports become `beta` when the server's packages freeze (design/03 section 7), by an RFC that changes `surfaces.toml` and sets the notice the beta class gives (ADR-0020). Its prerequisites are the deployment-scoped amendment of question 1, the Keys port RFC (design/21 K2) and the answer to question 2. The first embedding guide for storage has the same prerequisites.

Adapter selection and admission (P6, P14, design/03 E2):
- Adapters enter a build through `dist.toml`. The distribution build (#1593) generates, for each storage port, a dispatch type over the adapter types the distribution lists, which implements the port's adapter traits by delegation, and `server.profile` or the storage configuration keys pick the variant at start. The composition root admits that dispatch with `Setup::admit` (Rule 12). The Bus dispatch's subscription type and the Events dispatch's plan and results types are `Dispatch` over the listed adapters' types, because the call token cannot be passed on and a `Planned` cannot be built outside `tenant` (section 2, "Forwarders"). The three named profiles are the default `dist.toml`. No adapter is named in `grdr-server` source outside the generated module, so adding one is data plus a build, never a code change in the server.
- An embedder or contrib author lists its own adapter crate in its own `dist.toml`, with its adapter type, the function that builds its fixture, the fixture environment its conformance test needs (a store the builder supplies, for example a container image or a connection setting), and `not_applicable`, the faults its fixture cannot induce, which may name only the faults the kit's `data/optional-faults.toml` lists for the port and never a `Store` fault; the report states how many cases were not applicable. The distribution build generates each suite's test against the release's own `grdr-ports-testkit` under the bound `F: Fixture<Adapter = <the listed type>>`, so the suite drives the listed type and no other. It runs those tests in a cargo invocation separate from the program build (Rule 1), and admits the adapter only on a passing report it produced itself, in which every `NotApplicable` case names a fault the entry's `not_applicable` lists. A report the author wrote elsewhere is not evidence. It builds each program in its own cargo invocation (`cargo build -p <program>`), never with `--workspace` or at the root (Rule 1). Nothing is patched, nothing is forked, and nothing is sent to Loonaro.
- What admission shows, and what it does not. The `testkit` scan (section 5) holds the admitted build to the shipped code plus the fixture module and hook statements that call the release kit's `reach`, and every report includes `unarmed_reach_is_inert`. So the listed type behaves under the suite as the shipped type does, whenever no hook is armed. The report does not show that the author's fixture is honest: the fixture module is part of the adapter crate, can reach its private state, and could repair the store behind the adapter during the run. A report on an adapter from outside the project is therefore evidence of that adapter under its author's fixture. This is one reason a contrib adapter is Tier 2 and never part of a named profile (design/03 section 6).
- The same build runs the register check of Rule 12 over the resolved closure after macro expansion and name resolution, and ARCH-029 to ARCH-032 over it: the handle rule (ARCH-029) and the transaction-type rule (ARCH-030) of section 2, which read source as written, the `testkit` scan of section 5 (ARCH-031), which compares expanded code, and the `forbid(unsafe_code)` check (ARCH-032). Its compile of each closure crate that depends on `grdr-ports` with `unsafe_code` forbidden is the first check of Rule 12.

Amendments already expected, each with its item:

- Bus: removing a partition from a stream, with the removal of a drained partition from each Events partition record (section 10).
- Deployment-scoped transactions (question 3) and the Keys port (design/21 K2).

### 14. Proposed changes to design documents and `architecture.toml`
Each lands after acceptance as a protected change (section 1): its own issue whose write set names its file, landed after `eval-security` and an evaluator on the other model pass (D-63, ADR-0035). The design/21 change also takes `eval-adversarial`, because it restates the rule the trust-core `tenant` module implements (`security/trust-core.paths`).

How D-35, design/21 principle 2 and design/21 R2 are read. "No code path reads without a tenant context" is read as "no tenant data reaches module code without a tenant witness". Two deployment-scoped methods handle tenant data inside an adapter and `grdr-ports`: `Subscription::fetch` and `Events::flush`. `fetch` takes a branded call token that module code can neither build nor relay; the port traits are sealed, so module code cannot supply a subscription of its own; and `fetch_batches`, the one way to its messages, takes a `ConsumerSubscription`, which only a partition consumer runner's `Consumer` handle opens over the store's bus. Module code therefore receives stored messages only inside an `OrgBatch` that a listed runner fetched. `flush` hands no tenant data out. Events rows reach module code only through an `OrgRows` built from a `Planned`, which only a context can produce. This is a reading of the spine, not a change to its text. If the council or an evaluator reads D-35 more strictly, the spine changes by its own RFC and this one waits for it.

- **design/20 section 3.** `Set(Vec<OrgId>, ReadOnly)` becomes `Set(DelegationSnapshotId, ReadOnly)`, as design/21 section 2 has it. "Every method takes 21's `TenantCtx`" becomes Rule 3. "It can be built only by the authentication middleware of `api` and `ingest` and by the job runner" becomes the minting boundary of section 2: the mint authority stays in `tenant`, and the runners hold the handles the composition root builds in `tenant::start`. Port traits are sealed and adapters implement adapter traits (Rule 12). The Events row lists `append(fence, LakeBatch)`, `flush(fence, due, deadline)`, `plan(OrgRead, ...)` and `execute(Planned)`, with reads through `plan_query` and `run_query`, and names the methods that come later.
- **design/20 section 4 step 7** (refines). A consumer skips a batch whose answer for Process is `Deferred`, as step 7 skips an organisation whose key cannot be unwrapped, and `ingest` rewinds those lanes once the answer is `Allowed` again; a `Refused` batch is skipped and counted. A flush that cannot seal an organisation's rows drops them as skipped, so the partition keeps advancing.
- **design/20 section 5.2** (refines). The archive segment travels in `LakeBatch`, which `OrgBatch::lake_batch` builds from one bus message, and is committed in the same lease-checked catalogue transaction. The commit unit is the organisation, all its due tables and segments together, which refines "a flush is per organisation and table". "Tail reads": the Events adapter unions buffered rows inside `execute`, through `StoreTail` in `distributed`; `query` no longer unions, and a missed tail is reported as `Coverage::WithoutTail`. A flush drops rows from the memtable only after its catalogue commit is visible. A read asks every partition in the adapter's partition record for the organisation, which `append` writes before it returns and the read takes from where it is written. Every memtable answer, `StoreTail`'s included, carries a floor per organisation, kept per fence: the greater of the newest `lake_org_head` snapshot whose commit dropped rows from that fence's memtable and the snapshot its holder read on the catalogue's primary after acquiring the partition under that fence. An owner answers in the order memtable read, fence check, floor read, and only while its fence is current. The item that defines `StoreTail` adds the floor. A partition with no owner, an owner that does not answer, or an owner whose fence was superseded, is a failed tail read, shown as "could not look". The bus watermark the flush returns is named `committed_through`, apart from the sensor-facing `durable_through` of section 9. Unreferenced objects are removed after a grace measured by a clock the writer does not set.
- **design/20 section 5.4** (adds). A sidecar table `lake_org_partition (organisation_id, partition)`: the Events adapter's partition record, one row per partition under whose fence a row of the organisation was appended.
- **design/20 section 5.8** (refines). The file-list cache serves a read only when it is at or after the greatest floor the read's memtable answers carry (section 5.2), so it covers commits by the current holders, by every earlier one and by the partitions an organisation has left. Otherwise the read takes its file list from the catalogue's primary, never from a replica that lags. Invalidation by catalogue commit notification stays, but correctness no longer rests on its timing, on the partition keeping its holder, or on the organisation keeping its partitions.
- **design/20 section 7** (refines). `bus_consumer`'s `holder, fence` columns are stamped by `subscribe` in one compare-and-set that never lowers the fence, and checked by `commit` in one conditional update that also bounds the offset by the partition's last one: the row-stamped form of Rule 5. That is what lets `bus.database` stay a separate instance. A consumer's lease for a partition is `<group>.<stream>.<partition>`. `bus_message` stores the delegation of the context that appended it, beside `organisation_id`. `commit` carries the detect snapshot key in the same row update, as the section already says.
- **design/20 section 8** (refines). "A claim takes a lease with a fencing token that every write checks": a job step's writes go through `write_fenced`, and every `acquire` issues a new token, also for the same holder. Each job kind declares its work kind. A provider's job records the delegation and epoch it was enqueued under; each step's context is minted only while that delegation is in force at that epoch (`GRDR-TENANT-0005`), and each use of its transactions checks it again.
- **design/21 section 2** (contradicted today). Principle 2: "a `TenantCtx` value required by every repository and store call" becomes "a tenant witness (RFC 0002 Rule 3) required by every repository and store call that touches tenant data; the deployment-scoped methods `architecture.toml` lists take none, and tenant data they handle reaches module code only inside a witness". R2: "No server read or write executes without a tenant context; a missing context fails closed" becomes "No server read or write of tenant data executes without a tenant witness; a missing witness fails closed. A deployment-scoped method that returns tenant data takes a call token, so only `grdr-ports` calls it and its data reaches module code only inside a witness." Service framework row: "minted only by the auth middleware and the job runner" becomes "minted only by `grdr-ports`, through the handles the composition root builds once in `tenant::start` for the authentication middleware, the partition consumer runners, the job runner and the workbench read path"; a single-organisation context carries the organisation's lifecycle state, the work kind it was minted for and the token's delegation; every store operation checks the current state's answer for that work, the delegation and the expiry; "Every method of the relational, lake, bus, blob and cache ports takes it" becomes Rule 3; port traits are sealed (Rule 12); a `Set` has no write methods, and its lake and blob reads go through `MemberCtx`, which cannot reach `content` or archive objects. Bindings: every store holds RFC 0002's store properties: a statement reads and writes only its binding's rows (Property 1); a transaction is bound at open by a path no declared statement can reach (Property 2); a write needs a write binding (Property 3); a store that serves more than one organisation holds these rules itself, checked at start and while it runs (Property 4); and the store checks delegation (Property 9). A stored bus message carries the delegation and epoch of the context that appended it (RFC 0002 section 8). Set policy: the binding carries the snapshot id and the set's provider, and a snapshot row counts only while its delegation is that provider's, `active` or `expiring` at the epoch the snapshot recorded, with no revocation marker newer than that epoch, so a revoked, expired or rebound member leaves every `Set` read at its next statement. How a store realises them is its adapter item's design (#2002 for PostgreSQL). Lake and blobs row: "N per-organisation plans", each under a `MemberCtx` from `tenant::members`. Bus row: the consumer read of `bus_message` across organisations runs under a deployment binding that only the bus consumer path sets, and its rows reach module code only inside an `OrgBatch`; the binding's form is question 3, and this row is a placeholder until that RFC settles it.
- **design/21 section 5** (refines). Revocation, and any change to a delegation's bindings, increments its epoch. Revocation, expiry and rebinding are one commit, which appends a revocation marker for the delegation and its new epoch, updates the delegation row and appends the change to the tenancy history; every lifecycle move appends its change in its own commit, and no change waits on another organisation's (RFC 0002 Property 13). After the commit a notification goes to the replicas, a hint whose payload no replica uses. Every reader counts the marker: a replica holds the notification as a floor at the new epoch, reads the marker with the row and never lowers an epoch, the token exchange and the snapshot writer issue nothing for a delegation with a newer marker, and the store's opens, delegated statements, commit steps and `Set` statements read it. On each notification and each confirmation a replica confirms its copy only by a read that returns every change committed before the read began, applies changes to a subject in their commit order, each at most once, and never lowers an epoch (Property 14). After the store is restored to an earlier point, or fails over to a copy that may have lost commits, every revocation and rebinding after that point is replayed with its epoch before the store takes traffic, and a replica that finds the history behind its copy drops the whole copy and raises Degraded until a full read completes (Property 15, SR-50, design/20 section 9). No reader holds a lock a revocation waits on, so revocation waits on no delegated transaction (Property 9). SR-58 holds a revocation effective on every replica from that commit, at the latest by `tenancy.copy-life` where the notification is late or lost. A delegation in state `active` or `expiring` is in force. Besides the API's check on each request, a stored message, a job step, a page of members and every store operation each re-check the delegation they carry, which must be the organisation's own (RFC 0002 section 2). A replica whose copy of the delegation is stale, unknown or behind the epoch the work carries defers the work; one whose copy is ahead of it refuses. The workbench token's expiry ends every read under its snapshot, and the revocation test includes a workbench `Set` read and a delegated transaction kept open across the revocation.

## Alternatives
- **Ship the surface `experimental` without an RFC, or one RFC per port.** Both rejected in the ruling on #1535: the class sets break rules, not the route, and the parts share the context, the error shape and the runner. `Clock`, `Entropy` and the retry executor share none of them, so they are RFC 0008.
- **Re-export arrow-rs types from `grdr-ports`.** Zero-copy, but the daemon would link Arrow, and every arrow-rs major (up to one a quarter, https://github.com/apache/arrow-rs/blob/main/README.md, read 2026-11-20) would break the port and every partner adapter. Rejected for Arrow IPC, whose format has stayed backward compatible within version 1 since 1.0 (https://github.com/apache/arrow/blob/main/docs/source/format/Versioning.rst, read 2026-11-20). Brief 11 already recommends Arrow and Parquet as the event format.
- **A row and value model of our own in `grdr-ports`.** It invents a second columnar format beside Arrow (P10, P17) and adds a conversion to every adapter. Rejected.
- **`async-trait` or boxed `dyn` ports, for runtime selection.** A new dependency and an allocation per call. Selection by generated dispatch from `dist.toml` gives the same reach with neither. Rejected.
- **A generic server builder that an embedder calls from its own `main`.** It works, but every embedder writes and maintains composition code, and the release build would select by a second route. Rejected for the one `dist.toml` route design/03 already names.
- **Source scans instead of the seal and the mint authority.** A scan of who implements a port or who calls a minting function holds only where it runs and only over what it reads: a macro, a build script or an `include!` emits what a source scan does not see, and a function pointer or an alias hides a call. Rejected for types. The checks that remain are the register check, which reads each crate after macro expansion and name resolution, and ARCH-029, whose handle rule reads source as written and fails the forms a macro, an alias or a re-export would use.
- **The `unsafe_code` lint as the `unsafe` barrier.** It fires on `unsafe` written in the crate, not on what another crate's macro, derive or proc macro emits into it, and not on a safe function of another crate that wraps `unsafe`. Rejected for the register check over expanded code and every crate of the closure; the lint stays as a first check.
- **One open trait per port, with admission checked by each `grdr-ports` function.** It needs no adapter traits, but a module implementation could still be handed to other module code, and every adapter would carry the check. Rejected for sealed port traits that only `Admitted` implements, with the check in one trust-core place.
- **An unpublished minting crate restricted by a dependency-graph rule.** It adds a crate and a same-layer edge and still rests on a rule a build must run. Rejected for a mint authority the compiler keeps inside `tenant`.
- **A mint authority without the once-per-process issue.** Any crate could call its constructor. Rejected: issuing once, first, by the composition root makes a second issuer either fail or stop the start.
- **A mint authority that runners hold, with a lint that follows its value.** Once a value holding it is erased to a trait object, kept in a `static` or carried through another crate, no type names it, so the lint would need data flow. Rejected for an authority that never leaves `tenant` and handles that each mint only within their scope.
- **A share lock on the delegation row, taken by delegated transactions.** Revocation then waits on every holder, and holders that overlap keep it waiting. Rejected for a marker that every reader counts and a revocation that is one commit.
- **The bound as a setting the transaction can change.** A statement could lift its own transaction's bound. Rejected for a bound enforced from outside the transaction (Property 10).
- **Split `Bus` into an append trait and a consumer trait.** A claim needs a `Lease` and a commit the fence of the partition's lease, so a holder of `Bus` without `Leases` cannot consume. The split would add a trait and stop nothing more. Rejected.
- **One fence form everywhere, lease-checked.** The bus tables may live in a separate database from the lease table (design/20 section 7), so the bus cannot check the lease inside its own transaction. Rejected for two named forms.
- **SERIALIZABLE as a lease-checked form.** A read of the lease row followed by another holder's `acquire` is a single read-write dependency, which serialisable snapshot isolation does not abort, so the stale commit lands. Rejected; only a lock on the lease row counts.
- **Storage-side fencing on the bus with the token stored at first commit, as #299 had it.** It leaves a window in which the old holder commits after the new one starts from an older position, and the new holder's correct offset then reads as `Regress`. Rejected for the compare-and-set stamp at `subscribe`.
- **The same token for a re-acquiring holder, as #298 R3 had it.** Every task of one process shares the token, so a stalled task and its replacement both hold a current fence. Rejected for a new token on every acquisition.
- **`guard(&mut self, &Fence)` or `commit_fenced` chosen at commit time.** A failed guard leaves the transaction usable, and a commit-time choice lets code holding a transaction skip the check. Rejected for `write_fenced`, which binds the fence when the transaction opens.
- **`tail` as a port method that callers union.** A caller that forgets the union, or drops a failed tail, shows "nothing happened" when the product could not look (P9). Rejected for the union inside `execute`.
- **One `Partial` reason for both a hit limit and a missed tail.** One of the two is lost: either paging ends `Complete` with tail rows missing, or a long read against a down tail cannot be paged. Rejected for `Completion` and `Coverage` side by side, with coverage carried in `Resume`.
- **Coverage stored in both the ending and the `Resume` it returns.** The two copies can disagree, and a caller can keep the wrong one. Rejected for one copy in `Ending`, from which `resume()` derives the `Resume`.
- **Read the catalogue head and file list on every `execute`, with no file-list cache.** Correct, but every row read pays the catalogue round trip the cache exists to save. Rejected for the version in the buffer answer, which lets the cache serve whenever it is new enough.
- **A Bus read that returns every partition a kept bucket-map version assigns an organisation, with a key-history table.** The lake adapter would need ingest's bucket function and key rule a second time, and a change to that rule in `ingest` would leave reads asking the wrong partitions. Rejected for the adapter's own partition record, which `append` writes.
- **A cached partition record.** A copy from before a partition's first row for the organisation does not ask that partition, and no answer the read receives can tell it so. Rejected for reading the record where it is written, at one indexed read.
- **The new partition's holder re-reads the head after the old partition's last commit for the organisation.** It needs a signal from the old holder to the new one, and a read during the move still has to ask the old partition. Rejected for asking every partition in the record.
- **Floors kept per `Holder`.** A task restarted inside one process keeps its predecessor's floor while its new buffer has no drop version, so a stale cache can serve and the row is missing with `Full`. Rejected for floors per fence.
- **Counting any answer from the holder a read reached.** A holder that lost its lease between the lookup and its answer has dropped its buffers and still reports its old floor. Rejected for an answer only under a current fence.
- **Closing the handover window by answering as a failed tail until the new tenure has caught up.** Each tenure would need the partition's last offset at `acquire` passed into the Events adapter, and every handover would end reads `WithoutTail` until the catch-up. Rejected; the window is stated and `Bus::lag` shows it.
- **Lifecycle cells that say yes or no.** `key_unavailable` ingest answers with retry-after and other refusals do not, so `ingest` would branch on the state in code (P14), and a model comparing booleans would not catch it. Rejected for typed answers.
- **Refusing to mint for a `suspended` organisation.** design/21 section 13 keeps `decision` and `spine` ingest, a read-only console and exports for that state, and each needs a context. Rejected for a context that carries the state and the work kind, and a check where work starts and at every store operation.
- **A context from a stored message with no state.** Every consumer then needs its own rule for `None`, and the easy one fails open. Rejected for the state the replica holds, `Unconfirmed` when stale and a refusal when unknown.
- **Delegated `control`-stream work only as jobs.** It leaves the gap between a step's append and the consumer's dispatch, and every other stream needs its own rule. Rejected for the delegation stored with each message and checked by `fetch_batches`.
- **Hook callees written by the adapter, with review checking that each does nothing while unarmed.** A contrib adapter gets no project review, and a callee that takes the adapter's state can change what the suite sees. Rejected for the kit's own `reach`, which takes only a constant, named through the leading `::`.
- **A build script allowed in a `testkit` crate when it does not read `CARGO_FEATURE_TESTKIT`.** A script can build the variable's name at run time or read every variable, so no reading of it tells reliably; whether a crate has a build script is a fact in `cargo metadata`. Rejected.
- **Refuse the file-list cache whenever a buffer answer has dropped nothing since its holder's `acquire`.** Correct, but after every handover each read misses the cache until the new holder's first flush, which can be the whole flush age. Rejected for the floor the holder reads once per organisation after `acquire`.
- **Compile the hook points into every build, inert unless armed, with the fixture in a separate test-only crate.** The admitted type would be the shipped code byte for byte, but every shipped binary would carry crash and fault points, and the arming call would be public API. Rejected for hook points behind the feature, held to one statement form by the `testkit` scan.
- **Per-organisation token exchange for provider hunts.** It gives every hunt a write-capable `SingleCtx` per customer. Rejected for `MemberCtx`.
- **Adapters mint contexts through public hidden constructors.** Every adapter, contrib included, becomes a minting site. Rejected: adapters return plain ids and `grdr-ports` mints.
- **A wrapper for transactions that gives no `&mut` to the adapter's type.** Repositories run statements through that type and need `&mut` to it. Rejected for `statements` with the transaction-type rule.
- **Repositories on the adapter's session, as revision 11 had it.** A repository's own SQL could commit, set constraints, rebind or shadow names under the adapter's checks. Rejected for a runner of declared, prepared statements, with the store's own rules as the boundary (Property 4).
- **`KitAuthority` in every build, held by the lint.** A qualified call or an alias the lint misses would mint for any organisation in a program. Rejected for the `kit` feature and the key of `grdr-ports-kitkey`, which the compiler and the closure check hold.
- **The `kit` feature alone, as revision 12 had it.** Cargo unifies features across one invocation, so every workspace build compiles the feature into every program it builds, and a check of one program's tree does not see it. Rejected for a key the program must name in its own manifest, per-program release builds, and a check of each program's own resolve.
- **The statement check as the store's boundary, as revision 12 had it.** A scan of text cannot see every spelling of a name, a function a plan reaches, or a write inside a `WITH`, and rounds 11 and 12 each found one more. Rejected for the store's own rules as the boundary for data statements (Property 4), with the statement check and the reply check for what those rules do not govern (Properties 7 and 8).
- **SQL text in the repository's `Statement`, as revision 12 had it.** A value built elsewhere with a declared name could carry other text, and one text cannot serve two dialects. Rejected for names in the repository and text in each adapter crate, run by identity.
- **One `Admitted` with a use state for stores, streams and transactions, as revision 12 had it.** A wrapper could hold a state its use never reaches. Rejected for `Admitted`, `AdmittedTx` and `AdmittedStream`.
- **Retries in every storage adapter's calls, as revision 12 had it.** One state per instance that requests reach shares a breaker and a budget between the callers of those requests, which is #1959's design. Rejected, with RFC 0008's ruling R7-1, for the construction-time connect only.
- **One back end's in-database mechanism in this RFC, as revisions 12 to 16 had it.** The port then carried one adapter's roles, binding, checks and change history, and each finding against that mechanism became a change to a public crate. Rejected by the chief architect's scope ruling after round 16 for properties every adapter holds (sections 2 and 9), with the PostgreSQL mechanism as requirements of #2002, tested against the real server in CI.
- **`SchemaRule` as one back end's catalogue rules, and `RefusedReason` with its statement classes and a plan node, as revisions 13 to 16 had them.** Every new rule of that back end became a public variant. Rejected for `StoreProperty`, one variant per property, with the adapter's own rule and class as a `RuleName` from its data.
- **The key re-exported from `grdr-ports`, as revision 13 had it.** Every crate of a workspace build could reach it without naming the key crate. Rejected; the testkit names the key crate itself.
- **A forwarder per token-taking trait, `SubscriptionDispatch` beside a `ResultsDispatch`.** Each is the same two-variant enum. Rejected for one `Dispatch` that implements each such trait.
- **Non-ASCII identifiers with NFC, a bidi-control refusal and a byte bound.** It works but puts Unicode normalisation into the storage format, and every adapter and file system must agree on it byte for byte. Rejected: names people choose go in columns.
- **A per-port copy of the store fault codes.** Twelve codes for one set of causes, each with a page. Rejected for `StoreFault` and the `STORE` area.
- **Declare `retain`, `erase`, `hold`, `manifest`, `put_versioned` and the other query nodes now, returning `NotSupported`.** An adapter could pass the kit without erasure. Rejected under Rule 6.
- **One error enum for the whole crate,** as design/03 section 10 reads today. An adapter crate implements one port and would return variants that cannot happen. Rejected.

## Drawbacks
- Each storage port is two traits, a sealed port trait and an adapter trait, and every call passes through a forwarder in `tenant::admit`.
- The mint authority is issued once per process, so a test process has one authority, held by the kit, and the composition root must issue it before any other code runs.
- Every append and every result batch is encoded and decoded once as Arrow IPC.
- `MemEvents` needs the Arrow crates, so the test kit builds more slowly and #1535 waits on #1532 and splits.
- The storage traits are not dyn-compatible, so the distribution build must generate a dispatch type per port before a contrib adapter can be selected.
- Two fence forms are more to learn than one.
- A new token on every acquisition means a process that re-acquires by mistake invalidates its own earlier fence and loses that work to a retry.
- The Events adapter carries the union, its tail source, the partition record, the coverage rule and the version check on its file-list cache, so it is larger than a plain lake reader. Each `execute` across processes pays one indexed read on the catalogue's primary for the partition record; a read whose cache is older than its buffer answers' floor pays one catalogue read more, and a holder pays one read on the catalogue's primary per organisation after each `acquire`.
- `Subscription::fetch` and `ResultStream::next` take a parameter their adapter receives and does nothing with, and the generated Bus and Events dispatch must nest `Dispatch` for more than two adapters.
- A read asks every partition its organisation has used, so after a re-partition it pays one more tail request per partition the organisation left, and ends `WithoutTail` while any of them is between holders. Each tail answer also pays one fence check.
- Every mint and every store operation reads the replica's tenancy table, every delegated open and write commit step reads the revocation marker, and a provider's job step re-reads its delegation before it is minted. An operation in flight when the state or a delegation changes still completes, bounded by its one call or statement, and a borrow of a relational transaction by the transaction's bound after a change of state, or by its next statement after a revocation; rows `append` buffered before a move commit at the next flush (section 10). Every relational transaction has a life bound, so a long read or export pages across transactions.
- A replica whose revocation notification is late or lost still serves a revoked delegation outside the store for up to `tenancy.copy-life`.
- No crate that names a capability type or a `tenant`, `storage` or `adapter` item takes a registry dependency or a proc macro until #1475 lands, so the test kit's Arrow, and every adapter that needs one, waits on it; the daemon, which names only RFC 0008's items, does not.
- `Setup` exists only inside `tenant::start`, so the composition root builds every handle before it starts a runner, and a runner of a new kind needs a new handle by amendment.
- Every module that names a handle is a trust-core path, so each change to a runner module takes `eval-security`, `eval-adversarial` and two models; runner modules should stay thin. `architecture.toml`'s lists and `security/trust-core.paths` carry the same modules, and the lint fails a listed module neither covers.
- A repository declares every statement it runs, and every relational adapter holds the store properties by mechanisms of its own, checked by store tests against a real store, so a relational adapter is more than its SQL.
- Binding at open, the schema check and the statement and reply checks cost each relational adapter work at every open, build and statement.
- Each relational adapter crate holds the SQL text of every repository statement it serves, so a new repository statement is a change to each relational adapter crate, under its review.
- Until #1959 is decided, every storage adapter returns a peer's transient failures to its caller unretried once it is built, so a request meets a store's brief fault as its own error.
- While a replica's tenancy copy is stale, its organisations defer everything but reads, and delegated work defers reads too.
- The `testkit` scan limits how an adapter adds test hooks: no other test-only code behind the feature, and no build script in a crate that has the feature.
- The distribution build needs each listed adapter's store to run its conformance tests, which makes a contrib build heavier than a plain compile.
- The `Fixture` trait asks an adapter author for stop and fault hooks, which a small adapter may find heavy; `NotApplicable` keeps the bar honest without hiding what was not run.
- Each deferred method and node costs an amendment RFC when its item arrives.

## Unresolved questions
1. **Deployment-scoped objects.** `state-log/`, `ephemeral/detect/` and the content repository have no organisation, so they cannot be `TenantPath` values. Lean: a separate deployment-scoped trait over a closed `DeploymentPath`, with `put_versioned`, listing and removal, never an org-less `TenantPath`. Settled by an amendment drafted when R-1 or D-1 is specified. It is a prerequisite of the filesystem Blobs adapter item and of the `embedded` profile's first-run slice, so neither assumes it.
2. **Where module repository traits live.** They are written once against `StatementRunner` and reached through `statements`, each with its `StatementSet` of names, while each statement's text sits in every relational adapter crate (section 9). In `grdr-ports`, every repository change is an RFC. In a layer 2 crate with `surface = "internal"` such as `grdr-repos`, as `grdr-messages` does, it costs one RFC for the crate and its same-layer edge. Lean: the second: no stability promise to an outside relational adapter until an RFC gives one. An embedder can implement the adapter traits and the probe statements' text today, but not the module repositories with any promise. Settled before S-2's first module repository.
3. **The deployment-scoped transaction.** Runtime settings and the operator realm (D-70, design/20 O-3 and O-4) need one, with a witness from the operator realm (design/21 O1). So does the bus log's consumer read across organisations, which needs a deployment binding that only the bus consumer path can set; the bus adapter writes its own tables inside its crate (ARCH-015 allows its SQL there), so it does not need this through the Relational port, but design/21 section 2 must state the binding (the placeholder in section 14). The tenancy table each replica holds (section 2) reads organisation states and delegations outside any one organisation's binding too, and the same RFC states how, names the writer of `delegation_snapshot` rows, which decide what a `SetCtx` can read, and states the tenancy history and its confirming read (Properties 13 to 15). Lean: a separate store identity for each of these paths, bounded and checked as Property 5 states. Settled by its own RFC with O-3, which is a prerequisite of the log Bus adapter item and of the authentication middleware item.
4. **The slice-0 surfaces of `grdr-model` and `grdr-schema`** (#18, #278, #279, #282, #284). These signatures name their types (`OrgId`, `DelegationId`, `DelegationSnapshotId`, `ProviderId`, `HolderId`, `IdError`, `Timestamp`, `UploadedLane`, `SessionId`, `DeviceId`, `Epoch`, `Seq`, the column manifest). RFC 0009 (ADR-0041, pull request #1991) states the `grdr-model` types, and #1852 settles the column manifest.
