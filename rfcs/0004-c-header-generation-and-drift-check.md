## Summary
Each FFI crate generates its C header from a descriptor in its own integration test, `tests/header_drift.rs`. It commits the header, and a C source of layout asserts beside it, under `include/`, and the library's own compile-time checks under `src/`.

The descriptor names every export, struct, enum, typedef and constant, and each field's data class and byte encoding. The compiler and the linker hold it to the Rust items:
- a changed signature, a missing field, a changed field type or a missing enum variant stops the test from compiling;
- every declared export is declared again by its C name, so the test does not link if the library lacks the symbol;
- the library compiles `src/<file>_abi.rs`, which the drift test generates: a size, alignment and offset assert for every struct, and a coercion of every export to its described signature.

The first two hold in the build `cargo test` makes and in the release test build. The third holds in every build of the library: each profile, feature set and target.

A tool crate, `grdr-cabi-testkit`, owns the rest of the drift test. It renders the header, the layout source and `src/<file>_abi.rs`, compares them with the committed ones, and runs five checks:
- `HDR-1`, C types and layout against the Rust types that built them;
- `HDR-2`, the committed text;
- `HDR-3`, every declaration, stated offset and stated data class against the contract that the header's row in `surfaces.toml` names;
- `HDR-4`, status codes and version constants against the registry and the library;
- `HDR-5`, each linked symbol against the Rust item described, and the crate's manifest.

Every failure names its next step. A CI job, `c-headers`, does five things on the systems `verify.yml`'s `plan` job selects:
- it runs each listed header's drift test by name, as `cargo test` and as `cargo test --release` with the shipped features, and requires exactly one passed test each time;
- it runs a negative control, a one-byte change to each committed header in a fresh copy, which must make both runs fail;
- it compiles every committed header and layout source as C and as C++, with warnings as errors, including under an embedder's 1-byte packing;
- it compares each built library's export table with its header;
- it checks the library, in each profile it ships in, and the drift test, for every target it ships for. The header's row in `surfaces.toml` names the profiles, features and targets.

**What this guards against.** The drift test and `c-headers` catch accidental drift. That is a signature, field, layout, constant, export or contract that no longer matches, made by anyone who writes the descriptor in good faith, an agent included. They do not stop a hostile writer of the descriptor. The controls against one are the trust-core review of `tests/header_drift.rs` with the evaluators D-63 requires, the export-table check of #1784 on the built libraries, and the protection of `surfaces.toml` and the contract (section 0).

No third-party dependency is added. cbindgen is not used, the licence policy does not change, and `Cargo.lock` gains no third-party package. `grdr.h` and `grdr_macos.h` use the same method; what differs between headers is content.

A runnable sketch on #474 builds each drift test both ways, builds each library as the embedded profile does (`panic = "abort"`, opt-level 3), and checks each library and drift test for six targets, x86_64 and aarch64 on Linux, macOS and Windows. It runs on two stand-in crates:
- each of 35 seeded rows that must fail does fail, and the 6 that must pass do;
- among the failures are P1, a field that exists only under `panic = "abort"`, and T1, a `c_char` export that differs on aarch64 Linux;
- the negative control catches a test that checks nothing;
- the 30 seeded unit tests pass on Windows and Linux;
- gcc, clang and MSVC build the generated files cleanly, under an embedder's 1-byte packing too.

## Motivation
EM-2 (#418) cannot be readied until this is decided. Its R5 asks for a test that fails when `grdr_fastpath.h` differs from the exported functions and `#[repr(C)]` types. Design/26 EM-2 says the "header [is] generated and diffed in CI". Design/03 section 7 gates the C ABI on "Generated header diffed". `c-abi.md` (#246) says the generated headers of EM-2 and EM-4 "are diffed against this text". #388 R12 asks the same for `grdr.h`, and #247 R7 for `grdr_macos.h`. Three headers need one answer.

The constraints:
- **Closure.** `libgrdr_fastpath` may resolve `grdr-fastpath` and `grdr-fastpath-ffi` only, as normal and build dependencies (design/26 section 2; #418 AC-6). A build-dependency is out.
- **Licence.** cbindgen 0.29.4 is MPL-2.0 (https://raw.githubusercontent.com/mozilla/cbindgen/main/Cargo.toml, read 2026-11-20; release dated 2026-06-10). `supply-chain/licences.toml` keeps MPL-2.0 out of the libraries and closures it names. Under ADR-0032 (#1686, proposed), code that runs only at build or test time is a development tool, so a cbindgen dev-dependency may be admissible. Its cost is in Alternative (b1).
- **No `xtask`.** ADR-0029 removed the `xtask` crate ("No `xtask` crate returns"), so #474 R1 (b)'s `xtask` route is gone.
- **Types in another crate.** #405 R1 may put the `#[repr(C)]` input and verdict in `grdr-fastpath` and have the FFI crate mirror them. A check that reads the FFI crate's source text would not see their fields; one that asks the compiler does.
- **No source scan.** Three reviews broke a line-based scan of `src/lib.rs` from different directions: macro bodies, attribute forms, rustfmt skips, decoys and manifest keys. A check of exports must use what the compiler and linker produce.

## Design

### 0. Threat statement
- **What the drift test is for.** It catches accidental drift between four things: the Rust exports and `#[repr(C)]` types, the committed header and its layout source, the header's listed contract, and the status registry. It checks them in three places: in the build `cargo test` makes, in the release test build, and through checks the library compiles in every build, in each profile and for each target the header's row names.

  "Accidental" means a change made in good faith that leaves one of them behind. Examples are a parameter type changed in Rust only, a field added without the descriptor, a hand edit of the header, a value moved in the registry, a field that exists only in one build configuration, or a test that stopped checking. An agent's mistake is accidental.
- **What it is not for.** A hostile writer of `tests/header_drift.rs`, of the crate's `src/` or of its manifest can make the drift test pass while the header is wrong. The descriptor is that writer's own statement, and the test runs code that writer controls.

  Nothing in this RFC claims otherwise. The hardening of section 5 catches accident and obvious misuse, not intent. That hardening is private fields on the descriptor's records, a test the testkit writes, and no paths or environment taken from the test.
- **The controls against a hostile writer:**
  1. **Review.** `crates/grdr-fastpath-ffi/**` and `crates/grdr-ffi/**` are trust core, so every change to their descriptors and sources takes `eval-security`, `eval-adversarial` and two passing evaluators on different models (D-63, owner instruction 7). `crates/grdr-cabi-testkit/**` takes the high-tier evaluators (#1777).
  2. **The built artefacts.** `c-headers` step 4 (#1784) reads the export tables of the release `cdylib` and `staticlib` with `llvm-nm` and `llvm-readobj`, outside any code the descriptor writer controls. It compares them with the committed header in both directions.
  3. **The oracles' protection.** Under ADR-0035 no session has permission limits, so the protected paths are held by review and CI. `team/06` section 2.1 lists them, and every evaluator fails a diff that writes outside its issue's write set. #1668's write-set job is to fail such a change in CI once it lands. A protected change lands only after `eval-security` and an evaluator on the other model pass. `spec/**` is high tier, and `surfaces.toml` is a trust-core path (ADR-0020). `rfc-required` (#1741), which would fail a host-contract change without an accepted RFC, is pending: #1741 is open.
  4. **The tier of every descriptor.** #1777 puts `crates/*/tests/header_drift.rs`, `crates/*/include/**` and `crates/*/src/*_abi.rs` at high tier. A crate that is not trust core, such as `grdr-sensor-macos`, therefore still takes the high-tier evaluators for a header change.

- **What remains.** A hostile writer who also passes trust-core review and changes the ABI in a way the export table cannot show, such as a parameter's type behind the same symbol, is not caught mechanically. That is a residual risk of this design (section 10), held by review.

### 1. Answers to #474
- **R1.** Neither (a) nor (b) as written. The header is generated, as design/26 and design/03 say. The generator is `grdr-cabi-testkit`, run by the crate's own drift test, over a descriptor the compiler and the linker hold to the Rust items. The committed header and layout source are the generated ones, byte for byte, and the `c-headers` job compiles both.
- **R2.** Not applicable: no cbindgen, no third-party dependency, no MPL-2.0 admission. The alternatives that would have needed one are under Alternatives.
- **R3.** The same method for `grdr.h` (#378 R5 (b), #388 R12) and `grdr_macos.h` (#247 R7). The status block of `grdr_fastpath.h` and `grdr.h` is one piece of default content in the testkit, `content::grdr_status`. Both descriptors use it, so the two blocks cannot differ. `grdr_macos.h` uses its own `i32` status enum and no status block. The sketch shows that header too.

### 2. Terms
- The **descriptor** is the list of a header's content, written in the crate's `tests/header_drift.rs` with the testkit's macros. Its parts are:
  - the file, guard, SPDX identifier and summary;
  - an optional status block and an optional version;
  - typedefs, enums, constants, opaque types, structs and functions.
- The **header list** is the set of `[[c_header]]` rows in `surfaces.toml` at the repository root. Each row gives a header's `file`, its `crate`, its `contract` document, the `section` of that document and its stability `class`. It also gives what the header ships in: `profiles`, `features` and `targets`, each a space-separated list (section 7, step 5). Every value is one double-quoted string, so the testkit and the job read rows with one line rule. ADR-0020 makes `surfaces.toml` the protected, trust-core registry of public surfaces, so a header's class has to live there anyway.
- To **render** is to produce the header, its layout source and `src/<file>_abi.rs` from the descriptor and, where the header has a status block, `status-codes.toml`. Rendering depends on nothing else, and in particular not on the host: the files are byte-identical on Windows and Linux in the sketch.
- To **bless** is to run the drift test with `GRDR_BLESS_HEADERS=1`, and the library built with `--cfg grdr_bless` (section 8). It writes the header and layout source to `include/`, creating the directory when it is missing, and the checks to `src/`. Then it fails the run, so a bless never passes CI. It writes nothing if any comment text would break the C.
- The **contract section** of a header is the `## ` section, in the document its row names, whose heading names the header file in backticks: section 2 of `c-abi.md` for `grdr_fastpath.h`, section 3 for `grdr.h`.
- A **check id** (`HDR-1` to `HDR-5`) names one kind of failure. Like the `TV-n` rules of `tables.md`, it appears only in test output, never at run time and never in output an administrator sees. It takes no `GRDR-<AREA>-<NNNN>` code and no `/codes` page.

### 4. The descriptor
```rust
c_struct_type!(Here, ffi::grdr_fp_input);          // module level, once per described type
c_opaque_type!(Here, ffi::grdr_fp_tables);
c_struct!(Here, ffi::grdr_fp_input, "<doc>", {
    struct_size: u32 => [Structural] "<doc>",
    path: *const c_void => [ContentArgument, InField("path_encoding")] "<doc>",
    /* every field */
});
c_fn!(Here, ffi::grdr_fp_load, "<doc>",
      ("blob": *const u8, "len": usize, "arena": *mut c_void, "arena_len": usize,
       "out": *mut *const ffi::grdr_fp_tables) -> ffi::grdr_status as "grdr_status");
c_const!(ffi::GRDR_FP_PASS, "<doc>");
c_status!(ffi::GRDR_E_ARG);
c_enum!(ffi::grdr_macos_status as i32, "<doc>", { GRDR_MACOS_OK => "<doc>", /* every variant */ });
```
What the compiler holds:
- **D1. Signatures.** `c_fn!` coerces the item to `unsafe extern "C" fn(<the listed types>) -> <return>`. A changed parameter type, a parameter added or removed, or a changed return type fails with E0308. The error points at the descriptor line and prints the expected and found pointer types; the sketch's seed s1 shows it.
- **D2. Fields.** `c_struct!` destructures the struct with every listed field and no `..`. A field added in Rust fails to compile ("pattern requires `..`"), and one removed from Rust fails with E0026 and E0609.
- **D3. Field types.** Each field is read through `fn(&S) -> &T` with the listed `T`. A changed type fails with E0308.
- **D4. Enum variants.** `c_enum!` matches every listed variant with no wildcard, so a variant added in Rust fails with E0004. It records each value both as the described C integer type and as `i128`, and `HDR-1` compares the two.
- **D5. Data class and encoding.** Every field carries a `DataClass` (`Identifier`, `Structural`, `Derived`, `ContentArgument`, `ContentBody`; design/04 section 2). The macro syntax requires it, and the header prints it beside the field. A byte field must carry an `Encoding`: `Utf8`, `InField("<field>")`, `NetworkOrder`, `Binary` or `Opaque`. A byte field is a pointer to a byte or to `void`, or an array of bytes. Any other field must carry none, and `HDR-1` checks both ways. No encoding implies a terminator.

What the compiler and the linker hold together:
- **D6. Closed C types.** A `CTy`'s fields are private. Outside the testkit, a `CTy` comes from the testkit's own `CType` impls and from `described` and `described_enum`. Those two are public because the type macros expand in the describing crate and call them:
  - the testkit's impls cover `u8` to `u64`, `i8` to `i64`, `usize`, `c_void`, `()`, `*const T`, `*mut T`, `[T; N]` and `Option<unsafe extern "C" fn(..)>`;
  - `c_struct_type!`, `c_opaque_type!` and `c_enum_type!` give a described type its C type from its own path.

  A descriptor that calls `described` by hand is the misuse section 0 leaves to review.

  Every node records two things: the `TypeId` of the Rust type that built it, and the `TypeId` of the Rust type its position holds. Each parent records the second from its real type parameter, and `c_fn!` and `c_struct!` record it for every parameter, return and field. `HDR-1` requires the two to be equal at every node. It also requires every struct, opaque or enum name to be a described item of that same `TypeId`.

  This catches the accidental case: a C type taken for the wrong Rust type, or a hand-written `CType` impl for `bool`, `char`, a reference, `NonNull`, `NonZero*` or a bare function pointer, none of which the testkit maps. Seeded unit tests hold the four such impls of eval-security's round 1. It is not a defence against a writer who sets out to place a node where it does not belong; eval-security round 3 showed that the descriptor can still do so (section 0).
- **D7. Spellings.** `as "<name>"` spells a type by a typedef, and the name must be in the header's closed typedef table: the descriptor's typedefs, the status block's typedef and the enums' typedefs. The typedef's underlying type must equal the Rust type's. The only other name allowed is the builtin `char`, over a one-byte type. On a pointer to a one-byte type it names the pointee, so `*const c_char as "char"` is `const char *` on every target. Rust's `c_char` is an alias of `i8` on some targets and of `u8` on others, such as aarch64 Linux. A bare `c_char` would therefore render differently per target, so `HDR-1` refuses a `c_char` in the descriptor that is not spelled `as "char"`. `c-headers` step 5 type-checks the drift test for every shipped target, which catches a `c_char` export described as `i8` (seed T1).
- **D8. Array parameters and function-pointer fields.** `"entropy": *const u8 [32]` renders the C array parameter `const uint8_t entropy[32]`, which C reads as a pointer. `[n]` is allowed only after a pointer parameter, with n above 0. The length is not in the Rust type, so `HDR-3` holds it against the contract. A function-pointer field lists its parameter names, `("ctx", "size", "align")`, one per parameter, and only `Option` of a function pointer maps, since C may pass null.
- **D9. Enums cross only as return values.** C may pass any value of an integer typedef, and a Rust enum holding an undeclared value is undefined behaviour. So `HDR-1` refuses a Rust enum type, at any depth, in a parameter or a struct field, and allows it only as a by-value return. Where C writes the value, the export takes the integer type, spelled by the enum's typedef (`"prior": i32 as "grdr_macos_status"`), and converts it with a checked `match` that returns an error status for an undeclared value.
- **D10. Names.** A struct, enum, function or constant takes its C name from the last segment of a two-segment Rust path, `ffi::<name>`. Parameter names are C names, written as strings, because `in` is a Rust keyword. Status constants are listed with `c_status!(ffi::GRDR_OK)`, which takes the name from the item, so a name cannot be paired with another constant's value. If #405 defines the input and verdict in `grdr-fastpath`, the FFI crate re-exports them under the C names.
- **D11. Every declared export is the item described.** `c_fn!` writes a foreign declaration of the C symbol by its name and with the described signature, and takes its address.
  - If the library defines no such symbol, the drift test does not link. That catches the accidental form of round 3's E1 and E2: an export compiled out by a `#[cfg]`, with a `pub use` of another function left in its place.
  - The test then compares that address with the address of the Rust item the descriptor names. An accidental stand-in, such as an old function left behind beside the export, a `pub use` of the wrong item or a module that shadows the crate path, is a different function, so `HDR-5` fails. The sketch's seeds G and X1 show it.

  The compiler checks the signature of the item described (D1), and the identity check ties that item to the export, which together catch the accidental mismatch of a signature. A hostile writer can still satisfy both while the exported signature differs (eval-adversarial round 3). The export-table check of #1784 and review are the controls there (section 0).

What differs between headers is content, not code (P14): the file name, guard, SPDX identifier, summary, an optional status block, and an optional version. A version is `{ major, minor, packed macro, minor_bits, runtime }`, so the `major << 16 | minor` scheme of `c-abi.md` is data. The contract is not descriptor content at all: it comes from the header list. A Rust constant left out of the descriptor is not part of the C surface; that is allowed, and seed s9 shows it.

### 5. The checks
The test is one line at the top level of `tests/header_drift.rs`, `kit::drift_test!(descriptor);`, which writes a `#[test] fn header_drift`. It calls `grdr_cabi_testkit::run(&descriptor(), env!("CARGO_MANIFEST_DIR"), env!("CARGO_TARGET_TMPDIR"))`, which uses the real file system and environment. `run` is public, because the macro expands in the FFI crate. A hand-written test that calls it with another directory, or one that checks nothing, is the obvious misuse that the negative control of section 7 catches and review holds (section 0). The `Env` trait and `Paths` are internal to the testkit, for its own unit tests.

The descriptor's records, `Header`, `Function` and `Struct`, have private fields. `c_header!`, `c_fn!` and `c_struct!` build them through constructors hidden from the documentation, so a descriptor does not edit a record by accident after the macro has checked it. Like `drift_test!`, this catches accident and obvious misuse. A hostile writer can still call the hidden constructors the macros call, or write its own test (section 0).

`run` reads the committed files, `surfaces.toml` and the contract its row names, the crate's `Cargo.toml` and, where there is a status block, the registry. It lists `src/` recursively and fails on any entry it cannot read. Then it runs the checks below, writes the rendered copies to `CARGO_TARGET_TMPDIR`, and blesses if asked. It returns one line per failure: the id, the detail, and `next:` with the one step that fixes it.

A missing or unreadable input is a failure of the check that reads it, never a separate kind. A symbol the library lacks is a link failure of the test build, before any check runs (D11).

| Id | Fails when | Example detail, and its next step |
|---|---|---|
| `HDR-1` types and layout | A struct's offsets, size or alignment from rustc differ from the C layout of its listed fields, computed with rustc's sizes and alignments on the host. | `HDR-2` text | A committed file is missing, has CR line endings, or differs from its rendering. | `HDR-4` constants | The registry uses a form outside the reader's subset, or repeats a key, a name or a value. Also when its rows that are not retired differ from the `c_status!` constants. Also when the crate's `grdr_status_str`, where the descriptor passes it, returns other than each row's name and the registry's `unknown_name`, or the version function returns other than the packed version constants | `Rust GRDR_E_STATE = 9 has no such row`; next: make `status-codes.toml` and the Rust constants agree; a new code needs an RFC (c-abi.md section 6) |
| `HDR-5` exports and manifest | The C symbol the linker resolves for a described function is not the Rust item the descriptor names (D11). Also when the crate's `Cargo.toml` sets `package.build`, `package.autolib`, `package.autotests`, a `[lib] path` other than `src/lib.rs`, or `required-features`, `test` or `harness` on the `header_drift` target. Also when `src/lib.rs` has no `mod <file>_abi;` line, so the library would not compile its generated checks. As an early warning only, it also keeps revision 3's source scan: an export not written out at the top level of `src/lib.rs`, or hidden behind `include!`, `#[path]`, `global_asm!`, `export_name`, `rustfmt::skip` or `#[cfg]` | `grdr_fp_arena_size: the linked C symbol is not the Rust item the descriptor names`; next: describe the exported function itself, and remove whatever stands in for it |

Rules the checks rest on:
- **Every build of the library checks itself.** `src/<file>_abi.rs` holds, under `#[cfg(target_pointer_width = "64")]`, a size, alignment and offset assert for every struct of the 64-bit model. It also holds a `compile_error!` on any other pointer width, and a `const` coercion of every export to the signature the descriptor states.
  - Every profile, feature set and target that builds the library compiles these checks: the embedded profile with `panic = "abort"`, a feature only a test build turns on through a dev-dependency, an aarch64 target. So a layout or signature that differs there stops that build (eval-adversarial round 4's blocker; the sketch's seed P1).
  - Each assert carries a message naming the header, the item and the next step, such as `"grdr_fastpath.h: grdr_fp_input.label_bits moved; bless as the header's banner says"`, so the first error a developer meets says what to do.
  - The library therefore does not build for a 32-bit target, `wasm32` among them, until that target's checks exist (section 11).
  - The module sits behind `#[cfg(not(grdr_bless))]`, so a bless can build the library while the checks are stale. Only the bless command sets `grdr_bless`, and each FFI crate's `Cargo.toml` declares it under `[lints.rust] unexpected_cfgs`. `c-headers` step 1 fails when the repository's Cargo configuration or the job's environment sets it.
- **Every build of the test.** The descriptor's own checks (D1 to D4, D11, `HDR-1`) compile into the test, so `c-headers` runs the test twice: as `cargo test` builds it, and as `cargo test --release` with the row's `features`. Step 5 also type-checks it for every shipped target. A field or parameter under `#[cfg(not(debug_assertions))]` is then seen (eval-security C1 and C2), and so is a `c_char` signature that changes with the target (seed T1).
- **Two layout models.** `HDR-1` uses rustc's own sizes and alignments on the host, so it is right on any target, including one where `uint64_t` aligns to 4 inside a struct. `HDR-3` and the layout source use the 64-bit model: natural alignment and 8-byte pointers, which every 64-bit target this repository builds shares. On a 64-bit host the two agree, so an offset the contract states is checked against rustc. `LP64_POINTER_BYTES` and the 100-column `WIDTH` are part of the rendered form (section 6), not `limits.toml` entries.
- **The early warning is not the guarantee.** `HDR-5`'s source scan finds an undescribed or hidden export before CI does, which is all it is for. The guarantee against accidental drift rests on D11 and on `c-headers` step 4. The scan reads attributes whole, outside string and char literals. If it ever gives a false failure, it is removed, not loosened.
- **Identity and folding.** In the unoptimised test build no linker this repository uses folds identical functions, so two distinct functions have distinct addresses. In the release run a linker may fold them. Folding joins only identical machine code, though, so an equal address still means the export behaves as the described item.
- **The manifest, as Cargo reads it.** `HDR-5` reads `Cargo.toml` by lines, which catches the usual spellings by accident. `c-headers` step 1 also reads every listed crate through `cargo metadata --no-deps`, the manifest's real consumer. It refuses a `custom-build` target, a library `src_path` other than `src/lib.rs`, and a `header_drift` target with `test` false or required features.
- **Registry reader.** It accepts comments, blank lines, top-level keys (`unknown_name`), `[[status]]`, and `key = value` where the value is a decimal integer, `true`, `false`, or a double-quoted string with no escape and no inner quote. Any other line, or a repeated key, is `HDR-4` with its line number. `handle_after` is behaviour, so #388's handle-state tests check it, not the header.
- **Header-list reader.** It reads the `[[c_header]]` rows of `surfaces.toml`, each line `key = "value"`, skips other tables, and refuses a repeated key. The descriptor has no contract field, so it cannot point the test at a copy by accident.
- **Contract reader.** It is a tokeniser and stays one.
  - It reads every fence whose language, the first word of the info string, is `c` or `h`, whatever attributes follow (`` ```c title="t.h" ``). It refuses, as `HDR-3`, a fence of another C-like language (`C`, `H`, `cc`, `cpp`, `cxx`, `c++`, `hh`, `hpp`, `objc`, `objective-c`). So a contract cannot hide a declaration from the reader by accident.
  - Identifiers and numbers, with suffixes such as `1u`, are one token each, and each other non-space character is one token.
  - Each `#define` line is one declaration, and every other declaration ends at a `;` outside braces. Other preprocessor lines are skipped.
  - A stated offset is the first number in a field's comment inside a `typedef struct ... {` block, and a stated size is the first number after its closing brace.
  - A stated data class and encoding is the first `[...]` in a field's comment, compared as text with the bracket the header renders for that field, such as `[identifier; network byte order]`. Every field of a struct the descriptor describes must state one.
  - No expression is evaluated.
- **No waits, no skips.** The test reads and writes files and makes no process, network or clock call, so nothing in it waits. It has no skip path on any host. A test that stopped checking cannot report itself; the negative control of section 7, step 2, catches that.

### 6. The rendered files
The header, in this order:
1. `/* SPDX-License-Identifier: <spdx> */`, from the descriptor.
2. A banner: the file, its summary, "Generated by the header_drift test of `<crate>`; do not edit", and the exact command, `RUSTFLAGS="--cfg grdr_bless" GRDR_BLESS_HEADERS=1 cargo test --locked -p <crate> --test header_drift`.
3. The include guard, `<stddef.h>` and `<stdint.h>`, and `extern "C"` under `__cplusplus`.
4. The status block, where the descriptor has one. For `grdr_status` headers:
   - `#ifndef GRDR_STATUS_DEFINED`, then `typedef uint32_t grdr_status;`;
   - one `#define <name> ((grdr_status)<value>u)` per row, with its `meaning` as a comment;
   - a retired row stays, marked "Retired.".
5. The version macros, then constants, enums (a typedef and one `#define` per variant), typedefs, opaque types, structs and prototypes. Each field is commented with `[<data class>; <encoding>]` and its doc, and prototypes are wrapped at 100 columns.

The structs sit between `#pragma pack(push, 8)` and `#pragma pack(pop)`. An embedder that compiles with a smaller packing still gets the natural layout the contract states: a `#pragma pack(1)` in force at the include, gcc's and clang's `-fpack-struct=1`, or MSVC's `/Zp1`. The sketch measured all three (section 12). The contract reader skips them, because they are preprocessor lines.

The header carries no offsets or sizes, because they differ between targets. The layout source, `<file>_layout.c`, carries them.
- It includes the header and, under `#if UINTPTR_MAX == 0xFFFFFFFFFFFFFFFFu`, asserts every typedef size and every struct size and field offset of the 64-bit model. It uses `_Static_assert`, or `static_assert` in C++.
- On any other target its `#else` branch is an `#error` saying that the file models 64-bit targets only, so a target it does not model cannot pass by asserting nothing.
- It is committed beside the header and ships beside it in the embedded kit, so an embedder can compile it without Rust.

The third generated file, `src/<file>_abi.rs`, is the library's own copy of those checks (section 5), plus the export signatures.

Every line ends in LF. The product name never appears; the `grdr` namespace stays fixed under a rebrand (ADR-0003). Person-facing status text is not in the header: `grdr_status_str` returns identifiers (c-abi.md section 3; D-69).

### 7. The `c-headers` job
The `c-headers` job of `verify.yml` takes its systems from the workflow's `plan` job, as the `rust` job does: `needs: plan`, with the matrix `fromJSON(needs.plan.outputs.systems)`. It adds no system list of its own. `plan` gives pull requests Linux only (owner instruction 28, runner minutes). It gives every system to a dispatched run, a push to `main` and the nightly run of the public repository, and Linux only to a private copy. So:
- **On every pull request**, ubuntu-26.04 runs every step, compiling with gcc and with clang.
- **On the dispatched run on the head commit**, macos-26 adds Apple clang and windows-2025 adds MSVC, found through `vswhere` and `vcvars64.bat`. The same holds on pushes to `main` and nightly. An item reads those results as #418's AC-8 reads the `rust` jobs. It takes the `workflow_dispatch` run of `verify.yml` on `issue/<n>` whose `headSha` equals the branch head, and expects `c-headers (macos-26)` and `c-headers (windows-2025)` to conclude `success`. The dispatch rules are those #454 put on `main`.
- **In a private copy**, only Linux runs. MSVC and Apple clang never compile its headers. That is the copy's choice of runner minutes, and the release that ships a header comes from the public repository.

On each system it runs, the job:
1. **Holds the files and manifests to the header list.**
   - Every `[[c_header]]` row's header, layout source, `src/<file>_abi.rs` and `tests/header_drift.rs` must exist in its crate, and every `crates/*/include/*.h` must have a row.
   - Every row names at least one profile and one target, and every profile it names is `release` or is defined in the workspace's `Cargo.toml`.
   - `grdr_bless` appears in no Cargo configuration file of the repository, and in no `RUSTFLAGS` or `CARGO_ENCODED_RUSTFLAGS` the job inherits.
   - `cargo metadata --no-deps` must show, for each listed crate, no `custom-build` target, a library `src_path` of `src/lib.rs`, and a `header_drift` target with `test` true and no required features.
2. **Runs each listed drift test by name, in both builds, with a negative control.**
   - `cargo test --locked -p <crate> --test header_drift -- --exact header_drift --include-ignored` must show exactly one passed test in libtest's summary.
   - So must the same command with `--release` and `--features` from the row.
   - Then, in a fresh copy of the checkout with its own empty `CARGO_TARGET_DIR`, the job changes one byte of the committed header. It runs both commands again, and each must fail with exactly one failed test and an `HDR-2` line naming that header. No binary from the checked tree can stand in.

   A drift test that is compiled out, ignored, feature-gated, not built or checking nothing therefore fails the job, even though `cargo test --workspace` would exit 0. The sketch's N1, a hand-written test that checks nothing, passes both commands and fails the control.
3. **Compiles.**
   - Each header alone: as C99 and as C++11 with `-fsyntax-only` under gcc and clang, and as `/std:c11` and `/std:c++14` through a one-line translation unit under MSVC, whose lowest modes those are.
   - Each layout source: as C11 and as C++11 under gcc and clang, and as `/std:c11` and `/std:c++14` under MSVC.
   - Each layout source again under 1-byte packing, which must still pass: included between an embedder's `#pragma pack(push, 1)` and `#pragma pack(pop)`, and compiled with `-fpack-struct=1` under gcc and clang and `/Zp1` under MSVC.
   - One translation unit that includes every header twice, which checks the shared `GRDR_STATUS_DEFINED` guard.

   The flags are `-Wall -Wextra -Wpedantic -Werror` under gcc and clang, and `/W4 /WX` under MSVC.
4. **Compares export tables.** It builds each listed crate in release and compares the exported functions of its `cdylib` and `staticlib` with the functions its header declares, in both directions (#1784). It uses `llvm-nm` and `llvm-readobj` from the pinned toolchain's `llvm-tools-preview` component. This step reads the artefacts that ship, outside any code the descriptor writer controls, which is why section 0 counts it among the controls against a hostile writer.
5. **Checks the shipped configurations.** For each row, for each of its `targets`, with the target's standard library installed by `rustup target add`, it runs:
   - `cargo check --locked --profile <p> --features <row's features> --target <t> -p <crate> --lib` for each of the row's `profiles`. This compiles the library's generated checks exactly as that profile ships it: its panic strategy, its features, no dev-dependency's features, and that target's types.
   - `cargo check --locked --tests --features <row's features> --target <t> -p <crate>`, which type-checks the drift test for that target.

   The rows of `grdr_fastpath.h` and `grdr.h` list `x86_64` and `aarch64` on Linux (`-unknown-linux-gnu`), macOS (`-apple-darwin`) and Windows (`-pc-windows-msvc`), the platforms of design/24's support table, and `profiles = "release"`. #1588 adds `embedded` to both when it defines `[profile.embedded]` (design/03 section 8). The row of `grdr_macos.h` lists the two `-apple-darwin` targets.

   The step runs on Linux. If a crate's dependencies need a target's own SDK even to check, that target's commands run on the matching `plan` system in the dispatched run, and #1779's lead lists the case. A missing target library fails the step. The lists are data in the protected header list, not in the job (P14).

On a system the plan gives it, a missing compiler or tool fails the job; nothing is skipped there. The job is gate configuration, so lead-agent-kit builds it (#1779, and #1784 for step 4), and it blocks #418.

The sketch ran steps 2, 3 and 5 by hand, step 5 through rustc with `-C panic=abort -C opt-level=3`, and every compile exited 0:
- gcc 14.4.0 (`qa ctr gcc:14`) and clang 18.1.3 (Ubuntu 24.04): C99, C11, C17, C++11, C++17 and C++20 under `-Wpedantic -Werror`;
- MSVC (Visual Studio 18): each header alone, both layout sources and the combined unit, as `/std:c11`, `/std:c++14` and `/std:c++17` under `/W4 /WX`;
- 1-byte packing: `#pragma pack(1)` at the include under gcc 14, clang 18 and MSVC, `-fpack-struct=1` under gcc 14 and clang 18, and `/Zp1` under MSVC. With the header's pragmas removed, each of these fails the layout asserts, as the control requires.

Neither Linux image has 32-bit libc headers. With `clang -m32 -ffreestanding`, the layout source stops at its `#error`, as intended. Section 11 makes a 32-bit compiler leg a condition of any 32-bit pilot.

### 8. Changing a header
A change to a C ABI is a public-surface change: D-60 for any function, field or code beyond design/26, and RFC 0004 for the header's form. So a header change opens with an issue, not a pull request. In order:
1. The contract section (and `status-codes.toml`, for a code) gains the declaration, through its RFC or protected-change item. A new header also needs its `[[c_header]]` row in `surfaces.toml`, a protected change. A contributor who reaches `HDR-3` opens an issue asking for that change and stops there; only the chief architect's item edits those files.
2. The Rust items change.
3. The descriptor changes. Until it does, D1 to D4 stop the build, and D11 stops the link.
4. Bless with `RUSTFLAGS="--cfg grdr_bless" GRDR_BLESS_HEADERS=1 cargo test --locked -p <crate> --test header_drift`, which fails by design. The cfg leaves out the library's stale checks, so a struct that changed can still build. Then run `cargo test --locked -p <crate> --test header_drift` again, without either variable, which passes only if steps 1 to 3 agree. In PowerShell set the variables with `$env:RUSTFLAGS = "--cfg grdr_bless"` and `$env:GRDR_BLESS_HEADERS = "1"`, and in cmd with `set RUSTFLAGS=--cfg grdr_bless` and `set GRDR_BLESS_HEADERS=1`; clear both afterwards.

The descriptors of `grdr_fastpath.h` and of `grdr.h` are on trust-core paths. Every change to those headers therefore takes `eval-security`, `eval-adversarial` and two passing evaluators on different models (D-63).

What holds the contract and the header list against the writer of a code change, after ADR-0035:
- review: `team/06` section 2.1 lists both as protected, every evaluator fails a diff outside its issue's write set, and a protected change lands only after `eval-security` and an evaluator on the other model pass;
- CI: #1668's write-set job, once it lands;
- tiers: `spec/**` is high tier, and `surfaces.toml` is a trust-core path (ADR-0020);
- `rfc-required` (#1741), pending while #1741 is open.

This section, the check table of section 5 and the bless command in its three shells become `crates/grdr-cabi-testkit/AGENTS.md`. The testkit item's acceptance compares that table with section 5's word for word, so the two cannot drift. Each FFI crate's `AGENTS.md` points to it from "How to test". `docs/product/embed/` gains one page for embedders: vendoring the header and layout source, the version rule of section 9, and what may be stripped (section 11). An agent reads the crate `AGENTS.md` at the start of every run that touches the crate.

The same section also states the packing rule, as one more sentence of its carried text: "The header declares its structs between `#pragma pack(push, 8)` and `#pragma pack(pop)`, so a host that compiles with a smaller packing still gets the layout of this section."

Sections 2.1 to 2.3 also gain, in each field's comment after its offset, the field's data class and encoding in the header's spelling, such as `/* 88 [identifier; network byte order] dest_kind 2 and 3 */`. They take the classes and encodings the sketch's descriptor gives as the proposal. `HDR-3` then holds the descriptor to them, so the contract is their one source. ### 10. What the check does not cover
- **A hostile writer of the descriptor, the crate's sources or its manifest.** The drift test runs code that writer controls, and its records are that writer's statement. It can be made to pass while the header is wrong; round 3 of eval-security and eval-adversarial showed several ways. The controls are those of section 0:
  - trust-core review with the evaluators D-63 requires;
  - the export tables of `c-headers` step 4 on the release artefacts;
  - the protection of `surfaces.toml` and the contract.

  The residual risk is an ABI change behind the same exported symbol, such as a parameter's type, made by a writer who also passes that review. It is accepted for an experimental surface (D-60) and is not claimed as closed.
- **Behaviour.** Which status a function returns, and when, is #418's differential and argument tests, and #388's handle-state tests.
- **Compatibility across releases.** Within a major, declarations are only added and input structs only grow trailing fields (D-71; design/03 section 7). #1771 builds that check; section 11 makes it a gate.
- **A run-time version mismatch.** No product program loads a library through these headers. The daemon links `grdr-fastpath` from Rust (design/26 section 2), and the sidecar is a Rust binary. A partner's host applies section 9's rule. If a product program ever loads one, it reports a mismatch as a health condition, never as a tamper finding. It gets a registered code, a runbook, and a `grdr doctor` line naming both versions and the component to upgrade. That program's item adds the code.
- **Signedness of an enum whose values are all non-negative.** D4 catches a wrong signedness only through a negative value. Every value is the same in either type, so C reads it the same.
- **`#[repr(C)]` itself.** A type that crosses in a described signature without `#[repr(C)]` fails the library's build with E0080 when Rust lays it out differently from C, which is the sketch's s12. Where the two layouts happen to agree, `c_fn!`'s foreign declaration trips rustc's `improper_ctypes` lint. It warns by default, so it fails in the clippy gate, under `-D warnings`, not in `cargo test`; the workspace's lint table sets only `unsafe_code`. `HDR-1`, the library's generated asserts and the layout source then hold the layout of every `#[repr(C)]` type.
- **Whether a data class is right.** The contract states each field's class and encoding, and `HDR-3` holds the descriptor to it. The C structs have no proto message that states them, so whether the contract's class is the right one is review of the contract, a protected change.
- **A target or profile the row does not list.** Step 5 checks exactly the row's lists. A build for anything else still compiles the library's own checks, so a layout or signature that differs there fails that build. Only the drift test's own checks (D1 to D4) do not run there before release.

Data classes (P8): the check reads source, interface text, the header list and registry files, all `structural`. It logs nothing at run time and adds no field to any message. The contract and the headers now state each field's class. Nothing compares those classes with the wire types' own; review of the contract holds them (section 10). Assurance effect (P1): none. No action class changes `visibility`, `control`, `on_failure` or `tamper`.

### 11. Stability
- The headers share the class of their C ABI, which their `surfaces.toml` row records: experimental until one external embed pilot completes (D-60). A change to the renderer that changes any header's text is an amendment that names RFC 0004 and regenerates every header in one change.
- A header leaves experimental only once #1771 runs as a release gate. #1771 is also a gate of the first release that ships any header, even though that release has no earlier one to compare with, so the check exists before a second release can break it.
- Before a pilot on a 32-bit target, the `c-headers` job gains that target's compiler leg, and the layout source and `src/<file>_abi.rs` gain its asserts.
- A vendor that ships a header under its own brand may strip the banner and every comment. The declarations are the ABI, and the version constants are the only compatibility signal.
- `grdr-cabi-testkit` is internal. It changes by ordinary items, except where a change alters a rendered header, which is an amendment as above.

## Alternatives
Each alternative below was checked against what shipping projects do:
- rustls-ffi installs cbindgen as a tool pinned to 0.29.4 in its `ensure-header-updated` job, regenerates the header and runs `git diff --exit-code`. Its workflow says the pin exists because point releases can change the output (https://raw.githubusercontent.com/rustls/rustls-ffi/main/.github/workflows/test.yaml, read 2026-11-20).
- safer_ffi generates headers from a registry inside the library, behind a `headers` feature and a dedicated binary (https://raw.githubusercontent.com/getditto/safer_ffi/master/README.md, read 2026-11-20).
- `offset_of!` has been stable since Rust 1.77 (https://doc.rust-lang.org/core/mem/macro.offset_of.html, read 2026-11-20).

The options:
- **(a) A hand-written header, and a test that parses it and the crate's `extern "C"` items.** It needs two parsers: a C subset, and Rust source, which takes `syn` (a new dependency) or a hand-written one. A source parser does not see through `pub use`, type aliases or types defined in `grdr-fastpath` (#405), and it checks no layout. Rejected.
- **(b1) cbindgen as a dev-dependency.** Under ADR-0032 (#1686, proposed), a test-time dependency is a development tool, so the licence may not bar it. It still adds cbindgen's ten required direct dependencies, among them `syn`, `serde`, `toml` and `tempfile`, to the dev graph of a trust-core crate. It reads source, and it checks neither rustc's layout nor `c-abi.md`. Rejected.
- **(b2) cbindgen in `build.rs`.** It breaks the fast-path closure. Rejected.
- **(b3) cbindgen as a pinned tool in `build-tools.toml`, run by a CI step, as rustls-ffi does.** Allowed by the licence and the closure, but:
  - the check leaves `cargo test --workspace`;
  - each session needs cbindgen to regenerate;
  - the types in `grdr-fastpath` need `parse_deps`;
  - it checks neither rustc's layout nor `c-abi.md`;
  - each bump can churn three headers.

  It is the fallback if the testkit proves too costly to keep.
- **(b4) An `xtask` tool.** ADR-0029 removed `xtask`. Rejected.
- **(d) The header as the source, with Rust generated from it by bindgen.** It needs libclang on every host and makes the Rust side generated code inside the trust core. Rejected.
- **(e) A registry in the library, as safer_ffi has.** It ships the descriptor in the artefact or needs a Cargo feature. Rejected.
- **(f) A proc-macro attribute on each export.** It needs `syn` and `quote`. Rejected.
- **(g) A hand-written header with only C static asserts.** It checks layout, but not signatures, because linking checks names only. Kept as the `c-headers` job beside the drift test, not instead of it.
- **(h) A copy of the renderer in each crate's test.** Three copies, and the shared status block could drift. Rejected for one testkit.
- **(i) The testkit as a public layer 1 crate (revision 1).** Design/03's `tool` layer already covers a dev-only crate. Rejected.
- **(j) A C compile inside `cargo test`, driven by `CC`.** Every contributor's `cargo test --workspace` would then need a configured C compiler. Rejected for the `c-headers` job.
- **(k) Explicit padding fields, so no offset depends on the target (seat 5).** Section 2.1 of #246 leaves implicit padding after `dest_port`, and pointers differ between 32- and 64-bit targets in any case. Declined: alignment comes from rustc, and a 32-bit target gets its own compiler leg before a pilot.
- **(l) Fewer per-field docs, taken from `c-abi.md` (seat 8).** The header keeps each field's data class and encoding, which an embedder reads there; the contract now states them too, as their one source (section 9). Declined; offsets left the header instead.
- **(m) A system list of the `c-headers` job's own (revision 2).** It would be a second planner beside `plan`. Rejected.
- **(n) A Rust enum in a parameter, read with a validity check.** The value is already undefined behaviour before the check runs. Rejected for D9.
- **(o) A line-based scan of `src/lib.rs` for exports (revisions 1 to 3).** It was broken by macro bodies, attribute forms, rustfmt skips, decoys and manifest keys, and each patch invited the next bypass. Rejected for D11 and the export tables of `c-headers` step 4.
- **(p) rustdoc JSON or rustc metadata as the compiler's view of the exports.** rustdoc JSON needs `-Z unstable-options`, which the pinned stable toolchain refuses, and rustc's metadata format is not stable. The linker's resolution of the declared C name (D11) and `llvm-nm` on the built artefacts give the same facts on the stable toolchain. Rejected.
- **(q) A sealed `CType` trait.** The type macros expand in the describing crate, so any trait they can implement there, a hand-written impl can too. Rejected for D6, which verifies every node against accident; against a hostile writer, see section 0.
- **(s) A drift test that defends against a hostile descriptor writer (revisions 3 and 4).** Three review rounds showed that the test runs code its writer controls, so each closed route opened another. Withdrawn by the owner's decision to narrow the promise. Section 0 names the controls that do not run the writer's code.
- **(r) The contract named by the descriptor (revisions 1 to 3).** The descriptor could point at a copy (eval-adversarial C1). Rejected for the header list in `surfaces.toml`.

## Drawbacks
- The descriptor is a third statement of each signature beside the Rust and the header. The compiler and the linker hold it to the Rust, but each change edits it. Changing one exported function takes three hand edits (contract, Rust, descriptor) and a bless.
- `HDR-3` ties the test to the form of the contract document: a heading that names the header in backticks, `c` code blocks, offsets as the first number of a field comment, and a data-class bracket in every field comment. A reshuffle fails closed, and the cost lands on the chief architect's protected file.
- D6 needs every boundary type to be `'static`, which every C ABI type is.
- D11 adds one never-called foreign declaration per export to the FFI crates' drift tests, under their reasoned `unsafe` allowance.
- One more crate, one more CI job with five steps, a C compiler on each hosted runner, a `cargo check` per shipped target and profile, and three `surfaces.toml` rows.
- A third generated file per header, `src/<file>_abi.rs`, which also means a bless sets `RUSTFLAGS` and so rebuilds the crate's dependencies once.
- The FFI libraries do not build for a 32-bit target until that target has its checks (section 11).
- The drift test reads files outside its crate (`spec/`, `surfaces.toml`). A crate that is ever published lists `tests/header_drift.rs` in `package.exclude`.
- The status block carries each code's English `meaning` as a comment. A reword regenerates both C ABI headers.

## Decision
Accepted by the chief architect under D-61, on revision 6. The review ran four rounds with `eval-architecture`, the persona council, `eval-diff`, `eval-acceptance`, `eval-security` and `eval-adversarial`. The session that holds the owner's delegation ruled that round 4's findings are folded in without a further round.

Reasons:
1. **It answers #474 inside the spine.** The header is generated and diffed in CI, as design/26 EM-2 and design/03 section 7 say. No third-party dependency, licence change, public crate or same-layer edge is added (D-02, D-61). The fast-path closure stays `grdr-fastpath` and `grdr-fastpath-ffi` (design/26 section 2).
2. **It catches accidental drift: of layout and signatures in every build of the library, and of the rest in the test builds and on the listed targets.**
   - The compiler and the linker hold the descriptor to the Rust items (D1 to D4, D11).
   - The testkit holds the header to the descriptor, the listed contract and the registry (`HDR-1` to `HDR-5`).
   - The library compiles its own layout and signature checks in every profile, feature set and target, the embedded profile included.
   - `c-headers` runs both test builds, a negative control, a C and C++ compile under an embedder's packing, the release export tables, and the shipped profiles and targets.

   Every accidental drift the four rounds and the sketch found fails one of these, by the rules above; section 12 lists which the sketch ran. Among them: C1 and C2 in the `--release` builds, P1 in the embedded build, T1 on aarch64 Linux, and N1 through the control.
3. **What differs between headers is content (P14).** Status block, version scheme, SPDX identifier and contract location are data: descriptor fields and `surfaces.toml` rows. A second header with a different status type passes the same code. The shipped profiles, features and targets are the rows' data.
4. **The promise is the one the mechanism can keep.** The drift test runs code its writer controls, so it cannot defend against a hostile writer, and section 0 says so. That threat is held by named controls that do not run that writer's code:
   - trust-core and high-tier review of every descriptor, source and generated file;
   - the export tables of the release artefacts (#1784);
   - review and CI over the protected oracles (ADR-0035).

   The residual risk is stated in section 10, not claimed away.
5. **The costs are stated and accepted** (Drawbacks):
   - a third statement of each signature;
   - three generated files per header;
   - a textual early warning;
   - one CI job of five steps across targets.

   cbindgen as a pinned tool, Alternative (b3), stays the fallback.

What follows from this decision:
- ADR-0034 (#1776) records it.
- #1778, #1779, #1780 and #1784 carry its mechanisms, with the round 3 and round 4 seeds as must-fail cases in their acceptance.
- #1817 adds the header list, and #1777 the tiers and owner.

A comment after this decision that shows a defect opens a new RFC; there is no waiting period (owner instruction 7). No later reason may claim that a check defeats a hostile writer of the descriptor.
