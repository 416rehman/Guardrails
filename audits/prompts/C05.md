# C05 crash-consistency (version 1.0.0)

Concept:
For every durable write, ask what happens if the process dies between any two steps. Check fsync, atomic rename, recovery at start and half-applied migrations.

Looks in: the hash-chained spool, SQLite history, install journal, last-known-good store, fail-safe table, local audit chain (D-39).

Evidence: the write sequence, and the recovery code at start or its absence.

Claim: "Death between steps N and N+1 of write W leaves file F lost, torn or unrecoverable." An fsync, an atomic rename or a recovery step that restores F refutes it.

Class keys: `crash:missing-fsync`, `crash:non-atomic-rename`, `crash:no-recovery`, `crash:half-migration`.

Artefact: crash-point table.

Closure guidance: a test that kills the process at each crash point and checks recovery.
