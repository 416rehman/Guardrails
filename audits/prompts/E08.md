# E08 hard-coded-behaviour (version 1.0.0)

Concept:
Find behaviour and values in {scope} that are written into code where a mechanism or a data source should carry them. Behaviour: a vendor, agent, model, integration or product named in code to choose what happens; a rule, detection or policy decision written as code instead of a pack or manifest; a threshold, bound, timeout, retry budget or schedule held as a literal or a named constant; a branch on one customer, organisation, tenant, deployment or host; a workflow, approval path or UI flow fixed in code where a registry or setting would carry it. Values: a URL, host, domain, port, IP or email address, a product, company or brand name, a platform path, a colour or spacing value, or a person-facing string, in non-test code outside `brand/`, the configuration schema and the data files. For each, name the mechanism or data source it belongs in: a port with adapters, a signed pack, a manifest, a configuration key with its default in the schema, `brand/brand.toml`, `limits.toml`, the design tokens or a language token in `interface/strings/` (D-69). List the extension points you found already carrying such behaviour as data, so coverage is visible. Do not report test code, fixtures, generated code, or a value the structure check S7 already reports on the same line.

Looks in: layers 1 to 4, `xtask`, the web packages and the desktop and tray programs. The shapes: string compares and `match` arms on vendor, agent or product names; tables of vendors or agents compiled in; numeric literals and constants passed as durations, capacities, limits, retries or scores; `if` on an organisation, tenant or host identifier; host names, URLs and addresses assembled from parts; defaults chosen in code instead of the schema.

Evidence: the line that holds the behaviour or value, the call site that acts on it, and the mechanism or data source that exists or should exist for it.

Claim: "Behaviour B at item I is hard-coded; it belongs in mechanism M as content C", or "value V at item I is hard-coded; it belongs in data source D under key K". A quoted read of the same behaviour or value from a pack, manifest, adapter, setting or data file refutes it, as does a decision record that names the code as the mechanism's own fixed part.

Class keys: `hard-coded:vendor-or-agent`, `hard-coded:rule-logic`, `hard-coded:threshold`, `hard-coded:per-customer-branch`, `hard-coded:workflow`, `hard-coded:endpoint`, `hard-coded:brand`, `hard-coded:visual-value`, `hard-coded:person-string`, `hard-coded:platform-path`.

Artefact: a list per mechanism of the behaviours and values to move, with the key or content each becomes.

Closure guidance: a type or a decision record. The repair moves the behaviour behind its port, pack, manifest or setting, or the value into its data source, read through a typed accessor, so the next case is content and not code; a decision record that cites the fingerprint closes a result only where the code is the mechanism's own fixed part. A lint rule, an exemption entry or a comment alone never closes it; a true exception to check S7 goes to `quality/hardcoded-exemptions.toml` through a protected change that `eval-architecture` agrees to.
