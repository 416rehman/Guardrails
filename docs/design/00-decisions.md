## 1. What we are building

Guardrails ADR is an open-source agent detection and response (ADR) platform, published by Loonaro; the market calls the category AIDR. It does five jobs:

1. **Discover** every AI agent on endpoints, servers, CI, clusters, browsers and SaaS, including bespoke agents nobody registered, with their MCP servers, skills, plugins, model endpoints and credentials.
2. **Attribute** every action to an agent session and the person or team behind it, with stated evidence, and say "undetermined" when the evidence is not there.
3. **Enforce** policy before an action completes, at whichever control points the host allows, and report honestly how strong each control is.
4. **Protect** identities, secrets and data: brokered short-lived credentials, protected paths, redaction, information-flow rules.
5. **Detect and respond**: detections on the device and across the fleet, session-centred incidents, graded approvals, a scoped kill switch.

Three shapes come from one codebase:

- **Standalone**: one developer, no server, no account, nothing sent anywhere by default.
- **Platform**: sensors plus a server and console; self-hosted from one node to HA and to many cells, air-gapped included, or hosted by Loonaro as a multi-tenant service with a provider tier for MSPs.
- **Embedded**: content, event feeds, the hook broker or the engine inside another vendor's EDR or gateway, up to a rebuilt white-label product.

Not goals: an identity provider, a SIEM, a model-routing or key-management gateway, a model-safety product, a mobile or ChromeOS sensor.

## 2. Principles

| # | Principle | Evidence |
|---|---|---|
| P1 | **Boundary, scoped boundary or request, never blurred.** A boundary is enforced by the OS or a gateway against an uncooperative agent. A scoped boundary holds only for processes that entered it (a sandbox we launched, or an agent's own sandbox we lock and verify, D-21). A request is a cooperative hook or setting. The product reports which one applies, per action class. | Hooks fail open by default and are sold as kernel-level (02, 06, 15, 37; c3) |
| P2 | **Models may only restrict.** No allow, grant, declassification, suppression or clearing of a finding depends on a model. Every label and risk input records its origin (deterministic, heuristic, model). Never model-dependent: egress default-deny, protected paths, agent-config writes, credential brokering, the kill switch, tenant isolation, failure mode. | Adaptive attacks beat every classifier; judges leak through their verdicts (09, 22, 39, h01; c2, c8) |
| P3 | **Claims versus observations.** Harness telemetry (hooks, OTel, transcripts) is a claim; OS and gateway telemetry is observation. A gap is a signal, and a detection once the agent's known housekeeping is subtracted. Kernel-origin and gateway facts outrank user-mode telemetry; no verdict rests only on a spoofable source. | Harness OTel missed 27 executions, 26 of them housekeeping (01); user-mode ETW can be forged (h02; l03) |
| P4 | **Decide locally.** Policy is evaluated on the device or in the gateway from signed, cached bundles. A server outage never stops developers and never fails open silently. | Cloud-per-decision designs time out and fail open (04; l11) |
| P5 | **One core, many hosts.** A pure, deterministic Rust core (events and bundle in, verdicts and findings out) runs in the sensor, the proxy, the server (replay) and other vendors' products. | Replay, simulation, differential testing, embedding (27, 37) |
| P6 | **Ports with two core adapters, three named profiles.** Each external dependency sits behind a trait with at most two release-gating adapters per profile (for endpoint ports, per operating system), selected only through the profiles `embedded`, `ha` and `distributed`. Any other combination fails at start. Community adapters live in a contrib repository, pass a published port test kit and never gate a release. | Multi-store stacks made peers unsupportable to self-host (11, 24; c1, l09) |
| P7 | **Content is signed data.** Fingerprints, parsers, rules, policy packs, mappings and models ship as one signed pack format with one verifier, through rings, validated by the production interpreter in CI. | P12 | **Useful alone, better together.** The product works with no server, beside an incumbent EDR and inside one, and it never takes a slot another product needs exclusively. | Buyers already run CrowdStrike or Defender (27, g05; l02) |
| P13 | **Enforce below the agent.** Every device control point that counts as enforcement blocks from a level the agent's process tree cannot reach or switch off: the kernel, an OS sandbox applied before the agent or command started, or a proxy or MCP broker that the kernel or that sandbox makes the only route; off the device, a gateway counts when the network makes it the only way out. An agent's own sandbox counts as such a sandbox only when our privileged service locks it on through the D-49 channel and the conformance suite proves that agent version applies it; where no sensor checks at exec that each command entered it (macOS below tier 3), `visibility` for those classes stays `claimed`. The hook and the agent's own settings run at the agent's level, so a rule they apply counts as enforced only where an OS control point also checks the effect against floor rules and the hook's expectation (D-13); otherwise it is a request. They carry intent, reasons and approvals. On the device, enforcement holds only in the Protected profile, where our service is privileged and the agent is not; the User profile reports every control as a request (D-48). Where containment is on for an agent, a session outside it is refused credential release by default; inject, which keeps the secret out of the session, still applies except to production credentials (D-21, D-27; 15 section 2). Where no layer below the agent covers a class on a host, the record says `control: request` for that class (P1, P9). | Owner instruction, 2026-11-10; hooks fail open and are skipped by any route they do not see (15, 37; 07 section 4) |
| P14 | **Framework over features.** Every capability is a mechanism plus content: a port or trait with adapters, a signed pack, a manifest, a configuration schema or a plugin seam, with the product's own behaviour shipped as default content and configuration on top of it. A behaviour hard-coded where a mechanism would carry it (a vendor, agent, rule, threshold, workflow, UI flow, integration or policy written into code instead of into a pack, manifest, adapter or setting) is a design defect. Defaults are opinions expressed as data and can be replaced without a code change. Nothing is hard-coded: compiled code reads every domain, host, URL, port, address, product or company name, bound, timeout, threshold, visual value and user-visible string from one of five data sources (the `grdr.config` schema and its defaults, the brand manifest, `limits.toml`, the design tokens and the language tokens of D-69), and the figures in this plan are defaults held there. P5, P6, P7 and the extension points of section 5 and `design/03` are instances of this rule; it applies to everything else, the agent kit included (roles, hooks, gates, lanes and routines live in `.agents/` data, not in code). | Owner instructions, 2026-11-11; a self-hosted, white-label or OEM build must change any of these without a code change (D-41 L6, D-66) |
| P15 | **Designed for ten million endpoints.** Every decision is made for 10 million endpoints: the hosted fleet across all its cells and the largest single self-hosted installation. Each design states its arithmetic there (requests a second at steady state and at the worst burst, connections, bytes a day each way, storage per retention class, fan-out, key-service and object-store calls) and uses these mechanisms or records why not: (1) no synchronised timer or reaction: periodic and reactive work runs at a per-device or per-organisation phase plus jitter, on a schedule the server directs as data; (2) retries use full-jitter exponential backoff, treat retry-after as a floor and spend a retry budget; (3) admission control sheds by priority, lowest first, and never sheds commands or `decision`; (4) anything sent to many devices is content-addressed and immutable, cacheable behind any CDN, cache or mirror, invalidated by revision, offered as a verified delta and admitted at a paced per-device time; (5) every byte path is compressed and carries only what the receiver cannot derive, with a trained dictionary where a measurement shows it pays; (6) writes and sends are batched and coalesced; (7) load is partitioned into cells and, below the organisation, into device shards, and no per-request path calls a key service or a third party; (8) a read over more than one device comes from precomputed roll-ups or mergeable sketches. Defaults cost nothing at ten endpoints and need no paid service. | Owner instruction, 2026-11-11. As drafted, the plan reaches about 2.7 Tbit/s when hosted ring 3 opens, 60,000 TLS handshakes in one second per cell after a balancer restart, up to 2 million fleet-key signatures a second and about 117 PB of storage at 100,000 events a day (estimates, scale reviews of 2026-11-11) |
| P16 | **Air-gapped is a first-class deployment.** Every shape (standalone, and self-hosted `embedded`, `ha` and `distributed`) installs, enrols, updates, detects, responds, is upgraded, backed up, supported and audited inside a network with no route to the internet. No capability may require the internet: what needs a service outside the network has an equivalent inside it (a site mirror or any static file server, an on-premises IdP, KMS or HSM, SMTP relay, time source, model runtime, witness), or is reported `requires internet`, never as a gap or a failure (P9). Every external endpoint is configuration behind a port with no compiled default (P14), and a public origin or CDN (P15) is one optional value beside internal mirrors and static file servers. Inputs cross the boundary only as signed artefacts carried by removable media or a one-way transfer and verified offline against the project root; outputs cross only as files a person previews and carries out. In isolated mode no product process dials outside the operator's allow-list or resolves an outside name. There is no licence key, activation, entitlement check, trial expiry or phone-home. Staleness is shown, never enforced: expired update metadata marks a device Stale and enforcement continues (D-37), the deployment's freshness statements cover only metadata expiry, and every pack, snapshot, lookup and finding derived from content states its data age, which nothing resets. | Owner instruction, 2026-11-11; regulated, classified and industrial enterprise networks have no route out (24 section 7, D-59) |
| P17 | **Consistency and cohesion: one way to do each thing, everywhere.** Each concern has one source and one mechanism, and everything else is generated from it or reads it: one interface system (`interface/`: the DTCG tokens, the pattern, presentation, icon, route, notification, shortcut and CLI registries, and the language tokens of D-69) for every surface a person or an agent reads; one vocabulary (section 3, `schema/vocabulary.toml`); one registry per artefact kind (error and health codes, configuration keys, commands, ids, limits, retry policies). A surface composes registered patterns through its renderer's kit (`@grdr/kit`, the desktop kit, the terminal kit `term`, the notification kit) and nothing else: no inline style, raw visual value, hand-written string, hand-rendered enum, hand-built confirmation or one-off component. The same object has the same name, icon, words, states and confirmation on every surface; a surface may show less, never rename or restyle. Reuse before writing: search the registries and shared crates first; code, types and text used in two places exist once, and a second copy is a defect unless `architecture.toml` records the pair as deliberately independent (reference models, the `no_std` fast path, kernel programs). A new need adds an entry to the mechanism (P14), never a local exception. Every rule has a lint, gate or post-edit check whose message names the fix (interface checks UX1 to UX8, ARCH-017 to ARCH-024, ARCH-101 to ARCH-106, V26, V27), the `grdr-interface` skill teaches the interface half and `grdr-scaffold` makes the registry path the shortest one. Breaking it costs familiarity, and familiarity is what lets a person act on a security prompt without hesitating: two words for one thing, or one icon for two meanings, is a defect of the same class as a wrong label on a verdict. | Owner instruction, 2026-11-11; drift found on review: CLI exit codes 3 and 4 with opposite meanings (23, 28), `eye` for both Watch and AL1 (27), the device's main screen called Home and Now (27, 28), two notification-class tables (18, 28), one explanation as `grdr why` and `grdr receipts show` (28, 34) |

## 3. Vocabulary

One vocabulary for code, API, interface and documents. Do not coin synonyms. `schema/vocabulary.toml` is this section as data (term, definition, *surface* or advanced, display casing, plural, `translate`, rejected synonyms); it generates the `term.*` language tokens, Vale's accept and reject lists (34 F6), the identifier lint and the terminology audit (team/04 F06), and each locale's approved form sits with the other translations (D-69). On interfaces and in product docs, Mode values, assurance level names, profile names and product names are capitalised; every other term is a common noun in sentence case. Terms in code font are identifiers: they never change and are never translated; where one is also shown to people (a Mode, a verdict, an assurance level), its label comes from the presentation registry and is translated (D-69). Terms marked *surface* appear in the simple interface; the rest are for advanced views, API and export.

**Tenancy.** *Operator*: whoever runs the server, administering it through the separate *operator plane* (D-70). *Provider*: manages organisations under delegation (an MSP); it may have one parent provider (a distributor or OEM) with provisioning and billing rights only. *Organisation*: the hard isolation boundary (keys, storage prefix, region, quotas). *Organisation set*: a provider-side grouping of organisations, the unit for baselines, rollout rings, queues and reports. Below the organisation: group, device, agent instance, session. Standalone uses one random organisation id generated at install.

**Agents.** *Agent* (surface): an agent type in the catalogue, or a bespoke one identified by its program identity (signing identity, else package or image name, else source remote and entry point, else path). *Agent instance*: that agent for a principal on a device or workload. *Session* (surface): one run, with child sessions for sub-agents. *Principal*: a human, service account or agent identity; humans appear as pseudonyms. *Sponsor*: the accountable person or team for an instance.

**Activity.** *Control point*: `hook`, `mcp-broker`, `proxy`, `sandbox`, `sensor` on the device, plus `browser`, `gateway`, `connector`. *Action* (surface): a normalised attempt in one class: `exec`, `file.read`, `file.write`, `file.delete`, `net.connect`, `net.request`, `llm.request`, `mcp.connect`, `mcp.call`, `cred.use`, `agent.spawn`, `config.change`, `elevate`, `ui.act`, `data.flow`. *Event*: an immutable observation. *Fact*: a typed value from an analyser. *Label*: session state that policy reads; *enforcing* labels are written synchronously by deterministic session rules, *advisory* labels by anything else.

**Decisions.** *Verdict*: `ALLOW`, `DENY`, `MODIFY`, `STEP_UP`, `DEFER`, plus obligations. *Mode* (surface): `Off`, `Watch`, `Ask`, `Block`. *Pack* (surface) and *Rule* (surface): signed content and its entries. *Approval* and *Exception* (surface) are what people see; the API noun is *Grant*: signed, expiring, bound to rule ids and an action digest or pattern. *Receipt*: the signed record of one decision.

**Outcomes.** *Finding* (surface): a detection result with a class (threat, policy violation, overeager, tamper, coverage gap), two ratings (behaviour severity, content sensitivity) and a lifecycle. *Incident*: findings grouped by session lineage, then merged across device, principal, credential and artefact digest. There is no separate case object; incidents sync with ticketing.

**Graded scales.**

- *Assurance record*, per device, agent instance and action class: `visibility` (none, claimed, observed, cross-checked), `control` (none, request, scoped-boundary, mandatory-boundary), `on_failure` (open, closed), `tamper` (user, admin, platform). Policy reads the record.
- *Assurance level* (surface), a label computed from the record by a published function: AL0 Inventoried, AL1 Observed, AL2 Guided (requests proven to fire), AL3 Contained (scoped boundary), AL4 Enforced (mandatory boundary, cross-checked). Policy never reads the label.
- *Attribution grade* 0 to 4 from a fixed table over an evidence set (4: separate OS principal or session-bound credential; 3: exclusive session container or exec-time tag; 2: a claim matched to an observation; 1: single source; 0: inferred). `actor_kind` is agent, human, undetermined or system.
- *Approval grade*: G0 same-user click in `grdr-approve` or a command run outside any agent session (a request); G1 OS authenticator over the action digest; G2 privileged helper on a secure surface or separate principal; G3 out-of-band device. Only G2 and G3 are called unforgeable. The agent's own permission prompt is not an approval at any grade; it may only point the person to `grdr-approve`.
- *Capture level*: `metadata` (structure and derived facts), `redacted arguments`, `redacted content`, `full content`.

**Names.** The product is Guardrails ADR, published by Loonaro. Its names, domain and addresses are values in the brand manifest (`brand/brand.toml`), and no code or configuration default outside `brand/` holds them (D-66). The command `guardrails` belongs to another project and `grd` is taken on crates.io, npm and PyPI, so the working technical namespace is `grdr` (free on crates.io, npm, PyPI, Homebrew, Docker Hub and Debian at the last check): CLI `grdr`, binaries `grdr-*`, crate prefix `grdr-`, protobuf packages `grdr.*`, Cedar namespace `Grdr`, environment prefix `GRDR_`. No wire or ABI identifier contains the company name. See D-66.

## 4. Decisions

### Product, licence and project

**D-01. Three shapes from one codebase.** Standalone is a mode of the one daemon and a real product. *Why:* rivals' free tiers observe only; open hook guards have no console (01, 08, h04).

**D-02. Apache-2.0 for all code, no CLA, no DCO sign-off.** The server too. eBPF kernel programs are `GPL-2.0-only OR BSD-2-Clause` in their own crate. Content is Apache-2.0 with no attribution duty. Docs are `Apache-2.0 OR CC-BY-4.0`. One root licence file, SPDX headers, a do-not-read list for copyleft and source-available code. *Why:* the only choice EDR vendors can embed and foundations accept (28, 10, 27; c6 confirmed). *Rejected:* AGPL server, open core. *Revisit:* never after the first public release; hold one go or no-go review of the server licence before it, informed by whether anyone commits to pay for hosting, support or an embed pilot.

**D-03. Neutral ownership on a stated trigger.** A covenant is published as an early work item, not as a condition of the repository being public, which it is from its first push (owner instruction 28): OSI licences forever; binaries under the source licence; reproducible releases; and transfer of the project's marks, domain, repositories (under the owner's GitHub profile until then), update root keys, default update and intelligence endpoints, conformance registry and held-out corpora to a neutral foundation on the earlier of (a) two unaffiliated production adopters plus one external committing organisation, or (b) 18 months after first public release. The foundation is chosen after pre-read meetings (question 5): CNCF Sandbox first (Cedar, Falco, Tetragon, agent sandboxes are there), then OpenSSF; AAIF only once it has accepted a security project (h05; c6, l09). We contribute hook-standard conformance evidence to OWASP regardless.

**D-04. Revenue without withheld features.** Paid: hosting at a published price; support; maintenance of LTS lines beyond the public window; OEM services (integration engineering, private conformance runs, warranty, a tailored compliance file); live access to the intelligence service (for a site with no route out, the same signed packs carried in by file; the download, never the product, checks entitlement), whose records all become public after a fixed delay (malicious verdicts and withdrawals are public immediately; the delay applies to enrichment and prevalence). Vulnerability pre-disclosure is free to any redistributor meeting published criteria (c6). Every paid offer requires counsel's opinion first (D-46), and Loonaro makes no paid offer without it; free legal help for open-source projects (foundation legal programmes) is the first route. Paid hosting also requires the hosted service's preconditions in D-63.

**D-65. Where we lead, and what we are not.** We lead where bundled products are absent or weak: unregistered and bespoke agents; hook-against-OS reconciliation; offline local decisions; enforcement for Codex, Cursor and open harnesses; Linux, WSL, containers and CI with kernel enforcement in the open; self-hosting; a fully open multi-tenant console; published efficacy. We ingest from and export policy to OpenShell, DefenseClaw, Numbat and Prempti instead of competing with them. Table stakes we must match: Windows and macOS inventory of agents, MCP servers and extensions; hook verdicts for Claude Code, Cursor and Codex; an MCP control point; Allow, Ask, Block; SaaS connectors; session audit (h03, h04; c6).

**D-66. Names.** Technical identifiers use the neutral namespace in section 3 and every user-visible name comes from one brand manifest, so a rename or a white-label build is mechanical. Agents run and record a search of package registries and trademark databases that fixes the final namespace before the first release; it is a work item, not a condition of the repository being public (owner instruction 28), and a formal clearance opinion is outside the zero budget. *Answered by the owner (question 4, 2026-11-11):* the product is Guardrails ADR (agent detection and response), published by Loonaro, and `grdr` stays the technical namespace; because "Guardrails" is descriptive and used by several AI products, the search result is recorded with the name (c6, l12). `brand/brand.toml` holds the product name, short name, domain and addresses, and Loonaro's distribution sets its `domain` to `guardrailshq.com`; until that domain's DNS exists, the defaults point at GitHub-hosted addresses. A self-hosted or white-label deployment sets its own names and hosts and never depends on Loonaro's domain (P14).

### Core engine and policy

**D-05. Sans-IO core.** The core does no I/O and takes time and randomness as inputs. It builds for native, C ABI and `wasm32`. It exports an interest set per bundle and session (process scope, path, host and port tables a host can compile into its own filters), and each verdict carries a cache key, scope and expiry (l08).

**D-06. The canonical model is our own protobuf.** Envelope: UUIDv7 id; organisation; device; epoch, lane and sequence; trace ids; `principal` (pseudonym and how it was mapped); `actor_chain` (instance, session, child sessions, tool-call id); `actor_kind`; `attribution` (evidence set, grade, advisory score); source and provenance grade; integrity fields. Every field carries a `data_class` option (identifier, structural, derived, content). Packages start at `v1alpha1` and freeze before the server's first release; `buf breaking` gates changes. Lake columns are this model flattened. OCSF 1.9 (with a small extension) is a generated export; OTel GenAI (pinned commit), OpenInference and OpenLLMetry are ingest dialects (23, 26; c1, c4, c5, l07).

**D-07. Verdicts and the approval mechanic.** The verdict set is CSA AARM's five. `STEP_UP` never relies on an agent's own prompt: the control point returns a denial with a retry token, an approval mints a grant, the agent retries. Holding an action open is an optimisation only where the deadline is known and failure is closed, capped at 80% of the control point's timeout (30 seconds on Linux file holds). Each control point declares the verbs it can execute and the engine degrades predictably (06, 34, 36; c2, c7).

**D-08. Cedar is the only enforced authorisation language.** Cedar 4.x with a published, fixed schema (for example `mcp.call` on an `McpTool` resource). Richer outcomes are `forbid ... unless` evidence is present, with annotations as remedy hints. Analysers are engines whose vocabularies are signed pack data: path-pattern sets, host sets, command classes over canonical argv, MCP argument extractors keyed by tool-manifest hash. Their results reach Cedar as sets (`resource.classes`, `context.facts`). Removing a pattern from a protective class is a widening change. Churn in feed-managed, restrict-only lists delivered by signed intelligence packs is not. Dogwood syntax may be accepted as an authoring front end that lowers to Cedar (20, g07; c2). *Revisit:* if evaluation exceeds 1 ms p99 at 1,000 policies including request construction, add slicing by action class.

**D-09. Session rules write enforcing labels; detections write findings.** Two kinds of rule. *Session rules* are small deterministic state machines (match an event or fact, set a label or counter with scope and decay), evaluated synchronously inside the session monitor before the observing control point is acknowledged; only their labels are visible to Ask and Block policies. *Detections* are Sigma-format rules with correlations, evaluated asynchronously on the device and server; they produce findings, a bounded per-session risk integer built from named contributions, and advisory labels that evaluate as absent in Cedar. An eventual label that arrives after a decision it would have changed raises a finding. Receipts record the session-state sequence number so replay is exact. The detection engine is a trait with conformance vectors; `rsigma`'s parser and evaluator crates are one vendored implementation behind it. We publish a log-source taxonomy for agent events and a conversion pipeline for the OCSF export. YARA-X scans content. There is no third expression language: manifests are match tables (20, 09, g06, h05; c2, c8, l03, l10).

**D-10. Normalisers are first-class code with real oracles.** The shell and PowerShell canonicaliser, path resolver and protocol parsers return `resolved`, `unresolved` or `malformed`. Malformed denies. Unresolved is a fact (`exec.opaque`): at a boundary the concrete exec, open or connect is judged by the OS; at request level an opaque command in a fail-closed class steps up. An unrecognised harness version never denies: the adapter drops that agent to Watch and reports it. Oracles are the real consumers (shells under exec tracing, kernel path resolution, each agent's own parser, Cedar's Lean model); each normaliser has a differential fuzz target (09, 21, 32; c2, c5, l06).

**D-11. Policy layers.** The canonical object is a pack: Cedar policies, typed parameters (lists) and a mode. Layers (provider, organisation, group, device, user) each mark settings default or locked. Device and user layers work standalone; the organisation and group layers require the server; the provider layer requires the provider tier (D-35). Ceilings hold by construction: each layer is its own policy set and any layer's deny wins; lists carry a parent maximum checked by set containment. Cedar's symbolic analyser runs on the server and in `grdr policy check` to produce semantic diffs and lints; a timeout counts as widening. Narrowing applies without approval but never without staging: a provider-layer change is a rollout whose ring unit is the organisation. Privacy settings can only be narrowed by provider and operator layers. Three views (Simple edits modes and lists only; Advanced; Code) over one representation, with a GitOps lock. Drafts are replayed against history (matched, almost matched, not matched) before they may leave Watch; replay of rules that read content runs on the device and returns counts (20, 33, g07; c2, l05, l07).

**D-12. Compile down only what is sound.** Only unconditional, locked forbids over path classes, host classes and MCP server identity compile to an agent's native deny settings, plus hardening flags. No command-string rules and no native "ask". Output is a fragment or MDM artefact from code-defined templates, never an overwrite. Each target has a per-agent-version conformance test proving native denials are a subset of what Cedar always denies. Targets: Claude Code managed settings, Codex `requirements.toml`, browser policies, and an incumbent EDR's prevention policy as a boundary-grade option (05, 08, g09; c2, l01, l02).

**D-53. Default content.** An Essentials pack is enforced from first protection: Block for agent-lineage writes to any agent's or our own control files, honeytoken use, bypass or hook-disabling flags, and disabling the product; Ask for reads of credential stores and private keys, for recursive delete outside the workspace, and for elevation from agent lineage (Protected profile). A rule enters Essentials only with zero hits on the benign corpus and zero block-induced task failures. Everything else starts in Watch, except D-21's refusal of credential release to uncontained sessions where containment is on, and after seven days proposes promotion with "this would have asked you N times". The thirty default detections and ten default response actions are those ranked in `c8` from incident evidence (c2, c7, c8, l06).

### Control points and the endpoint

**D-13. Eight control points, cross-checked.** Five on the device (hook, MCP broker, proxy, sandbox, sensor) plus browser, gateway and connector. The device points need no server; the gateway is the proxy in server mode (D-40). The hook evaluates intent and issues an expectation bound to tool-use id and process key; the OS control point evaluates effects against floor rules and that expectation, and honours the same grant. An agent process with no session-start event within a set time is "hook dark", a tamper detection. An unmatched effect is scored against a housekeeping profile shipped per agent version; a version with no profile reports "cross-check not calibrated". SaaS-hosted agents are reached through connectors and never exceed AL1 (02, 06, 08; c3, l03, l12).

**D-14. A hook broker with a shim that can stand alone.** One signed native shim per agent speaks the Claude Code dialect with per-agent translators. It talks to the daemon over a peer-checked socket or pipe and verifies the owner of that endpoint. It carries a fail-safe table that the privileged service compiles on the device from the last-known-good bundle and signs with a device-local artefact key (fail-closed classes as literal patterns, no parsing): if the daemon does not answer in 250 ms, or by the deadline in a valid update-handover marker (never beyond 2 seconds), the shim decides from the table, and it always returns within 2 seconds. Every hook registration sets an explicit timeout. Vendor fail-closed flags are set only in managed installs where the organisation chooses `on-sensor-loss: block`, after an on-device self-test. The broker fans out to registered verdict providers with a deadline and deny-wins merge; providers receive minimised payloads and may return only DENY or STEP_UP; one provider per action class may MODIFY. It speaks OWASP Agent Control Standard (with signature, replay and skew checks) and Microsoft agent-hooks as adapters and publishes its capability claims in the vocabulary of the draft portable hook specification. The broker is a library and a specification, so a host vendor can build and sign its own shim (15, 27, g02, h03, h05; c3, l02, l06, l08).

**D-49. Writing another product's configuration is a release channel.** The installer probes each agent's effective managed source. One owner per agent per device: where MDM or server-managed policy exists we write nothing and render a fragment for that owner; where sources must compose we require merge behaviour. We never edit or drop another vendor's entries. Files are schema-validated, proven by starting the pinned agent in CI, written atomically, journalled so uninstall restores byte for byte, and ringed with halt on agent-start failure (one failure while a ring holds under 1,000 devices; above that, a failure rate above the not-updated cohort's, 22 section 7.3). AL2 is claimed only after a canary proves the hook fired in each session: the session-start event plus the first tool call's hook event matched to an OS observation (we never inject a tool call into the agent's session); "configured, not effective" is a health state and a finding. Adapters declare tested version ranges; a canary job installs each catalogued agent's new release within 24 hours (l02, l04, l06, l08, h03, h08).

**D-48. Install profiles and the standalone contract.** First run changes nothing: a read-only scan with no elevation shows agents found and recent sessions from existing transcripts. Then the user chooses. *Protected* (recommended, one elevation): a minimal privileged service owns policy, keys, spool, shim and managed settings. *User* (no elevation): hooks in user-scope settings, tamper grade `user`, every control reported as a request, no credential broker. Process topology is the same in both; only privilege differs. Standalone sends nothing to anyone by default: the only outbound traffic is anonymous, mirrorable update fetches, which can be turned off; reputation is matched on the device; `grdr egress` lists every destination and CI asserts it, as `grdr server egress` does for the server; `network.mode = "isolated"` holds every product process in every shape to the operator's allow-list (24 section 3). `grdr join` enrols into a server without rewriting history (the local organisation id becomes an alias; back-fill is the user's choice; the user sees capture level, readers and locked rules first); `grdr leave` restores standalone; `grdr uninstall` restores every changed file (l01, l06, c3, c7).

**D-15. Failure mode is policy, per rule class.** Loss-of-sensor behaviour is declared per pack and group; the default is allow with a loud Degraded state, and deny for the fail-closed classes in the shim's table. Fail-closed applies to processes inside session containers. Each adapter publishes the failure mode it can actually achieve per agent version, proven by the conformance suite; where closed is not achievable the class is backed by a boundary or the record says `on_failure: open`. Updates hand the socket over so that update-induced denials are zero (04, 06, 25; c3, l02, l04).

**D-16. No mandatory TLS interception; never fight for the proxy slot.** Network visibility is tiered: connect and SNI rules; content from hooks, native OTel and transcripts; an explicit local listener as the agent's base URL or proxy, which chains to any customer gateway or system proxy and trusts the OS store; opt-in selective interception that never touches browsers or updaters, with a per-device, name-constrained, memory-only CA injected per process tree. The product detects existing interceptors and chains or stands down (01, 02, 38, g05, h08; l01, l02).

**D-17. Windows is driverless by default.** Baseline telemetry is kernel-origin ETW plus PowerShell script-block events, behind our own trait (the common Rust ETW crate is unmaintained). Sysmon is read when present and never installed or configured by us. An AMSI provider is an opt-in outside the baseline. Scoped-boundary control comes from user-mode WFP filters, job objects and restricted tokens or AppContainer for processes that enter by one of four routes: `grdr run`; the agent's process-wrapper setting where it exists; the agent's own sandbox, whose principals we enumerate; a hook rewrite of a shell call into the launcher. The default containment on Windows is tool-subprocess containment, not re-homing the whole agent. Agents that enter by none stay at request level. The sensor detects trusted Dev Drive volumes, where file filters outside the antivirus range are detached, and reports the coverage loss. An optional minimal driver (process-create veto, minifilter on configured paths, WFP redirect) ships on its own release train. It requires an EV certificate and Microsoft's hardware programme (Partner Center, WHCP testing), which cost money and so depend on a sponsor or partner, and trust-core review under D-63. User-mode Windows binaries carry Sigstore signatures and provenance, and Authenticode once a free open-source signing programme (for example SignPath Foundation) signs them; until then they are marked `not platform-signed` and nothing waits for it (D-59). The Windows endpoint security platform shows no user-mode blocking path and is limited to Microsoft's antivirus partners, so it is reached only through an embedding partner; its adapter sits behind the same trait as the driver. x64 and ARM64 (12, g05, h02; c3, l02, l04).

**D-18. macOS in three tiers.** Tier 1: hooks and launch sandboxing with no Apple approval. Tier 2: a Network Extension content filter under a Developer ID, at a grade chosen by the slot broker; no DNS proxy, transparent proxy or VPN configuration by default. Tier 3: Endpoint Security with Apple's entitlement, one system extension with a client per concern and our own tree follower that re-selects the exec target on every exec; full clients never hold for a human. On macOS 27 a launch-scoped supervisor uses the descendants client with a kill-subtree watchdog, synthesises audit records for denied execs and documents the setuid limit. Tiers 1 and 2 report `visibility: claimed` for exec and file. Rust static library, thin Swift shell. Prerequisites: tier 2 requires Apple's Developer Program (a Team ID and Developer ID signing for Loonaro, annual fee, question 8); tier 3 requires the Program and the Endpoint Security entitlement, which can be requested only once the Team ID exists. Without the Program, macOS ships with tier 1 only, Sigstore-signed but not notarised (`not platform-signed`, D-59) (13, h02; c3, l04).

**D-19. Linux is the reference platform for open kernel enforcement.** A probe reads the active LSM list and kernel features before loading anything and selects, in order: BPF LSM; `fmod_ret` or override on security hooks; cgroup BPF network control plus fanotify marks on the protected-path set only; launch sandbox; observe. Each tier states which action classes it can block. Programs and links are pinned and maps locked so enforcement survives loader death; signed programs are used where the kernel supports them. Hooks attach at LSM, VFS and socket layers; launch sandboxes deny io_uring. One cgroup-v2 scope per session-exclusive session. The same sensor serves WSL2, containers, Kubernetes (privileged DaemonSet on runc nodes; unprivileged sidecar, hooks and forced gateway egress elsewhere; a coverage ledger per workload) and an ephemeral CI mode. Observation needs only the sensor; kernel enforcement requires S-12 and leaves the internal ring only after the review D-63 sets for kernel components. The `cgroup_sock` network program is reviewed on its own and does not wait on S-12 (R-40) (14, g04, h02; c3, c9).

**D-20. One process topology, privilege by profile.** A minimal core holds a compiled floor policy and handles fixed-layout events and actuators, so fail-closed classes never wait on anything else. A sandboxed engine process parses all untrusted content and evaluates content-dependent policy. The uplink, the proxy and broker, and a tiny updater are separate. The shim, tray and desktop app are untrusted. Exactly two topologies are tested: user and protected (37; c3, l01, l10).

**D-21. Session containers attribute; containment has three modes.** Every session-exclusive session gets a container, which is attribution only. Containment is chosen per agent from the catalogue: *delegate* (configure and lock the agent's own sandbox and verify it at exec), *wrap-tools* (launch tool subprocesses in ours), *wrap-agent* (the whole agent in ours: for agents with no sandbox of their own, or whose own sandbox S-11 shows still applies inside ours). Containment is opt-in per agent and OS until a developer-workload corpus passes inside it; the launcher probes first and stays at request level with a stated reason. An agent whose own sandbox cannot run on a host falls back to *wrap-tools* where its adapter proves the hook rewrite (10 section 7), and stays at request level only if that also fails. Where containment is on for an agent on an OS and the catalogue makes wrap-agent its mode there, turning on protection in the Protected profile also places a link to our launcher, named after the agent's command, in a directory early on the system `PATH`, and sets the agent's own process-wrapper setting where one exists and the agent honours it on that OS (Claude Code ignores it on Windows, 08 section 5), so starts by command name and, where that setting is honoured, the agent's self-spawns run under `grdr run --contain` with nothing typed differently; both are written through the D-49 channel, user shell profiles are never written (D-27), and a start that misses them (an IDE's bundled copy, an absolute path, a shell profile that puts the agent's directory first) runs uncontained and is reported. A sandbox conformance suite proves every declared boundary on every back end at execution time. Adopting an agent that is already running gives attribution, not containment; the console offers "restart contained", and, where containment is on for that agent and OS, credential release to uncontained sessions is refused by default (P13), which is the enforceable form of "requires containment" on every OS. NVIDIA OpenShell and similar governed runtimes are recognised as a containment back end and a posture fact (08, 13, 14, h01, h04; c3, l04).

**D-22. Self-protection: prevent against user-level agents, detect against administrators.** The prevent goal applies only in the Protected profile. Agent configuration, our own files, and monitoring and alerting configuration are protected system state for agent lineage. Elevation and broker paths (sudo, UAC, container sockets, systemd, launchd, Task Scheduler, WMI, our own launcher) are the `elevate` action class: Ask by default, fail-closed from contained sessions. Agents' local stores (tokens, MCP secrets, transcripts, conversation databases) are protected from non-agent processes. The server detects heartbeat gaps but records its own outages and suppresses gap findings inside them. Kernel-grade tamper resistance comes from a host EDR in embedded mode (21, 22, 37, h07; c3, l01, l11).

**D-23. Coexistence is designed and tested.** A slot broker probes each OS slot and degrades: enforce, observe, or ingest the incumbent's telemetry and delegate response to its API. No exclusive slots, no injection, signed native binaries, no encoded scripts. Each release ships a generated coexistence pack and a ceiling matrix (OS, agent, incumbent: reachable assurance), and passes an interference test against Defender, Falcon and at least one more incumbent before broad release; the licences for incumbents other than Defender require design partners or free vendor programmes (D-64). A targeted build that does only agent discovery and enforcement beside any EDR is a supported configuration (g05, h03, h08; l02).

### Discovery and attribution

**D-24. Discovery is four passes that produce evidence.** (1) *Catalogue*: our own schema with tiers (A: first-party, all routes, nightly install proof; B: imported identifiers; C: community, unproven); other catalogues are import dialects. (2) *Building blocks*: SDKs, frameworks, MCP libraries and model runtimes, scanned only in a process already classed as an LLM client, recording package name and version; no crawl of home directories or repositories. (3) *Behaviour*: `llm-client` when a process talks to an inference endpoint or local runtime; `agent` only with loop evidence. Without plaintext the result is `agent-suspected` (repeated response-then-new-child cycles plus a composition signal) and never drives Ask or Block. Pass 3 on macOS requires the Network Extension (D-18 tier 2). (4) *Declared versus observed*: registries and inventories (local sources, incumbent EDR inventories, registry connectors) diffed against sensors. Unknown agents go to a triage queue keyed by program identity; decisions survive rebuilds, and a changed signer or remote reopens triage. Environment capture is an allow-list of names. A team can declare a bespoke agent with a manifest file or an SDK call (17, 16, g09, h03, h08; c4).

**D-25. Attribution is a session graph that admits doubt.** A session container exists only where the root process is session-exclusive (a CLI agent, `grdr run`, a process wrapper). For agents inside shared hosts such as IDEs, the container proves only "inside an agent-capable host"; per-action attribution needs a per-call binding (hook match on tool-use id, command and working directory, or an exec-time tag), and everything else is `undetermined`, which each rule class must handle. Session identity is assigned by the sensor, and labels, grants and denial ledgers inherit to children and cannot be reset by the harness. Lineage is a graph with fork and exec edges, IPC edges (XPC, COM, D-Bus, launchd) and artefact edges; brokered hops are lower-grade edges; file-mediated execution is "influenced by" (17, g09, h02; c4, l01).

**D-26. Outward identity in three grades.** `tag`: unsigned markers, for search only. `receipt`: a sensor-signed record in our audit log keyed by the external object id. `credential`: a distinct upstream principal or session name minted by the broker; only this is claimed to separate agent from human in third-party logs. Outward tags carry the session pseudonym. Git attribution is a signed note, off by default, never pushed outside an allow-list (17, 35; c4, l07).

### Identity, secrets and data

**D-27. Broker identities; do not build an IdP.** Identifiers are SPIFFE-style with an `identity_proof` field (observed, self-asserted, IdP-issued, attested). The trust domain is the organisation, named by an opaque id; standalone ids stay `observed`. A token service with no users or directory is trusted only by our own gateway, broker and customer-federated relying parties. Model credentials have one mode per agent instance, chosen by the policy compiler: `vendor-login` (default), `gateway`, `key-helper` or `federated`. Tool credentials are bound per session through the launch environment or the agent's managed environment block; user dotfiles are never rewritten. The broker has two modes: *inject* (the secret never enters the session) and *release* (helper protocols; at most 15 minutes, reduced scope, session labelled `secret-read`). It verifies callers by kernel handle, executable identity and request scope; a phantom token counts only with a matching kernel peer. Leases stay on the device or a customer-run gateway. Delegation is the intersection of the human's rights and an agent ceiling, narrowing per hop, with RFC 8693 `act` chains. The decision point is exposed through AuthZEN 1.0; containment emits CAEP events. Prerequisites: observed ids and credential inventory need only the sensor; launcher-bound helpers require the launcher (`grdr run`) and the Protected profile; the token service requires the server's `identity` and `keys` targets; minted cloud and forge credentials require the token service; ID-JAG and registry correlation require the token service and registry connectors (07, 18, 19; c4, l01).

**D-28. Data protection in order of value.** Protected paths and environment scrubbing; an irreversibility gate (action class by target class, with production identified by credential or tag); secret handling declared per agent and channel as rewrite, deny-read or none; session labels with sink gating; egress rules with method, path and tenant pinning; injected credentials; honeytokens; a workspace baseline at session start with copy-on-first-write and a mass-change breaker; classification connectors; provider posture. Default labels: `secret-read`, `sensitive:<class>`, `untrusted:web`, `untrusted:external-tool`, `injection-suspected` (model origin). Default sinks: requests outside the session's egress profile, pushes outside the organisation, package publishing, message sending, calls to unpinned write-capable MCP tools, model requests to a non-tenant provider. `secret-read` to a sink is Block. Sink gating leaves Watch only after replay shows it inside the prompt budget. MCP tool results are labelled by source trust; telemetry-class connectors are untrusted (35, 05, 22, h01, h07; c8).

**D-51. Privacy by schema.** Pseudonymisation has two layers: the sensor derives a device-side keyed pseudonym (so standalone works offline), and in platform deployments the server re-pseudonymises at ingest with a key the device never holds, so a local administrator can link only their own device's records. The mapping lives in an identity vault under the organisation's key. Re-identification needs a purpose, an incident reference and two approvers, and is shown to the subject. Default upload is `metadata`; `redacted arguments` stay on the device and travel only as evidence spans attached to findings or under a content grant; an organisation may raise the level, visibly. The pack validator rejects grouping by principal; baselines key on agent type, project and peer group; prompt and approval health is reported per rule and per group of five or more. There is no covert mode, the disclosure surface cannot be hidden in any shape, and conformance marks require this floor. The sensor installs no input hooks and records no keystroke timing, screen or clipboard content. History from before enrolment stays local. Organisations can exclude principals, paths and repositories. The operator uses tenant data only to run the service. Retention defaults: content 30 days, structural events 184 days (the EU AI Act's six-month floor for deployer logs), receipts 13 months (34, 33, h08; l07, c7).

### Detection, response and AI

**D-29. Detection tiers.** Tier 0 is deterministic: session rules, detections, tripwires, config-integrity monitors. It is the only tier on by default. One review stage sits above it (a finder plus a verifier whose evidence spans are checked by string match), ordered by a deterministic priority score with a random sample and seeded recall canaries. Further model tiers are small local models, a learned ranker and a read-only investigator; all of them require the judge back-end trait. Model tiers are off until the organisation selects a judge back end and a capture level that permits it; the hosted service has no default third-party model. The token payer is an organisation setting (customer key, capped platform key, local model); when the budget is spent, model tiers stop and the console says "review skipped". Trusted input to a judge is policy only; everything else is framed as untrusted; output fills typed fields and free text is rendered inert; judges have no egress; verdict codes only, rate-limited, with probing detected (39, 09, h01; c8, l01, l07, l11).

**D-30. Response: one signed action contract, graded automation.** Each actuator declares, per OS and assurance, which actions it can execute and its fallback; the console shows the effective action before confirmation. Session-level actions: deny with reason and alternative; hold for grant; freeze; end session with an expiring restart block; cut session egress; quarantine a config artefact; disable an MCP server, tool or skill by digest; revoke brokered leases; capture evidence; restore files. Rules may automatically deny, hold, end a session and disable by digest with a time limit; wider actions need a person unless opted in per rule, and every automated rule declares a blast-radius cap and runs in simulate first. The kill switch has scopes from session to provider and four actuators (process, network, inference route at the gateway, provider admin API). Commands above device scope carry signatures from approvers' own hardware-backed keys, verified on the endpoint against a roster changed only by a quorum of the previous roster. One approver may issue a reversible 60-minute freeze; kill, revoke or extension at organisation scope or wider needs two. Devices rate-limit destructive commands and apply pending ones before the next tool call when they reconnect. Order: freeze, isolate, capture, revoke (36, 21, h06, h07; c8, l01, l03, l05).

**D-31. Approvals are graded; anything that widens needs proof of a person.** Every grant records its approval grade, and each rule class sets a minimum. Where the minimum is unavailable, Ask becomes Block; the one exception is the user's own local policy in the User profile, where a disclosed time lock (default 10 minutes) may stand in for G1. An approver is self, sponsor, admin or quorum per rule. A grant is exact and single-use by default; its digest covers canonical argv, working directory, environment delta and content hashes of referenced executables and scripts, re-checked at execution; a label escalation voids it. Three unanswered or denied requests in a row freeze the session. Every widening operation in any shape (mode down, pause, exception, removal of a pack or the sensor, capture level up, provider or exclusion registration, kill-switch release, turning off containment or its automatic start for an agent) is a step-up at that class's minimum grade; the command line, tray, desktop app, deep links, local console and MCP server may only propose, and refuse mutating calls from inside an agent session. Devices enforce that operator-signed artefacts can only narrow; widening needs the organisation's own signature in hosted and provider deployments. The approval helper uses OS-native surfaces only (33, 36, 29; c2, c7, c8, l01, l06).

**D-32. Threat intelligence is digest-keyed and careful.** A mirrored pack of OpenSSF malicious-packages, GHSA and KEV is matched on the device and needs no server. The MCP broker pins tool definitions locally regardless. Own scanning: a reputation service (requires the server's `intel` target; prevalence requires data from many organisations) keyed by content digest and tool-manifest hash, publishing named findings with scanner and evidence as OSV records, "malicious" only with two independent sources or a published human review by a reviewer outside the project (the project has no human reviewer, owner instruction 7), a dispute route, sightings as prevalence above a k-tenant threshold, and verdicts on high-prevalence artefacts through rings. Scanner verdicts on skills are a risk signal only; provenance (digest pinning, signatures, drift detection) is the control (g06, h01, h05; c8).

**D-54. Findings lifecycle, hunting and export.** Findings use OCSF finding states. A suppression is a scoped, owned object with justification and mandatory expiry that hides a finding and never changes policy. Rules expose declared tunables; tenant overrides survive pack updates. Blocked attempts always create findings. Only threat and tamper findings page. Hunting is SQL, a pipe-style front end and Sigma rules run as hunts; an observable index built at ingest maps values (executable hash, destination, MCP server digest, tool-manifest hash, skill digest, package, credential id) to first seen, last seen, devices and sessions; new indicators are matched over retention through the observable index, new or changed rules are replayed over the last 24 hours by default and over a longer range only as a quota-bound job whose scan size is shown first, and all are marked retro and never page. The export contract: findings, incidents, decisions and response actions with stable ids and update events, at-least-once with per-destination cursor and replay; down-converters are versioned data with golden tests. Generic sinks (signed webhook, syslog, OTLP, OCSF JSON to object storage, HEC) and the local event feed do not require the server (l03, l02).

### Platform

**D-33. One server binary, three profiles, three service tiers.** Targets are module boundaries: `decide`, `approve`, `ingest`, `control`, `content`, `detect`, `store`, `query`, `review`, `intel`, `notify`, `identity`, `keys`, `audit`, `api`, plus `gateway` (the proxy in server mode), `operator` (the operator plane, D-70) and `router`, which runs in any installation of more than one cell: hosted, self-hosted (air-gapped included) or OEM. Profiles: `embedded` (one process), `ha` (N replicas of all), `distributed` (one target per process; the hosted service runs only this, and self-hosters may run it above the `ha` size ceiling with a published reference architecture). Singletons are held by lease. Tier 0 (inline): `decide` and `approve` serve verdict adapters, AuthZEN, approval relay and command dispatch from memory with no database, bus or lake on the request path. Tier 1: ingest, control, content, operator. Tier 2: query, review, intel. Lower tiers never block higher ones. The pipeline is at-least-once, idempotent on device, epoch, lane and sequence, ordered per session, with a stated lateness window (24, 11; c1, l10, l11).

**D-34. Storage ports.**

| Port | `embedded` | `ha` | `distributed` |
|---|---|---|---|
| Relational | SQLite | PostgreSQL 18 | PostgreSQL 18 |
| Events | Lake on local disk | Lake on object storage | Lake on object storage |
| Bus | Log on the relational port | Log on the relational port | NATS JetStream |
| Blobs | Local filesystem | Object storage | Object storage |
| Jobs | Step journal on the relational port | Same | Same |

The lake adopts an existing open table format instead of inventing one: Parquet with a SQL catalogue on the relational port, written and queried in-process with DataFusion; first candidate the DuckLake layout (so DuckDB is an external reader), second Iceberg; a bespoke catalogue only if the storage spike fails. The store consumes the bus, keeps a memtable per organisation for tail reads, flushes by size or time and compacts to a bounded object count per organisation, class and day. The bus is the only write-ahead log, so HA needs only Postgres and object storage. Session summaries and inventories live on the relational port; entity search uses the relational engine and event search uses lake scans. Real-time detection runs on the bus. Endpoint-local history and the flight recorder use SQLite, not the lake. More than one organisation requires PostgreSQL (11, 24, h05; c1, l05). *Revisit:* a ClickHouse adapter behind the typed query layer if the spike misses its targets at both tested volumes.

**D-35. Tenancy and keys.** Organisation id comes from the device credential. Isolation is a framework-injected tenant context, Postgres row-level security and per-organisation prefixes and keys; no code path reads without a tenant context. Provider views use a set-valued context computed from live delegations; provider lists and tiles read relational roll-ups, and only provider hunts fan out per organisation in the lake. Organisations are provider-originated (the provider is owner of record until the customer claims it) or customer-originated (delegation approved by the customer, role-scoped, time-bound, revocable); cross-organisation actions are written to both audit logs. Key modes: operator KMS and customer-managed key, through the Keys port's `local` adapter (key file, TPM-sealed credential or OS keystore) or `kms` adapter (AWS KMS, GCP Cloud KMS, OpenBao Transit, PKCS#11), so every profile runs with no cloud KMS and no route out (P16). Endpoint-sealed fields and third-party proof of policy integrity are part of the design and use reserved schema fields, so they need no schema change. The provider tier requires this tenancy model and the server. Scale beyond one cell, hosted or self-hosted, uses cells sized by a load-tested capacity vector behind a router that holds only the directory; an organisation larger than a cell's free capacity spans cells in its region as device shards with a home shard (20 section 11); intelligence, the content repository and billing roll-ups are global (24, g07; c1, l05, l10).

**D-52. Event fidelity contract.** Always shipped, never sampled: the session and tool-call spine, every non-default verdict and receipt, findings, labels, credential use, config changes, spawns, MCP activity, model-request metadata, process start and exit in agent lineage (beyond the first `process_rollup_after` identical executable and parent-executable pairs in one tool call, default 8, repeats roll up like other allowed effects, while every first-seen pair and every non-zero exit still ships), and first-seen executable, destination and path prefix per session. Repeated allowed exec, file and connect events within a tool call ship as counted roll-ups carrying a Merkle root of the elided events. The flight recorder keeps full fidelity locally for a period set by policy (default 72 hours), uploads its look-back around any finding, answers a signed evidence request, and reports expired data as a gap. All of it obeys the capture level. Storage and bus are designed and tested at 5,000 and 100,000 events per endpoint per day and at 10 million endpoints (P15); a capture study on real machines precedes storage, pricing and replay design (c1, c5, l03, l07).

**D-36. Sensor transport and identity.** Data plane: acknowledged unary batch POST (Connect unary, valid on HTTP/1.1 and HTTP/2) with `(device, epoch, lane, seq)` idempotency, a hash-chained spool and gap events; streaming only for gateways and node sensors. Control plane: a fleet service on the same endpoint with OpAMP semantics (desired digests, health, package offers) and one push channel with long-poll fallback; an OpAMP wire adapter requires a real consumer. Plain zstd unless the capture study shows a lane's trained dictionary saves over 30% of that lane's fleet-weighted compressed bytes. The uplink works through explicit, PAC and authenticating proxies and through TLS inspection: device authentication is application-layer (an HTTP message signature by the device key), mutual TLS is added where the path allows, and each downgrade is a reported fact. TLS 1.3 through rustls with aws-lc-rs, hybrid key exchange preferred. Enrolment: single-use token; a per-organisation deployment key for RMM and MDM (devices start in Watch until admitted); platform attestation; workload identity federation for containers and CI. Each device reports key protection (hardware, OS keystore, file). Two chains under one device id is a clone finding. The server controls flow and schedule: one server-directed schedule sets batching, check-in phase, heartbeat, long-poll, reconnect spread and backoff caps; retry-after is a floor plus jitter, never an instant; admission sheds by priority and never sheds commands or `decision`; backfill and evidence drain within credit; per-request responses are signed by short-lived keys the fleet key certifies (23, 24; c5, l04, l05, l11).

**D-37. Updates and rollouts.** Everything that changes sensor behaviour except a response command is one signed pack type with one verifier and one last-known-good store. Four channels use it: binaries, schema and policy, detection content, native agent configuration. Trust is TUF-style with two roots: a project root (threshold two, with its keys and the release signing keys generated inside two separate GitHub Actions environments, the release signer and the independent rebuilder, and held there as environment secrets; compiled into binaries; alone authorises binaries) and a deployment root (one per self-hosted installation or OEM, and one per region of the hosted service with delegations to its cells and one fleet key; pinned at enrolment; authorises policy and configuration, never binaries). The TUF client sits behind our own trait. Packs declare a minimum engine version and are validated against every supported engine. Rollout gates are named (crash-free rate, check-in loss, CPU and memory against baseline, deny-rate and prompt-rate change, hook latency, agent-start probe); halt is automatic, and resume is never automatic: the operator's recorded decision in a deployment, and in the project's own channels only a new release that passes the gates again (22 section 7.3). Every artefact is content-addressed and immutable behind any CDN, cache or mirror and may be offered as a delta verified against the full target; an offer is admitted at a per-device time spread over its ring's ramp, never released at once; gates read cohort sketches merged across cells. A rapid lane carries only indicators and reputation verdicts and still bakes. Rollback is a new signed release; the crash-loop ladder never relaxes fail-closed classes, never goes below a signed security floor, and every step is a server-visible event. Update authority is a group setting: self, managed (MDM or package manager owns binaries) or image. Expiry of certificates, or of update metadata that no freshness statement covers, marks a device Stale and never stops enforcement or renewal; on a site without internet the deployment vouches for the newest project snapshot it imported with a short-lived freshness statement, which satisfies the expiry of every project role except the root and nothing else (22 section 6.5) (24, 25, h05; c5, l01, l04, l08, l11).

**D-38. API and access.** Protobuf is the contract, served as Connect, gRPC and gRPC-Web, with generated OpenAPI, SDKs and a Terraform provider; Google AIP mechanics. Console authorisation is Cedar in its own namespace; the operator plane has its own API package and namespace (D-70). OIDC and SAML sign-on, SCIM, workload identity federation before static tokens. Our own MCP server is stateless and read-only by default: tokens bound to one organisation, metadata only without a content grant, no code execution, no response actions, proposals rendered by the server from the canonical diff; a governed agent's session cannot read policy, detection content or its own exception state (g07, 24; c5, l01).

**D-55. Roles and separation of duties.** Roles: organisation owner, policy author, policy approver, responder, investigator, content reader, auditor, privacy officer, platform operator, plus provider technician roles. Invariants enforced in Cedar and tested: an author never approves their own widening change or promotion to Ask or Block; a requester never approves their own exception; the platform operator cannot read content; response and policy roles are separate; operator access to an organisation's data needs a tenant-visible, time-boxed grant; break-glass needs two people (l02, l11; 33).

**D-39. Tamper-evident audit in layers.** Sensors hash-chain events per lane and sign each batch head with a per-boot key certified by the device key; chains commit to salted digests so erasure does not break them. The server archives batches byte-exact. On the device, with no server: local chain and `grdr audit verify`. With the server: a per-organisation checkpoint chain exported to a customer-controlled sink. On top of the checkpoint chain (requires it): tile log, inclusion proofs, a witness outside the operator's control (a witness service named in configuration, which may run inside the customer's network, or an offline witness that countersigns checkpoint files carried to it), SCITT-style receipts (23, 34; c5, l10).

**D-40. Integrations and the gateway.** Three tiers: declarative manifests (the only tier that runs on sensors); WebAssembly components with explicit grants and out-of-process plugins on the server. Each adapter family ships two first-party members when it first appears; the rest arrive through the content lane. One decision API (the server's `decide` target, which these adapters require) sits behind thin verdict-provider adapters for vendor-side hooks; those adapters evaluate only policies marked stateless and report the vendor's fail mode as part of assurance. The `gateway` target is our proxy in server mode: an enforcement point for model routes and MCP over HTTP with in-process policy, fail-closed defaults and kill-switch actuators, not a routing gateway. agentgateway, Agent Router, Kong and LiteLLM are adapters that declare their verbs and fail mode; a host that can fail open is reported as a request. Provider-scoped integration instances serve MSPs (PSA ticket sync, usage posting, RMM deploy scripts) (26, 38, h01, h05; c6, l05, l10).

**D-41. Embedding options.** These are options, not a progression. L0 and L1 need only the sensor and content; L2 to L6 each require an embedding partner.

| Option | What the partner takes | Blocks before execution |
|---|---|---|
| L0 | Content compiled to KQL, LogScale, EQL, XQL, SPL and generic Sigma | No |
| L1 | Local event feed: Windows Event Log channel, journald, unified log, JSON lines, OTLP | No |
| L2 | Hook broker and provider interface | At hooks |
| L3 | Embedded engine in two parts: a fast-path library (fixed-layout inputs, precompiled tables, no parsers, no JIT, no threads, host allocator) for protected processes, and the content engine as an unprivileged sidecar or WebAssembly | Wherever the host enforces |
| L4 | Our core over the partner's data lake, response through its API | No |
| L5 | Full platform beside the partner's EDR | Yes |
| L6 | Co-brand (a provider branding profile, configuration only) or rebuilt (the partner builds from source with a brand manifest and its own signing identities) | Yes |

An MVI-member EDR or MDR design partner is the external precondition for an L3 sidecar pilot, and recruiting one does not wait on any component, because the owner's Windows platform questions (WESP, protected processes) can only be answered through one. L2 opens to third parties only if native hook merging proves insufficient.

**D-60. Host contract and stability classes.** The host contract requires an embedding partner; its seams (ports, reserved schema fields, pack types) are in the core regardless. A host supplies a profile: event classes with provenance grade, session mechanism, actuator verbs. The engine derives the achievable assurance and returns "not evaluable" per rule instead of passing silently. Conformance has three kits: golden vectors, a scripted scenario pack the partner runs on its own sensor, and a provider kit. Every public surface is experimental, beta or stable; stable means additive-only within a major with 12 months of overlap; nothing is stable before one external embed pilot completes. Embedded builds make no network call to Loonaro and embed no trust roots. A content relay lets a partner pull, verify, test against a named engine build, re-sign and ring our packs (27; l08, c6).

**D-56. Service objectives and the offline contract.** Twenty-eight-day objectives: tier 0 verdict within 150 ms 99.95%; ingest acknowledgement 99.9%; queryable within 60 seconds 99%; finding within 2 minutes 99%; policy propagation 60 seconds at p99 from a ring step opening to applied on that step's online devices, at any scope size; console and API 99.9%. Every cell and self-hosted install runs a synthetic sensor sending a signed known-bad sequence every five minutes with an independent alarm path inside the operator's network. Per-organisation pipeline lag shows as "could not look". When the server is unreachable: cached policy and grants work, step-up falls back to the local authenticator, the broker serves from the customer's store with a stated cache lifetime (l11).

**D-57. Durability, retention and erasure.** Partition by organisation, data class and day; captured content is stored apart under per-session keys. Erasure deletes the pseudonym mapping and destroys content keys; holds are catalogue pins checked by every delete path. Physical deletion lags logical deletion by the point-in-time window. The store writes a signed per-organisation manifest so the lake can be rebuilt without the database. `grdr server backup` and `restore --verify` ship with the server; the second failure domain is a second store, a second site or removable media written by `grdr server backup --to <dir>`, so none needs a cloud account. A restore is a signed state transition: it mints a new server epoch; revocations, kill states and consumed token ids are also written to versioned object storage and replayed; sensors re-send from a durable watermark; the audit log is never restored backwards. Recovery objectives: relational 5 minutes and 1 hour; events 15 minutes and 4 hours (c1, l11, l07).

**D-58. Server lifecycle and the self-hosted contract.** Upgrade order is server, gateways, sensors. The unit of upgrade is the product bundle and the unit of transfer is the changed component: a deployment moves only from one tested bundle version to another (D-71), and because a bundle lists every component by digest, the updater, mirrors and the air-gap delta bundle carry only the artefacts whose digests changed, as deltas where S-27 admits them, so a patch that fixes one component is one download. Content packs, detection rules, intelligence snapshots, adapter manifests and policy move on their own signed, ringed channels without a bundle upgrade, as do the eBPF object and the optional Windows driver within their declared interface ranges; public crates and SDKs are for developers and embedders and never upgrade a deployment. Supported lines are the current minor, the two before it and the live LTS; the first LTS is the first minor at least 90 days after server 1.0, then every twelfth minor, with public security fixes for 24 months; upgrades hop at most two minors with required stops; longer support periods are set with counsel before any paid offer. Migrations expand and contract across two releases, so N and N+1 run together during a rolling update; an upgrade-path manifest and `grdr server preflight` refuse unsafe jumps. The operator plane (D-70) drives an upgrade: it shows the available bundle (from the project's TUF repository through the operator's mirror or CDN, or from an imported air-gap bundle), its changelog, the path and the preflight result; upgrades the server (rolling for one minor, recreate for two, automatic binary rollback when a health check fails); then offers the sensor packages to the fleet through rings with bake times and automatic halt. The update policy is an operator setting: manual, automatic patch releases only, automatic minors inside a maintenance window, or LTS only; where `helm upgrade` or an MDM package channel applies the upgrade, the operator plane shows skew and preflight instead. Each release publishes tested versions of Kubernetes, PostgreSQL, NATS and object stores, with their digests in a signed dependency lock (`dependencies.lock.json`) whose every entry the air-gap bundle carries (D-59); any other S3-compatible store that passes `preflight`'s probe runs as Tier 2. The server ingests from any sensor of the same wire major. Self-hosting is the default way to run the platform and is supported as `embedded` and `ha`, as `distributed` above the `ha` ceiling (about 50,000 endpoints, to be load-tested; `distributed` for self-hosters requires that load test), and above one cell's tested capacity vector as several `distributed` cells behind the installation's own `router`. No phone-home, licence key, activation, entitlement check or trial expiry in any shape, and every supported line installs, upgrades and is supported with no route out (P16) (l11, c5).

**D-59. Packaging and reference deployments.** Endpoints: per-machine MSI (x64, ARM64), one universal pkg, signed deb and rpm repositories; silent, idempotent, offline-installable, no secret on the command line; a profile generator for MDM. Every artefact is signed keylessly with Sigstore through GitHub's OIDC identity, with SLSA provenance, an SBOM and its Rekor inclusion proof for offline checks. Platform signatures come on top where a programme grants them: Authenticode on the MSI through a free open-source signing programme (D-17), and notarisation of the pkg only with Apple's Developer Program (D-18). An artefact without its platform signature is marked `not platform-signed` in the release manifest, and nothing in development, testing or release waits for one. `grdr doctor` reports capabilities, slot owners, hook-fired per agent, network path and overhead; `grdr support-bundle --preview` redacts on the device. Multi-session hosts require per-logon-session policy and listeners; an installer without that support refuses them. Server: one image (amd64, arm64) and one Helm chart written to the strictest marketplace rules, the node sensor in its own chart; Terraform modules for AWS, GCP and Azure, each mapping to managed PostgreSQL and object storage; an air-gap bundle with a mirrorable update repository, a server stop bundle for every minor, and delta, content and metadata exports between releases (24 section 7). The bundle carries everything every profile needs, so nothing is fetched on a connected host: our artefacts; every third-party image, chart, binary and package of `dependencies.lock.json`, built by us from source on a minimal base, signed, with SBOM and provenance; models, intelligence and content snapshots, browser-extension packages, OS packages, the optional site services the conformance run uses and the offline docs; and the complete corresponding source and our patches for every copyleft component (`sources/`), with a generated `THIRD-PARTY-NOTICES`. Its delta carries only changed digests, third-party ones included. `grdr server airgap import` shows one combined terms screen and imports only after explicit acceptance, recorded with the operator's identity, the bundle digest and the time in the operator audit log (`--accept-terms <file>` for unattended installs). The supply-chain gate bundles a component only if its licence allows redistribution; one whose terms forbid it is replaced by a redistributable equivalent or becomes optional, and is never required to install, enrol, update, detect, respond or operate (the FIDO Metadata Service BLOB is imported by the operator, and the bundle carries an authenticator list built from redistributable sources) (25, g04; l04, l12).

**D-67. Portability and exit.** An organisation owner can export and delete everything without operator help: the Parquet lake, a documented relational dump, policy as git, and the audit log with its verification material. Export and import move an organisation between hosted and self-hosted; devices re-enrol by signed redirect (l12, l05).

**D-68. Usage ledger and quotas.** An append-only usage ledger in core carries all ancestor ids (parent provider, provider, organisation): active endpoints, users, agents observed, bytes, retention, model tokens by key owner; roll-ups, export and signed statements; rating and invoicing are adapters. Ingest, bus and query have per-organisation limits; at quota, raw fidelity is sampled; under cell overload, admission delays lanes lowest priority first (P15); verdicts, findings and audit are never dropped (g10; l05, l11).

**D-70. Operator plane and two-tier server configuration.** Whoever runs the server (an enterprise, any hoster, Loonaro's hosted service) administers, configures and health-checks it in a separate, isolated place instead of through environment variables and redeploys. *Boot configuration* (a file, the environment or Helm values) holds only what is needed before the database is reachable: profile, listen addresses, references to the relational store, object store and Keys back end, and the operator listener. *Runtime settings* hold everything else (sign-on providers, mail, storage and retention defaults, quotas, cells, which modules and adapters are on, telemetry export, maintenance mode) as versioned revisions in the relational store, validated against the `grdr.config` schema with its `security` and `stability` options; each target loads a new revision and reports it healthy, and the change rolls back automatically when a target fails its health check. Every `grdr.config` key declares its tier, `boot` or `runtime`; a runtime revision moves through explicit states (draft, validated, applying, applied, rolled back, superseded, discarded) and applies to one replica first. `grdr config explain` shows the runtime layer with the others (03 section 9). The `operator` target (D-33) has its own listener and origin: loopback by default in `embedded`, its own hostname and Ingress in `ha` and `distributed`, with an optional IP allow-list and mutual TLS. It shares no cookie, session or account with the console and API, and runs as its own database role with no grant on tenant content (20 section 16). Operator accounts are a separate realm (passkeys, or the operator's own IdP through OIDC or SAML; TOTP only as the second factor of an operator account that cannot use a passkey); a first-start bootstrap token, printed once, can only register the first operator passkey. Authorisation is its own Cedar namespace, `Grdr::Operator`, behind its own API package, `grdr.operator.v1alpha1`, separate from `grdr.api`. The plane offers settings with diff, validation, staged apply and rollback; health of every target and port (database, bus lag, lake commits, Keys, backup health, certificate expiry) with history; diagnostics and support bundles; upgrade preflight, the upgrade path and migration status (D-58, D-71); organisation lifecycle (create, suspend, move, provider tier); key rotation; backup and restore drills; and an operator audit log on its own checkpoint chain. It has no route to tenant content: it calls no content API, the operator still cannot read content (D-55), support grants and two-person break-glass work as `design/21` section 8 says, and widening a `security` setting needs passkey step-up. Unauthenticated `/livez` and `/readyz` stay on a separate management port and return status only. Configuration as code still works: `grdr operator config export` and `apply`, Terraform resources for runtime settings, and a source lock, as for policy (D-11), that makes git authoritative for chosen keys, which the plane then shows read-only. The plane is a web application on the console's Astryx components (D-42); for Loonaro's hosted service it runs per cell and for the router, reachable only from Loonaro's private network. Server-side accounts and mail: mail is a `Mailer` port with a first-party SMTP adapter and HTTP-API adapters in contrib, its templates are language tokens (D-69), and delivery status and bounces are recorded; organisation invitations are single-use, expiring and bound to the invited address; every hosted account verifies its email, and verified domains drive home-realm discovery and SCIM; hosted sign-up for individuals and small teams is a passkey account with a verified email, or sign-in with Google through OIDC or with GitHub through its OAuth app flow (21 section 6), and an organisation can require its own IdP and disable the rest. There are no passwords, SMS codes or magic links, because they are phishable. Hosted mail is sent from the brand manifest's mail domain with SPF, DKIM and DMARC (`design/20`, `design/21` section 6, `design/23`, `design/24`, `design/25`, `design/27`, `design/32`).

**D-71. Compatibility is declared against contract ranges, with one resolver.** Components version on their own (public crates, SDKs, programs, the eBPF object, the optional Windows driver), and each declares in its build manifest the contract ranges it provides and requires: wire major (`grdr.*` packages), local IPC packages, C ABI version, pack `format_version` and engine line, Cedar `schema_version`, driver interface, eBPF object interface and API package, for example `requires = { wire = "1", pack_format = ">=3, <4", driver_interface = "2" }`. The ranges are data (P14). The release manifest carries a `compat` block generated from those declarations, and the product bundle version pins the exact component versions and digests tested together; the bundle and its `compat` block are a TUF target, so a device, an air-gapped import and the operator plane read the same facts. One resolver library, used by the updater, `grdr server preflight`, the operator plane and the release job, refuses any combination outside the declared ranges before anything is activated, with a message naming the component and the contract that does not match. At run time the existing handshakes (`Hello` capability bits, the frozen bootstrap service, `grdr_abi_version()`, `min_engine` and `requires_capabilities` on packs) degrade instead of failing: a missing capability makes a rule not evaluable and is reported (P9). `support.toml` generates the compatibility matrix that CI runs: every supported sensor line against the server (N-2, N-1, N, N+1), every pack against every supported engine line, the driver and eBPF interface ranges, and the upgrade path's hops. `buf breaking`, `cargo semver-checks` and the C header diff gate every change to a contract, and a change that breaks a declared range fails verify unless it also bumps that contract's major and adds the overlap its stability class requires (D-60) (03 section 7, 22 section 8, 24 section 11).

### Interfaces

**D-42. Web console.** A static Vite and React 19 app served by the API server as an OIDC backend-for-frontend, and locally by `grdr console serve`, an unprivileged per-logon-session process started on demand that reads through the daemon's local API (the daemon itself binds no TCP port). The local subset needs only the daemon; the full console requires the server. Every surface a person or an agent reads (web console, local console, operator plane, Rune app, tray, `grdr-approve`, CLI human output, block and agent messages, notifications and email, browser extension, installers, docs and status sites) is built from one interface system in `interface/` (P17): DTCG tokens, the pattern, presentation, icon, route, notification, shortcut and CLI registries, and the language tokens of D-69. On the web every element is an Astryx component. `@grdr/ui`, pinned and the only package that imports `@astryxdesign/*`, is a thin layer over Astryx for theme, tokens, language tokens and brand defaults and never reimplements an Astryx component. `@grdr/kit` builds the composites that define the product (session timeline, session tree, policy editor, mode control, approval card, setup list, triage) from `@grdr/ui` components alone, imports only `ui`, `tokens` and `i18n`, and is the embeddable kit, rendered inside a shadow root with Astryx's stylesheet adopted there (a spike proves this; if it fails, only the embed package becomes a registered exception, still styled from the tokens). A component of our own, on React Aria, exists only where Astryx at the pinned version has a gap that composing its components cannot meet, as an entry in `web/packages/ui/exceptions.toml` (the need, the gap, the exit condition, the owner) that `eval-ux` and `lead-interfaces` agree in check runs; specialised widgets Astryx does not ship as stable (charts, code editor, graphs) are registered the same way and wrapped once in `ui`. Large tables use Astryx Table and its virtualisation plugin; TanStack Virtual enters only as a registered exception if WEB-04 shows the plugin fails the event grids. Surfaces that cannot render Astryx (the Rune app, tray, email) take its component names, anatomy, variants and states and the same tokens. The tokens generate every renderer's theme. Strings are language tokens under D-69 from the first commit, with the pseudo-locales `en-XA`, `ar-XB` and `ja-XC` in CI. WCAG 2.2 AA is our own target (30; c7).

**D-43. Desktop in Rune, scoped and contained.** Requires S-19 to pass. The Rune app is the developer's desktop app with six screens (first run, Home, My activity, Rules, Privacy, Settings), which are local-console destinations with the same route ids and titles. The full console exists once, as the web app, which `grdr console serve` serves on loopback. The tray uses native menus with no Rune or GPU dependency and opens the web console on software renderers and remote sessions. View-models live in a crate with no Rune dependency; Rune is pinned, mirrored, patched to remove tooling flags, soak-tested in our CI and run inside our own sandbox profile. Approvals never use Rune. The local console binds loopback on a random port with a one-time launch token, Host and Origin checks and no CORS; other local APIs use sockets or pipes. *Revisit:* two consecutive failed soak runs make the desktop web-only until Rune passes S-19; the owner asked for Rune, so the soak reruns on each new Rune release (29, 30; c7, l01, l06).

**D-44. Experience rules.** One interface system everywhere (P17): the same object has the same name, icon, words, states and confirmation on every surface; a surface may show less, never rename or restyle. Value before any change or sign-up: the first run scans, shows what it found and only then offers protection; setup lists open with completed steps ticked. One mode ladder; every mode control shows its effective outcome for the selected scope (boundary, request or not enforceable, with device counts). Ask names its approver; a classifier or model denial always degrades to Ask or a one-step exception, never a dead end. Every block message names the component that blocked (ours, the agent's own classifier, another product), the rule and the route to an exception within one second, and the agent receives a reason it can act on. The review queue is session-based with three buckets. Every dashboard tile is a sentence with a number, a comparison and one action. Providers get a workbench: one cross-organisation queue, approval routing with a timer and deny on timeout, saved dispositions, scheduled branded reports. Provider views always show the tenant and an "acting as" banner (33, h08; c7, l05, l06).

**D-69. Language tokens: one message source, compiled for every surface.** Every human-facing string on every surface is a language token: a keyed Unicode MessageFormat 2 message (LDML part 9, pinned to CLDR 49) in `interface/strings/`. Tokens have three tiers, like the DTCG tokens: terms (section 3's vocabulary from `schema/vocabulary.toml`, with one approved form per locale), shared messages (`common.*`, any string used on two surfaces) and surface messages. One compiler, `cargo xtask interface`, validates them and generates typed accessors: `grdr-messages` for every Rust surface (CLI, tray, `grdr-approve`, `grdr-ui-model`, the engine, the server's notification and report renderers) and `@grdr/i18n` for the console, the kit, the browser extension and the docs theme, so a missing key, a missing argument or a wrongly typed argument fails compilation. Formatting uses CLDR through ICU4X (`grdr-strings`) in Rust and the platform `Intl` APIs in browsers, held together by a parity corpus; nothing formats a date, number, list or plural anywhere else. Pack text (rule titles and messages, detection descriptions, tiles, reports, notification templates) is the same format inside signed packs, compiled to the MF2 data model at pack build, one update target per locale, and rendered only by `grdr-engine`, `grdr-server` and `grdr`; `grdr-hook` and privileged programs interpret no message data. Stored records keep a `MessageRef` (id and typed arguments), so each reader sees their own locale; times are stored in UTC and shown in the viewer's zone. Layout is direction-neutral: logical properties, a mirroring table for icons, every placeholder isolated, identifiers and the canonical call always left-to-right. Per-script typography is a token set in the DTCG source. Identifiers, codes, Cedar, CLI tokens, configuration keys, logs, `--json`, `Status.message` and all agent-facing text stay English; person-facing text is localised, Mode labels included, while the CLI and packs take the English identifiers. Agents translate from the glossary; deterministic checks, a cross-model back-translation and the pseudo-locale and screenshot gates decide, no person is a required step, and corrections from anyone arrive as pull requests through the same gates. Locales are data: adding one changes no code. Catalogues, CLDR data, fonts and time-zone data ship in every binary and in the air-gap bundle, and nothing is fetched at run time. *Rejected:* ICU MessageFormat 1 with FormatJS (a second implementation of the semantics on the web, no bidi strategy, no Rust formatter, and the `react-intl` 12.1.7 pin was inside the cooldown when read); Fluent (not a Unicode standard, parsed at run time); `rune-i18n` and WebExtension `messages.json` as sources (second formats); hosted translation systems (cost, network, a human gate).

### Assurance of the product and the project

**D-45. Efficacy is measured in the open.** A harness with three passes per scenario (product absent, monitor, enforce), an oracle independent of the product, and AMTSO's outcome vocabulary. Two scenario families: model-driven, and scripted through a replay model endpoint that makes the real agent emit fixed tool calls. Tracks: prevention, detection, discovery of generated bespoke agents, attribution with scripted humans, fault injection, sandbox conformance, performance beside incumbents, privacy leakage. The scorecard reports attack success at 1, 10 and 100 attempts and the margin between the tuning set and the held-out set. The pull-request gate is the public `verify` only; the held-out suite gates releases and agent work items, is readable by every human maintainer, and each set is published two releases after use. The harness needs only the core and the replay model endpoint, and every release and every gated agent work item requires it (g08, h01, h04; c8, c9, l09).

**D-46. Compliance is data.** A control library with crosswalks, exported as OSCAL: SOC 2, ISO 27001 and 42001, NIST, EU AI Act deployer duties, the UK NCSC and Five Eyes agentic guidance, Singapore's framework, CSA AARM, AIUC-1, PCI and HIPAA retention. We say "passes the AARM R1 to R9 test set" until the conditions for the public label are met. A buyer-RFP response and the RFP's mandatory requirements as release gates. A monitoring catalogue, impact-assessment pack and worker notice are generated from live configuration. For the project: OSPS Baseline, OpenSSF Best Practices, SLSA Build L3 provenance, SBOM and VEX from the first release; these, the control library and evidence export cost nothing. Customer evidence export requires the server. Paid certifications (SOC 2 Type I and II, ISO 27001 for the hosted service) require revenue or a sponsor. Before any paid offer: counsel's opinion on Cyber Resilience Act class and route, a human-staffed incident response team that can meet the 24-hour, 72-hour and 14-day clocks, an EU contact, public technical documentation and a support statement (34, h04, h06; c6, l07).

**D-61. Governance and contribution.** `GOVERNANCE.md` and `MAINTAINERS.md` are written by an early work item; the repository is public from its first push and does not wait for them (owner instruction 28). No person is a step in building, reviewing, landing or releasing (owner instruction, 2026-11-11); separation of duties and independent checking hold between agents and deterministic software (D-47, D-63). Agents are tools: no agent identity holds a code-owner entry or a vote, and only the merge queue, which is deterministic software, lands a change. Changes to the spine, public crates, wire formats and the Cedar schema go through an RFC that the persona council and `eval-architecture` review; the chief architect decides, with no waiting period. One rule set for everyone, agent or human: every change has a work item, which is a GitHub issue, and its pull request body carries `Closes #<n>`, the evidence template and a collapsed metadata block (harness, the model id that wrote the change, attempt) that the review pass reads to pick the other model. A commit message is one line, a Conventional Commit subject (`type(scope): summary`, at most 72 characters), with no body, no trailer and no credit line; `guard-command` refuses any other agent commit and gate V24 checks every commit on the branch. Workers commit on `agent/<n>/a<attempt>` branches. The merge queue (`cargo xtask queue`) squash-merges a pull request as its title plus ` (#<pr>)` once verify is green on the rebased head, CI is green where it runs, every evaluator its lane requires has passed (D-63), at most three review rounds were used and the branch is current, and the merge closes the issue; there is no `Signed-off-by`, DCO check or batch sign-off. Components version on their own and a product bundle version pins the set that D-58 upgrades (D-71). release-please opens release pull requests with versions and changelogs from the commit subjects, the merge queue lands them, and release-please creates the tags and GitHub releases; artefacts are signed keylessly (D-59), so no person holds a release key. Community content enforces, leaving Watch, only after its fixtures, the benign corpus and two independent evaluators on different models pass it; first-party content needs evaluator evidence. The covenant states succession if the owner is absent. A steering group forms at the second external maintainer. The agent kit is part of the open project and harness-neutral (28, h09; l09, c9).

**D-62. Security response.** `SECURITY.md` at the first commit; private intake through GitHub private vulnerability reporting, on from the repository's setup, and the brand manifest's security address, triaged by `lead-security`. An engine or normaliser bypass and a memory-safety fault are vulnerabilities with CVE and VEX per supported line; a missed detection is a content gap. Embargoed fixes are made by agents in a private fork of the repository with network tools off; whether the subscription's data terms give zero retention is recorded, not a gate. A pre-disclosure list receives fixes at least ten working days ahead. A seven-day patch target applies to bundled dependencies, ordered by KEV and EPSS: a KEV-listed reachable advisory is fixed first, on every supported line. Proactive work uses only free tools: the supply-chain gates (cargo-deny, cargo-vet, osv-scanner and Grype on lockfiles, SBOMs and images, SHA-pinned actions, zizmor, gitleaks, harden-runner, VEX reachability); CodeQL for Rust and TypeScript and GitHub's secret scanning with push protection from the first push, because the repository is public from it (owner instruction 28; CodeQL's terms allow automated analysis only of open-source code in a public GitHub repository); Semgrep OSS rules; a weekly OpenSSF Scorecard whose score is ratcheted; ClusterFuzzLite in CI for every fuzz target; an OWASP ZAP baseline scan of the console and API against the embedded server; and variant analysis, so every fixed vulnerability becomes an audit prompt run over the whole tree and each surviving hit a work item. Independent review covers the privileged core, updater, shim and approval helper before their first stable-channel release, the transport before the server's first release, and each kernel component before it leaves the internal ring. Evaluator agents run it: `eval-security` and `eval-adversarial` on Opus in clean contexts, cross-model review by the model that did not write the change, two independent passing evaluators on different models, the full verify and the matrix cells the paths need (D-63). There is no money for paid audits; a free external audit (for example OSTIF, OpenSSF Alpha-Omega and similar funds) adds to that review when one is granted, and nothing waits for one (l08, l09, l02).

**D-47. Built by agents, governed by the repository.** Single writer per work item; non-coding planners; isolated workers; independent evaluators that drive the real artefact; scheduled gardeners; a persona council for design review; a deterministic merge queue. The repository holds code, gate configuration, decisions and evidence; GitHub issues hold every work item, its status and its discussion; nothing a gate reads is editable by the writer it judges (owner instruction, `design/_review/04-owner-kit-instructions.md`). Architecture is enforced by dependency-direction lints whose messages state the fix. Protected paths are enforced by filesystem or sandbox rules and a CI diff check, because edit hooks are bypassed through the shell. One `verify` command is called by hooks, every harness and CI; the local dispatcher's `verify` is the primary gate on every change and hosted CI is the backstop (D-64). The team runs on the owner's Claude subscription, so work is measured in share of the subscription's usage windows, not dollars. One agent, the chief architect, uses Fable 5.2; medium-to-heavy work uses Opus 5.5 and everything else Sonnet 5.5, with no Haiku and no other vendor's model (`team/01`, `team/02`). A deterministic dispatcher, not an agent, orchestrates headless Claude Code sessions within the subscription's usage windows: it caps concurrent sessions, pauses when a usage limit is reached, resumes after the window resets, and never fails work because of a limit; every recurring agent (gardeners, canaries, scheduled evaluators) has a usage cap per run. The dispatcher runs on the owner's machine under the owner's existing Claude Code and `gh` logins, so no step needs a new token or account, and agent runs on GitHub-hosted runners are optional; every agent acts under that GitHub login, with roles enforced by `guard-command` on every `gh` call, and GitHub Apps are an optional later hardening. AI review is capped at three rounds on the diff; cross-model review is done in a clean context by the other of Opus 5.5 and Sonnet 5.5 from the one that wrote the change. Power prompts are versioned skills, each with a trigger, one concept, read-only evidence, a refuting verifier and closure only by a type, test, lint or decision record; their value is measured against a plain "find the bugs" control. Every bug fix carries a three-arm proof (fails before, passes after, fails on revert); removals carry survival tests. Every writer follows the `grdr-structure` skill (structures before implementations, files under 500 code lines, explicit state types instead of implicit state machines, comments only for a reason the code cannot show, no panic path in non-test code, no hard-coded value), enforced by post-edit, stop and verify checks. Third-party skills and plugins come from a private marketplace pinned by full commit SHA, all enabled by owner instruction. The development fleet runs under the last signed release of the product (31, 32, h09; c9, l12).

**D-63. Risk tiers, review lanes and the trust core.** One deterministic classifier, `cargo xtask risk`, reads each diff and sets its tier and review lane; the dispatcher, the `review` workflow and the merge queue follow the lane, and an agent may raise a lane, never lower it (P2 applied to our own process). `static`: proven equivalent or checkable without a model (comment, whitespace or formatting only, prose outside protected paths, a file `kit check` re-derives, a lockfile change inside the supply-chain policy), landed on deterministic proofs alone. `static` never applies to a protected-change item, and on a trust-core path it applies only to that lockfile case (no new package name and no new major version), which owner instructions 8 and 22 name so that routine dependency updates land on proofs; every other trust-core change takes `full`. `light`: at most 50 changed lines in at most 3 files, with no trust-core or protected path, new dependency, public-API or wire change, new `unsafe`, or change to error codes or limits, landed on verify plus one `eval-diff` pass on Sonnet. `standard`: the tier's evaluators (`team/02` section 10). `full`, for high tier and the trust core: `eval-security` and `eval-adversarial` on Opus in clean contexts, cross-model review by the other of Opus 5.5 and Sonnet 5.5 from the one that wrote the change (D-47), the full verify and the matrix cells the paths need, bound to one commit. Evaluators publish check runs, never approvals, and `eval-tier` samples reviewer quality against the reviewer eval set. Changes to trust-core paths, apart from that lockfile case, take the `full` lane and need two independent passing evaluators on different models. The trust-core paths are eBPF programs, the Windows driver, the macOS extension shell, the privileged core, IPC peer authentication, updater, cryptography (which only composes vetted libraries), policy evaluator semantics, tenancy, `unsafe` in the FFI, the approval helper, and gate, CI and release configuration. The scale design's command delivery (nudges, `Wait`, `PendingCommands`), response keys, the integrity wire form, CDN-lag handling in the TUF client, the provider set-context row-level security policy, the KEK soft and hard TTLs and `SignedSet` are trust-core changes. A trust-core change also needs a reference model with differential tests, and matrix and soak evidence; a trust-core component leaves the internal ring only through the review D-62 sets for it, and stays in the internal ring without it. A protected change (gate configuration, ratchets, exemption files, acceptance rules, the marketplace, the spine and plan) is its own work item, implemented by `lead-agent-kit` or the chief architect with `GRDR_SCOPE=protected` set by the dispatcher for that lease only, and lands only after `eval-security` and one more evaluator on the other model pass; an exemption or a ratchet loosening also needs `eval-architecture`, or the evaluator for that area, to agree in a check run, and no agent changes a protected path inside an ordinary item. The chief architect and `programme-manager` own review capacity, sampling and planning; an escalation goes to the item's lead, then the chief architect, never to a person, and the dispatcher cuts writer concurrency when the evaluator queue passes its cap or the subscription's usage window is the binding limit. Dependencies: the seed pins the newest stable release of every dependency, tool, action and toolchain, each free of yanks and open advisories, on the licence allow-list and with provenance where the ecosystem offers it; after it, Dependabot (`.github/dependabot.yml`, which needs no account beyond the repository, owner instruction 23) proposes updates with a cooldown of 3 days for patch and minor releases and 7 for majors, with Cargo's `min-publish-age` and pnpm's `minimumReleaseAge` as a second layer, security fixes skip the cooldown with `eval-security` reading the diff, and every update lands through the merge queue in the lane its diff earns. Circuit breakers tighten lanes and tiers when revert or incident rates rise. The owner's buddy is the second person for what stays with people: second maintainer, second administrator of Loonaro's accounts, second approver where Loonaro's own operation of the hosted service needs two people (D-55), and on-call partner. A hosted tenant, beta included, requires two people on call (met by the owner and the buddy), the legal entity (Loonaro), a written incident-reporting process, and infrastructure funded by revenue, sponsorship or donated cloud credits; self-hosting needs none of these (c9, l01, l11, h09).

## 9. Risks with triggers

| Risk | Trigger and response |
|---|---|
| Evaluator queue saturates | Over 20 items or oldest over 48 hours: the programme manager cuts writers to three |
| Evaluators miss a trust-core defect | Two independent evaluators on different models, a reference model with differential tests, matrix and soak; every defect found later becomes an audit prompt run over the whole tree (D-62) and circuit breakers tighten the lanes (D-63) |
| Agent-written kernel code harms hosts | Any panic in matrix or soak: component stays in the internal ring |
| Rune is not ready | Two failed soak runs: web-only desktop, soak rerun on each new Rune release |
| Apple does not grant the entitlement | Entitlement refused: Endpoint Security only through an embedding partner; macOS keeps tiers 1 and 2 |
| Test fitting | Held-out margin above 5 points: release blocked |
| Subscription usage limits | A usage limit is reached: the dispatcher pauses and resumes after the window resets, no work fails; usage per accepted item above twice the S-20 baseline: writers cut and new feature work paused until it is back under; trust-core, security and release work go first in the queue |
| Automation is bound to one account | The dispatcher, every agent and every routine act through the owner's Claude Code and `gh` logins, and the subscription's terms or limits can change or an account can be restricted. Response: the repository and its GitHub issues hold all state and the agent kit is harness-neutral, so work survives a loss of access and continues under another login or harness; a token added later for hosted agent runs lives only as an environment secret and is rotated on any suspected leak |
| Zero budget blocks a precondition | Apple's fee unpaid: macOS ships with tier 1 only and is not notarised. No driver sponsor: Windows stays driverless. No free audit granted: the evaluators' review stands alone. No hosting funds: self-hosting only, which reaches ten million endpoints (P15). No donated capacity: S-24 runs only its `ha` arm, so the cell cap stays at 50,000 endpoints and self-hosted multi-cell installations stay gated. No incumbent licences: coexistence is tested against Defender and free programmes, and the ceiling matrix marks the other cells untested |
| A platform-signing account is refused or suspended | Artefacts keep their Sigstore signatures and provenance and ship marked `not platform-signed`; the buddy as second administrator and a documented re-sign path restore it |
| Injection into build agents | Read-only agent jobs; the fleet's guard is the last signed release, never the working tree |
| An incumbent bundles the same thing for free | D-65 wedge reviewed against adoption when an incumbent ships it |
| Hook interfaces change or close | Adapter canaries within 24 hours; OS control points carry enforcement |
| A free origin caps, refuses or changes its terms | `updates.sources` moves that object class to another origin, a mirror or a CDN added by configuration, with no release (22 section 6.1); S-26 keeps a terms record per origin |
| A fleet herd breaks a cell | S-23 reruns on every change to the uplink scheduler, admission, nudge pacing or rollout ramp; the cell cap drops to the largest size S-24 passes |
