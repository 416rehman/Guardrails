## Summary

This document specifies D-19: one Rust Linux `SensorBackend` (the spine's `grdr-sensor-linux` with its own `grdr-sensor-linux-bpf` kernel crate) that runs unchanged on developer laptops, servers, WSL2, containers, Kubernetes nodes and ephemeral CI, and that off the laptop reaches the pods, runners and cloud runtimes an endpoint sensor cannot touch. Key choices:

1. **A capability probe reads `/sys/kernel/security/lsm` and kernel features at every start, never the distro name, confirms each tier by loading a no-op test program, and picks an enforcement tier per action class.** The tier is a reported fact (`health.sensor`), not an assumption (P9, c3 F7).
2. **Enforcement tiers, in order: BPF LSM; `fmod_ret`/kprobe override on `security_*`; cgroup-v2 network BPF plus fanotify permission marks on the protected-path set only; the launch sandbox; observe.** Each tier declares which action classes it can block; `on_failure` and the assurance `control` level follow from it. AL4 needs T1 or T2, because T3 cannot block `file.write`. Observation needs only the sensor; the launch sandbox needs no privilege; kernel enforcement leaves the internal ring only after the review D-63 sets for kernel components, and `cgroup_sock` is reviewed on its own because launch containment's network boundary depends on it (R-40).
3. **The kernel programs are their own crate, dual `GPL-2.0-only OR BSD-2-Clause`; everything else is Apache-2.0** (D-02), and the back end loads a prebuilt signed object, so a default build needs no kernel toolchain (03).
4. **Enforcement survives loader death.** Programs and links are pinned in bpffs and maps are locked against non-sensor tasks, because upstream has no agreed fix for user-space tampering with BPF LSM state (h02, LSFMM+BPF 2026).
5. **One cgroup-v2 scope per session-exclusive session** is the attribution anchor and the unit of cgroup network policy and `cgroup.kill`/freeze; it is containment only together with a sandbox or forced egress (D-21).
6. **fanotify permission events are the no-reboot hold-for-approval path**, for tasks inside session scopes only (SR-15); BPF LSM cannot wait for a human. seccomp user-notification brokers launched trees, never with `CONTINUE` on pointer-bearing calls.
7. **In Kubernetes two tiers are chosen by `RuntimeClass`:** a privileged DaemonSet on runc nodes, and an unprivileged sidecar plus in-agent hooks plus forced gateway egress on gVisor, Kata and Fargate, where the host kernel sees nothing. A per-workload coverage ledger states which tier covered each pod (P9, g04).
8. **An ephemeral CI mode** installs as a first job step, enrols by the runner's OIDC token through workload identity federation (D-36), and flushes in the CI system's post-job hook; self-hosted runners need no licence (P11).
9. **Cloud agent runtimes and sandbox vendors are reached through connectors** (inventory, OTLP ingest, forced egress, policy export), never a host sensor, so they never exceed AL1 unless the vendor lets us run in-guest (D-13).

## Design

### 1. Capability probe and tier selection

`grdr-sensor-linux` runs one probe (`grdr doctor` exposes it) before loading any enforcement program and writes its result to `HostProfile` (03, 04) and `health.sensor` (04). It never keys on the distribution name: Ubuntu 26.04 carries `bpf` in the active LSM list from kernel 7.0.0-42.42 in `resolute-updates` while 22.04 and 24.04 GA do not, and the cloud and HWE flavours were still in `-proposed` on 2026-10-31 (14 verification row 1), so the only reliable source is runtime state. The probe reads: `/sys/kernel/security/lsm` (`bpf`, `landlock`, `apparmor`, `selinux`) and the lockdown mode (BPF load returns `EPERM` under `confidentiality`); `/sys/kernel/btf/vmlinux`; the kernel config from `/boot/config-$(uname -r)` or `/proc/config.gz` where present (`CONFIG_BPF_KPROBE_OVERRIDE`, `CONFIG_FUNCTION_ERROR_INJECTION`, `CONFIG_DYNAMIC_FTRACE_WITH_DIRECT_CALLS`, `CONFIG_FPROBE`); the Landlock ABI (`landlock_create_ruleset` with the version flag); fanotify features (`FAN_DENY_ERRNO` from 6.14, `FAN_PRE_ACCESS` 6.14, `FAN_MARK_MNTNS` 6.15, `fs.fanotify.watchdog_timeout` 6.18); `kernel.io_uring_disabled`, `kernel.unprivileged_bpf_disabled`, `kernel.apparmor_restrict_unprivileged_userns`; whether `bwrap` and `socat` are on `PATH`, and whether an unprivileged user namespace can be created, by a live test whose result decides over the sysctl (for the `delegate` check of §7); cgroup v2 and whether systemd owns the hierarchy; arch and page size; signed-BPF UAPI (6.18) and BPF token (6.9); and the trampoline-link count already in use on each attach point we need (the cap is 38 before v7.3 and 36 on x86-64, 37 on arm64 from v7.3, and stable backports may lower older trees; g05 verification row 6). Config files are hints only: each tier is confirmed by loading and attaching a no-op test program of that type (LSM, `fmod_ret` on `security_file_open`, kprobe with override, `cgroup_sock_addr`) and by creating a fanotify permission group, and that result decides. A `BPF_PROG_TYPE_LSM` load is never attempted while `bpf` is absent from the active list; this also avoids a reported panic in that state (CVE-2026-64192, from secondary sources only and not verified; 14).

The probe outputs, per action class, the highest available tier and the blocking it can do. Selection order (D-19), what each tier blocks, and the assurance values it supports (07 §11):

| Tier | Mechanism | Blocks synchronously | Cannot block | `control`, `on_failure` | Provenance (04 §9) |
|---|---|---|---|---|---|
| T1 BPF LSM | `bpf` in the active LSM list; LSM programs returning a negative errno | `exec`, `file.read`, `file.write`, `file.delete`, `net.connect`, `elevate`, `cred.use` on protected credential paths | `net.request` and `llm.request` content (proxy and gateway) | `mandatory-boundary`, `closed` (pinned, §6) | `mediated` for the deciding hook, `observed-kernel` for tracing |
| T2 `security_*` override | `fmod_ret` on `security_*` (needs a BPF trampoline: x86-64, or arm64 with `DYNAMIC_FTRACE_WITH_DIRECT_CALLS`; no error injection), else kprobe override (needs `BPF_KPROBE_OVERRIDE` and `FUNCTION_ERROR_INJECTION`, both built on Ubuntu 24.04 and 26.04) | As T1, for the `security_*` functions the attach test accepts | As T1 | `mandatory-boundary`, `closed` | As T1 |
| T3 cgroup net + fanotify | cgroup-v2 `connect4/6`, `sendmsg4/6`, `cgroup_skb/egress` (works with BPF LSM inactive); fanotify `FAN_OPEN_PERM`, `FAN_OPEN_EXEC_PERM`, `FAN_ACCESS_PERM` on the protected-path set only | `net.connect` by address and port; `file.read` and direct `exec` of marked paths | `file.write`, `file.delete`, rename, create, chmod (no permission event); `exec` through an interpreter; any path outside the marked set | Network: `mandatory-boundary`, `closed`. File: `mandatory-boundary` for marked paths only, `open` (closing the group allows every pending event) | `mediated` |
| T4 launch sandbox | Landlock and seccomp launcher for sessions we launch (§7); the `sandbox` control point, not the sensor | `exec`, `file.*`, `net.connect` (by destination only with the network fence of §7), `elevate` and io_uring inside the launched tree | Anything outside the tree | `scoped-boundary`, `closed` (irrevocable once applied) | `mediated` (`channel: sandbox`) |
| T5 observe | exec, fork and exit tracepoints; fentry on `security_*` in monitor mode; `cgroup_sock_addr` returning allow; procfs and the netlink proc connector where BTF is missing | Nothing | Everything | `none`; `visibility: observed` | `observed-kernel`; `observed-user` for procfs |

T1 and T2 are the only tiers that make AL4 reachable, because AL4 needs `mandatory-boundary` on `exec`, `file.write` and `net.connect` (07 §11). The probe never silently downgrades: a class that drops a tier emits a `health.coverage` record with reason `no-permission` and the probe's cause, and the assurance `control` field for that class falls to whatever the remaining control points support, `request` from a hook or `none` (P9). A kernel without BTF gets T5 through procfs and netlink only, reported as such.

**No-reboot guidance.** On Ubuntu 22.04 and 24.04 the probe finds `bpf` absent from the LSM list; on 24.04 the configs for both T2 routes are built, so a synchronous deny is reachable without the `lsm=` boot parameter (14 verification, read from source and not yet run on a live kernel; spike S-12 confirms it on both arches, and 22.04 is decided by the attach test). The console shows the `lsm=` guidance only where neither T1 nor T2 attaches; it never claims a reboot is required where T2 works.

### 2. eBPF program inventory

All programs are CO-RE (BTF-relocated), loaded through `aya` 0.16 / `aya-ebpf` 0.3.0 (`libbpf-rs` 0.27 under its BSD option is the fallback for a C skeleton, 03). Design to the verifier limits (512-byte stack, one million processed instructions, bounded loops). **No in-kernel string globs**: path and host matching is by inode-keyed, cgroup-keyed and session-keyed maps populated from user space, never string matching that hits verifier limits (14 §1); a changed path class is a map update, not a reload. Each enforce program is built twice from one source, as `lsm/<hook>` for T1 and `fmod_ret/security_<hook>` for T2, and the probe's result picks the variant.

| Program | Attach | Mode | Maps |
|---|---|---|---|
| `exec_trace` | `sched_process_exec` raw tracepoint; fentry on `security_bprm_check` for the resolved file | observe | `proc_lineage` (task-local storage: session tag, process key, copied at fork) |
| `fork_exit_trace` | `sched_process_fork`, `sched_process_exit` | observe | `proc_lineage` |
| `cgroup_sock` | `cgroup/connect4`, `connect6`, `sendmsg4`, `sendmsg6`, `cgroup_skb/egress`, multi-attached at the cgroup-v2 root | observe, and enforce after its own kernel review (R-40) | `net_scope_policy` (session tag → allowed address and port set), `dns_map` (name to address, written by the DNS interposer) |
| `lsm_file` | `file_open`, `inode_create`, `inode_unlink`, `inode_rename`, `inode_setattr`, `path_truncate` | observe, and enforce after the kernel review | `protected_inodes` (device and inode → class bits), `expectation_map` (session tag and tool-call id → effect descriptor, 07 §9) |
| `lsm_exec` | `bprm_check_security` | observe, and enforce after the kernel review | `exec_policy` (session tag → floor rows), `expectation_map` |
| `lsm_socket` | `socket_connect` | enforce, where T1 or T2 is present; backs `cgroup_sock` for sockets created before a scope moved | `net_scope_policy` |
| `lsm_task` | `task_kill`, `ptrace_access_check`, `bpf`, and `inode_unlink` on our bpffs pins | observe and enforce (Security and privacy) | `self_protect` (sensor process keys, our map and program ids) |
| `uring_guard` | the io_uring LSM hooks the running kernel has (at v7.3: `uring_allowed`, `uring_cmd`, `uring_override_creds`, `uring_sqpoll`; h02), found by BTF | enforce for contained sessions | `exec_policy` |
| `ipc_edge` | `unix_stream_connect` LSM hook (fentry on `security_unix_stream_connect` without BPF LSM) to broker sockets: Docker, Podman, systemd, D-Bus, tmux, screen | observe | `broker_sockets` (inode → broker kind) |

All observe programs write to one BPF ring buffer per event class (`exec`, `file`, `net`, `ipc`, `health`), so a flood in one class cannot drop another; each ring's drop counter goes into `health.sensor` (P9). Ring sizes are probe outputs, page-size aware (Tetragon carries a 64K-page case, 14 §11).

Enforcement programs never hold: a fail-closed class denies with a negative errno; a hold-for-approval verdict routes to fanotify or seccomp-unotify (§4). The `expectation_map` is how the OS control point honours a hook-issued expectation and grant with no user-space round trip (07 §9, 12 §8): the daemon compiles the expectation into the map; `lsm_exec` and `lsm_file` match the effect against it and the floor rows, and pass, deny, or pass and emit the effect for the engine to judge after the fact (a would-be verdict where the tier cannot wait). **Signed programs** are used where supported (6.18+, UAPI `signature`, `signature_size`, `keyring_id`) as hardening, not a trust anchor (the IPE policy layer is unmerged as of 2026-11-10, h02 verification row 9); on 6.9+ with systemd 258 the privileged installer may delegate narrow BPF rights to an unprivileged per-user daemon via a BPF token (`PrivateBPF=`), which never removes the privileged install step (14 §1).

### 3. Licence layout and the Rust/C split

The kernel programs live in `grdr-sensor-linux-bpf` (spine section 5, 03), licensed `GPL-2.0-only OR BSD-2-Clause`, with the object's licence string set to `Dual BSD/GPL` so LSM, struct_ops and kfunc users load (`bpf_lsm_verify_prog` rejects an LSM program without a GPL-compatible licence; 14 §1, 10 verification row 1). Everything else, `grdr-sensor-linux` included, is Apache-2.0. The kernel's licensing document permits packaging GPL BPF programs with non-GPL user space because they are separate executables, which is this layout (Tetragon ships it; Falco's driver is MIT or GPL-2.0). The bill of materials do-not-use list (03 §13) and `cargo deny` keep GPL and AGPL code out of the dependency graph (Kunai and Portmaster are GPL-3.0; KubeArmor's enforcer is GPL-2.0-only), and those repositories are on the agents' do-not-read list (D-02).

The Rust/C split: the programs are written in Rust with `aya-ebpf` (`#[lsm(hook = "...")]`, `#[tracepoint]`, `#[cgroup_sock_addr]`), not C, so one language and one fuzzing story cover kernel and user space. Whether `aya` handles Rust-side CO-RE relocation deeply enough, `lsm_cgroup`, sleepable LSM and `fmod_ret` programs is unverified (14 open questions, L-01); a program `aya` cannot express is written as a small C program loaded through `libbpf-rs`, isolated in its own directory of the same crate, under the same licence and the same verifier and differential tests. The crate is outside the default workspace members and builds with its own pinned toolchain; CI produces a signed `.o` that ships as a release artefact (ARCH-011), so `cargo build` on a contributor's machine needs no clang, `bpf-linker` or kernel headers. The user-space back end ships as a static musl binary on x86_64 and aarch64, a layout Kunai shows is viable with embedded `aya` programs (14 §13).

### 4. fanotify permission events and hold-for-approval

BPF LSM gives a race-free deny but cannot wait for a human; fanotify permission events hold the calling thread while user space decides (14 §3). The sensor marks only the inodes of the protected-path set (credential stores, agent control files, private keys: the same set as `protected_inodes`) with inode marks, never a mount or filesystem mark, because a stalled listener blocks every opener of a marked object. Events: `FAN_OPEN_PERM`, `FAN_OPEN_EXEC_PERM` (direct `execve` only, not interpreter reads), `FAN_ACCESS_PERM`, and `FAN_PRE_ACCESS` (6.14) with byte ranges; the reply is `FAN_DENY`, carrying a specific errno with `FAN_DENY_ERRNO` from 6.14. `FAN_REPORT_PIDFD` gives a race-free pidfd for attribution.

Who waits. The listener answers an opener outside every session scope at once from the floor table (allow, or deny for the agent-store class of SR-12), so only tasks inside a session scope can ever be held (SR-15, D-15). A held request goes to the engine as a `STEP_UP`; the hold lasts at most 30 seconds (D-07), after which it becomes a denial with a retry token (07 §3), so an approval that arrives later mints a grant for the retry.

Gaps the design works around (14 §3, h02): no permission event for unlink, rename, create, chmod or write, so `file.write` and `file.delete` need T1 or T2 and are `control: none` where only fanotify is present; mmap access is seen only at map time (the page-fault pre-content hook was reverted in 6.14), so a mapped protected file is treated as fully read; closing the group replies `FAN_ALLOW` to every pending event, so this path is `on_failure: open`; the kernel watchdog (6.18, `fs.fanotify.watchdog_timeout`, off by default) only logs, so the daemon runs its own watchdog that answers every event before the cap and raises a tamper finding when the listener stalls. In the Protected profile the installer sets the kernel watchdog when it is 0 and journals the change for uninstall (D-49). The listener exempts the sensor's own processes, never opens a marked file while deciding, and removes pre-content marks before a filesystem freeze (freeze can deadlock pre-content listeners, h02).

**seccomp user-notification** brokers trees we launched (§7): `SECCOMP_RET_USER_NOTIF` with `WAIT_KILLABLE_RECV` (mandatory for Go agents, whose signal-based preemption otherwise cancels notifications). It is never used with `FLAG_CONTINUE` on pointer-bearing calls, where the man page says it is not a security mechanism (the target can rewrite arguments while blocked); the supervisor performs the `openat` or `connect` itself and injects the descriptor with `ADDFD`, and every memory read is bracketed by `NOTIF_ID_VALID`. A filter installed later by the target with higher precedence can pre-empt ours, so the launcher's static filter denies the dangerous calls outright and unotify is used only for calls that need a decision.

### 5. cgroup BPF network control

cgroup-v2 network hooks work with BPF LSM inactive, so this is the network enforcement tier wherever BPF loads, enforcing in the Protected profile once its own review is done (R-40; 14 §6). The programs are multi-attached once at the cgroup-v2 root and look up policy by the task's session tag, so a process that leaves its scope through a lineage escape (§8) keeps its policy; `connect4/6` and `sendmsg4/6` enforce the session's allowed address and port set (`net_scope_policy`) and `cgroup_skb/egress` backstops. Processes with no session tag are never filtered. We do not use systemd's `IPAddressAllow=`, `SocketBindAllow=` or `RestrictNetworkInterfaces=` on agent scopes: they would be a second policy source the engine cannot see.

DNS is resolved by rewriting port-53 `connect4`/`sendmsg4` from tagged tasks to a local resolver in the daemon that records name to address in `dns_map`; the allowed set for a host class is the addresses that resolver returned for its names. DoH, DoT and QUIC to unknown addresses are denied by the same default and otherwise go to the proxy or gateway (D-16, 07 `proxy`). The connect deny is a `mandatory-boundary` over addresses and ports. A host-class allow built from learned addresses over-allows names that share an address (CDN, domain fronting; g04 §6, §7), so rules that name hosts are evaluated at boundary grade only where the session's egress is forced through our proxy or gateway, which see SNI and Host; elsewhere the receipt records the host match as address-derived.

### 6. BPF LSM and the no-reboot fallbacks

T1 is the preferred deny: race-free, system-wide, and scoped by session tag inside the program (14). `SIGKILL` is not a block, because the in-flight syscall may complete (Tetragon's documentation, 14 verification row 3), so the sensor never relies on kill; `cgroup.kill` and freeze are response actuators (D-30), not tiers. When T1 is absent the fallback order is the tier table of §1 (T2, T3, T4, T5), and the console states the gap for each class left at T5. Two rungs of the research ladder (14 implications) are not adopted: generated AppArmor or SELinux profiles (per-binary rather than per-session, symlinked paths do not match, and they would rewrite a policy the distribution or another product owns, against D-23), and kill as a substitute for deny.

**Enforcement survives loader death** (D-19, R3). Upstream has no agreed fix for user-space tampering with BPF LSM state: programs are reference-counted and unload when the loader's descriptors close, maps are writable from user space, signing does not stop unloading, and pinned objects can still be unpinned by privileged user space (h02 LSFMM+BPF 2026 and verification row 4). The design therefore:

- pins every enforce program, link and map in a bpffs instance under `/sys/fs/bpf/grdr/`, so the daemon's exit or crash changes nothing in the kernel;
- keeps the floor rows and `protected_inodes` in the maps when the daemon is absent, so fail-closed classes keep denying; `expectation_map` entries carry an expiry checked in-kernel, so stale expectations lapse rather than allow, and with no daemon an unmatched effect in a fail-closed class is denied and everything else follows the pack's `on-sensor-loss` setting (D-15);
- uses `lsm_task` to deny map updates, program and link detach, map and program fd lookups by id, and unlink of our pins to every task outside `self_protect`, and to deny `kill` and `ptrace` of sensor processes from agent lineage;
- hands pins over on update by loading the new programs, atomically replacing links with `BPF_LINK_UPDATE`, then removing the old pins, so an update never opens a gap (D-15).

Against agent-lineage tasks this is prevention; against an administrator it raises the cost and every attempt is a tamper finding, because root can still remove the protection by other routes (a kernel module where not locked down, a reboot without `bpf` in `lsm=`, or our own uninstall), so the record's `tamper` value stays `admin` (D-22). Tetragon's silent enforce-to-monitor downgrade on a pin-path collision (h02) is the failure to avoid: enforcement mode is asserted per hook in every `health.sensor` heartbeat, never assumed, and a collision or a missing link is a tamper finding. Kernel enforcement (T1 to T3 in enforce mode) leaves the internal ring only after the kernel review of D-62: `eval-security` and `eval-adversarial` in clean contexts on different models, plus any free external audit that arrives (D-19, D-63). `cgroup_sock` is reviewed on its own, separately from the other enforce programs, because the launch sandbox's network boundary depends on it (R-40). On a host where no reviewed kernel enforcement is enabled, the only Linux denials come from hooks, the launch sandbox and, once its review is done, `cgroup_sock` network policy for session-tagged tasks.

On ARM64, LSM and fentry attach need `CONFIG_DYNAMIC_FTRACE_WITH_DIRECT_CALLS` (else `ENOTSUP`); where absent the probe drops to T3 or T5 and reports it. Lockdown in `confidentiality` mode blocks BPF load entirely, so the host keeps only the fanotify half of T3, T4, and T5 through procfs.

### 7. Landlock and seccomp launcher

T4 is the Linux `SandboxBackend` (03): `grdr-run` launches a process tree into a Landlock and seccomp sandbox we own, with no user-namespace dependency except the optional network fence of the Network rule below (unlike bubblewrap, which Ubuntu 24.04+ breaks through `apparmor_restrict_unprivileged_userns`; 14 §11, §14). It runs in both install profiles because it needs no privilege. Landlock is ABI-gated: the launcher uses only features the probe found (ABI 6 = 6.12 scopes, 7 = 6.15 audit, 8 = 7.0 all-thread restriction, 9 = 7.1 pathname UNIX sockets, 10 = 7.2 UDP, 11 = 7.3 no-new-privs, verified; 12 is in 7.4-rc only; ABI 4 = 6.7 for TCP ports is from prior knowledge, not re-verified; 14 §5 and verification row 5). By kernel that gives ABI 4 on Ubuntu 24.04, 6 on Debian 13 and RHEL 10, and 8 on Ubuntu 26.04 (14 §5, inferred from kernel versions). Landlock is allow-list only (it cannot carve `~/.ssh` out of an allowed `$HOME`, so the workspace and tool directories are allowed rather than `$HOME`), has no control of `stat`, `chmod` or `chown`, and does not affect inherited descriptors (14 §5). The launcher applies it in a single-threaded pre-exec step, so the pre-ABI-8 per-thread limit does not apply.

The profile, compiled from the session's policy at launch:

- **Files:** Landlock read and write rules over the workspace and the agent's declared paths; protected paths are simply not granted.
- **Network:** proxy variables point the tree at our local proxy listener (D-16), which resolves names and applies the egress profile. Landlock network rules match ports, not addresses (14 §5), so at ABI 4 and above TCP connect is limited to the proxy's port as hardening only; the boundary over destinations comes from the Protected profile's `cgroup_sock` program keyed on the session tag (§5), which allows only the proxy and enforces only after its own review under D-63 (R-40). UDP is denied, by Landlock from ABI 10 and below it by the seccomp filter refusing `SOCK_DGRAM` sockets for `AF_INET` and `AF_INET6`. Without that program (User profile, no BPF, or before its review), the launcher adds an empty network namespace whose only exit is a UNIX-socket bridge to the proxy listener (as in 17 section 2), before the seccomp filter applies, where unprivileged user namespaces are available; `grdr-run` itself runs the forwarder inside the namespace, so no extra package is needed, and the bridge's socket path is in the allowed set of the UNIX-socket rule below. Elsewhere `net.connect` in the sandbox is `control: request`. In the User profile every control is reported as a request (D-48).
- **UNIX sockets:** at ABI 9 and above, pathname sockets outside the allowed set are denied by Landlock (the gap Codex cites for rejecting its legacy Landlock path; 14 verification row 6); below ABI 9, `connect` on `AF_UNIX` goes to seccomp user-notification, where the supervisor checks the path and connects on the tree's behalf (§4). Container-runtime and systemd manager sockets are denied by default (D-22 `elevate`).
- **seccomp:** a static filter denies `io_uring_setup`, `io_uring_enter` and `io_uring_register` (§8), `unshare`, `setns`, `mount`, `pivot_root` and namespace-creating `clone` flags, returns `ENOSYS` for `clone3` (whose flags seccomp cannot inspect), as `sandbox-runtime` does (14 §14), and sets no-new-privs.

This is the `scoped-boundary` control level of the assurance record (07 §11) for the classes the sandbox conformance suite proves on that ABI (D-21); a class the suite does not prove on the running ABI stays at the level the other control points give.

**Containment modes** (D-21), chosen per agent from the catalogue and opt-in per agent until the developer-workload corpus passes inside it:

- `delegate`: configure and lock the agent's own sandbox (Codex's bubblewrap and seccomp, Claude Code's sandbox, which covers Bash-type commands only; 14 verification row 7), and verify at each exec that the tool subprocess is inside it (the `Seccomp` field of `/proc/<pid>/status` and the links in `/proc/<pid>/ns`); a tool subprocess outside it is a `sandbox-bypass` tamper finding. Before Claude Code's sandbox is locked on, the probe (§1) checks that `bwrap` and `socat` are installed and that unprivileged user namespaces work (§1 already reads `kernel.apparmor_restrict_unprivileged_userns`); where they do not, Claude Code's sandbox is not locked on (it would run its commands unsandboxed unless `sandbox.failIfUnavailable` is set; research brief 15, verification row 6) and no `sandbox-bypass` is raised. The agent then falls back to `wrap-tools` through the hook rewrite into our Landlock launcher. Its file and syscall rules need no user namespace; its network fence needs the reviewed `cgroup_sock` program or a user namespace (Network rule above), so where namespaces are blocked `net.connect` stays a request unless that program has passed its review. The rewrite counts as unproven while a foreign pre-tool hook on the shell event leaves its outcome non-deterministic (07 section 7). The agent stays at request level with the reason stated only if the launcher's probe fails or the adapter cannot prove the rewrite for that Claude Code version (D-21). The deb and rpm packages recommend `bubblewrap` and `socat` (24).
- `wrap-tools`: tool subprocesses are launched in our sandbox through a hook rewrite of the shell call into `grdr-run --session <id> --tool-call <id>`, which fetches the evaluated command from the daemon (08 section 5, route 4). For Claude Code on Linux (the `delegate` fallback) this covers the commands of its Bash tool and their descendants, run under the profile above in the session's cgroup scope. As on Windows (08 section 5), it does not cover Claude Code's own process: Read, Edit and Write stay at `request` for `file.write` unless a kernel tier enforces, and local MCP servers, hooks, language servers, WebFetch and `!` commands are outside it. `net.connect` follows the Network rule above. A tool-shaped child that does not carry the rewritten command raises `effect-mismatch` (07 section 9).
- `wrap-agent`: `grdr run <agent>` puts the whole agent in the sandbox, for agents with no sandbox of their own or whose own sandbox S-11 shows still applies inside ours (D-21). Where the agent has a process-wrapper setting that it honours on Linux (Claude Code's `processWrapper`), that setting starts the agent and its self-spawns under `grdr run --contain` (D-21, 28 DX-26).

Nesting is a per-agent decision, not an assumption (c3 F5, spike S-11): our `mount` and namespace denials would break an inner bubblewrap. With the profile above an inner bubblewrap cannot pass: the seccomp filter denies its namespace and mount calls, and Landlock's file rules deny `mount` and `pivot_root` (c3 F5). So an agent whose own sandbox is bubblewrap, such as Claude Code or Codex, stays in `delegate` on Linux (Claude Code falls back to `wrap-tools` on a host where its bubblewrap cannot run, as in the `delegate` bullet) unless a per-agent profile that allows those calls passes the sandbox conformance suite and S-11; no document defines such a profile. The launcher probes first; an agent whose inner sandbox does not survive inside ours is fixed to `delegate`, falls back to `wrap-tools` where its own sandbox cannot run on the host, and stays at request level with the reason stated only if that also fails (D-21). Adopting an agent that is already running gives attribution, not containment; the console offers "restart contained", and, where containment is on for that agent and OS, credential release to uncontained sessions is refused by default (D-21, P13). NVIDIA OpenShell and similar governed runtimes are recognised as a `delegate` back end and a posture fact (D-21).

### 8. io_uring and per-session cgroup scopes

**io_uring** bypasses syscall-tracepoint sensors (ARMO's Curing evaded Falco and default Tetragon, and Defender for Endpoint on Linux missed it; 14 §8). The design never hooks `sys_enter_*`: it hooks the LSM file and socket layers that io_uring operations still traverse, so file and network policy still apply at T1 and T2. There is no per-opcode io_uring hook; the io_uring-specific LSM hooks at v7.3 are `uring_override_creds`, `uring_sqpoll`, `uring_cmd` and `uring_allowed` (h02), and `uring_guard` (§2) uses whichever the running kernel has to deny io_uring to contained sessions where policy says so. The launch sandbox (§7) denies io_uring outright (D-19). At T3 and T5 an io_uring operation is judged only where it reaches a cgroup hook or a fanotify mark, which the record states. `kernel.io_uring_disabled` (0, 1 or 2, with `io_uring_group`; 14 §8) is offered as host hardening and never set by the sensor without the operator's opt-in.

**Per-session cgroup-v2 scope** (D-19, D-21, D-25): every session-exclusive session (a CLI agent, `grdr run`, a process wrapper) gets one cgroup-v2 scope. Where systemd owns the hierarchy, the daemon asks systemd over D-Bus for a transient scope unit (`grdr-ses-<id>.scope`) in the user's slice and passes the root process by pidfd, so we never write into a hierarchy systemd manages; where it does not (containers, WSL2 without systemd, CI images), the daemon creates the cgroup under its own delegated subtree. The root process arrives from `grdr run` or from an in-agent hook handing the daemon a pidfd at session start (adoption); on adoption, descendants that already exist are tagged by walking the pidfd tree, and observed or adopted sessions are moved into a nested scope only where SP-06-1 shows that is safe, otherwise they are tag-only (06 section 3 and its objection to D-19). The cgroup id is the attribution anchor that survives double-fork, `setsid`, `nohup` and `sudo` (14 §10), and the unit for `cgroup.kill` and freeze (the `Actuator` verbs, D-30). The session tag in task-local storage, copied at fork, is the policy key of `net_scope_policy`, `exec_policy` and `expectation_map`, so a process that leaves the scope keeps its policy. This scope is **attribution and the policy key only**; it is containment (a scoped boundary) solely when a sandbox (§7) or forced egress (§5) also applies (D-21).

Lineage escapes are followed per the escape table (14 §10): `systemd-run`, user timers and D-Bus activation (the `ipc_edge` hook on a tagged task's connect to the manager socket, then the next unit created is tagged); cron, at, shell rc files and git hooks (files written by tagged tasks are recorded by inode, and a later exec or open of them is an `influenced-by` edge); tmux and screen (UNIX-socket peer edge; server children after a tagged client attaches are tagged); the Docker and Podman sockets (`elevate`, denied from contained sessions, and otherwise the container's cgroup is mapped to the requesting peer); ssh to localhost (correlate the loopback four-tuple from a tagged connect to the sshd accept); `kubectl exec` (Kubernetes audit and CRI exec correlation, §10). These edges are `session.link` events with kind `ipc`, `brokered` or `influenced-by` (04 §4, 06); agent environment markers and process names are hints, never proof.

### 9. WSL2

WSL2 runs the same back end inside the WSL VM (g04). Since `linux-msft-wsl-6.18.54.1` (2026-10-06) the WSL2 kernel ships `bpf` in the active LSM list, so T1 is available; before that no WSL2 kernel had both halves on, so the probe decides per kernel (14 verification row 2). kprobe override is unavailable on both arches (x64 lacks `CONFIG_FUNCTION_ERROR_INJECTION`; arm64 has it but leaves `CONFIG_BPF_KPROBE_OVERRIDE` unset), and `CONFIG_FPROBE` is unset on both. `fmod_ret` on `security_*` needs only a trampoline, so on older WSL2 kernels (6.6.y, 6.18 before .54.1) T2 is available where the probe's attach test succeeds and the sensor is otherwise T3 or T5. Users on a custom WSL kernel get whatever the probe finds. The Linux sensor links to the Windows host device by the host's device id, as Defender's WSL plug-in does with `HostDeviceId`, reported in `inventory.device` (04); the join is ours because no vendor identity interoperates (08 owns the Windows side). Short-lived WSL instances must register and ship a first event quickly, where Defender's plug-in can take up to 30 minutes (g04 §5): the target is a first event acknowledged within 15 seconds of the instance starting. The instance is its own device; the Windows sensor hands it a single-use enrolment token at start (22 §4), so registration needs no user step, and in standalone the instance joins the host's local organisation.

### 10. Kubernetes and sandboxed container runtimes

Containers on a single Linux host with no orchestrator are cgroups the host sensor already sees; their `img:` identity and per-container instance are 05 section 9. The host kernel is blind inside sandboxed pods, and Google says so in writing: host-kernel tools cannot observe syscalls in gVisor or microVM sandboxes (g04). Coverage is therefore reported per workload by `RuntimeClass`, never assumed (P9). Two tiers, chosen by `RuntimeClass`:

**Privileged DaemonSet tier (runc nodes: EKS EC2, GKE Standard, AKS, self-managed).** The same Rust sensor runs as a DaemonSet, CO-RE eBPF, capability-scoped (`CAP_BPF`, `CAP_PERFMON`, `CAP_SYS_RESOURCE`, `CAP_SYS_PTRACE`; `CAP_SYS_ADMIN` fallback on older kernels), `hostPID`, mounting `/sys/fs/bpf`, `/sys/kernel/btf`, `/sys/kernel/security`, `/proc` and the CRI socket, `tolerate-all`, `system-node-critical`. A `controller` Deployment watches Pods, Namespaces, ServiceAccounts and `agents.x-k8s.io` CRs to build the identity cache. The per-node startup probe reports the enforcement tier exactly as on an endpoint, and this tier reaches T1 to T5 as the node kernel allows. Each node is one device, enrolled by its projected service-account token through workload identity federation (22 §4, D-36), with update authority `image` (22 §6.6); pods are workloads on that device, not devices. The node sensor uses the same acknowledged batch upload as an endpoint, and may stream instead, since D-36 allows streaming for node sensors.

**Unprivileged sidecar tier (gVisor, Kata, Fargate: the "no-kernel tier").** An unprivileged native sidecar (an `initContainer` with `restartPolicy: Always`, on by default since Kubernetes v1.29 and stable in v1.33, so it starts before and outlives the agent container) provides the hook shim and broker for in-agent hooks, sets `HTTPS_PROXY` to the cluster gateway, and exports OTLP. Whether Landlock and seccomp user-notification work inside gVisor and Fargate is unverified (g04 open questions); the sidecar uses them only where its own probe proves them. Each sidecar is an ephemeral device (workload identity plus pod uid, 04 §3), enrolled by projected token. For self-managed `runsc`, a node-level consumer of the gVisor `seccheck` remote sink (asynchronous, so observe-only; the trace-point count is read from `runsc trace metadata` at run time, since the README's 998 is a sample, g04 verification row 3) feeds the same pipeline with `is_exec_session` enabled to separate `kubectl exec` humans from the workload; no maintained open-source consumer of `seccheck` remains since Falco removed its gVisor engine in 0.44 (g04 verification row C). For Kata, a guest image with the sensor baked in, or the sensor as a privileged sidecar against the guest kernel, which GKE documents for microVM pods (g04 verification row 1). On Fargate nothing privileged exists (no DaemonSets, no privileged containers, no Arm), so the sidecar tier is the ceiling (g04 verification row 2).

**The coverage ledger** is, per workload, the `assurance.record` of each agent instance in it (07 §11) plus a `health.coverage` record naming the RuntimeClass, the tier that covered it, and the classes left at `control: none` or `visibility: claimed` with reason `no-permission`, keyed by the identity tuple below (P9, g04 whitespace). A pod of an agent RuntimeClass with no sidecar and no node coverage appears as `visibility: none`, so a missed injection is visible. A sandboxed pod shows the dangerous case plainly (LLM-generated code runs exactly where the DaemonSet sees nothing) rather than a false green.

**Admission** is for placement and injection only, never the runtime control. Injection is by a `SandboxTemplate` overlay where agent-sandbox is used, and otherwise by a mutating webhook with `failurePolicy: Ignore`; an admission webhook is an availability risk in other people's clusters, so none of ours is ever `failurePolicy: Fail` and none is mandatory. Validation is by `ValidatingAdmissionPolicy`, which cannot mutate: it rejects bare Sandboxes that leave `automountServiceAccountToken` on, as agent-sandbox's threat model recommends, and can warn on agent pods without the sidecar. VAP is GA in 1.30; on 1.29 it is beta and off by default, so there the chart installs no validation and the ledger carries the gap (g04 verification row B).

**Network policy.** CNI default-deny egress for agent pods, allowing only DNS and the gateway Service; the gateway holds provider and tool credentials so a bypass yields nothing; our node sensor attributes each connection to pod and process and alerts on direct-to-provider traffic. The managed NetworkPolicy of `kubernetes-sigs/agent-sandbox` blocks sidecar ports by default (g04), so the sidecar port is opened explicitly through a `SandboxTemplate` overlay.

**The agent-sandbox project** (`kubernetes-sigs/agent-sandbox` v1.0.10, Apache-2.0, orchestrator only, isolation delegated to gVisor/Kata via `RuntimeClass`) is integrated, not replaced: it has no runtime telemetry or policy hook, and that gap is ours to fill. Identity handles on its pods: the label `agents.x-k8s.io/claim-uid` and annotation `agents.x-k8s.io/claim-name` on SandboxClaim-owned pods, `agents.x-k8s.io/warm-pool-sandbox` on warm-pool pods, and `agents.x-k8s.io/sandbox-name-hash` on every pod (the only universal key); bare Sandboxes carry neither claim key (g04 verification row 4).

**The identity tuple** (g04 §3), carried on every container-origin event: `cluster_uid`, `namespace`, service account name and uid, `pod_uid`, `container_name`, `image_digest`, owner (Sandbox or SandboxClaim uid), `runtime_class`, `node`, `spiffe_id`, cloud principal, `exec_id`, and our session id. The device is the node for DaemonSet events and the sidecar's ephemeral device for sidecar events (04 §3); the agent instance is keyed on the workload, not the pod (04 §3). The SPIFFE id and cloud principal map to the OCSF `ai_agent` and actor; tool calls map to the `adr` extension's back-port of `ai_capability` until OCSF 1.10 releases, because the 1.9.0 `ai_operation` profile has `ai_agent`, `ai_model`, `delegation` and `message_context` only (g04 verification row 9, 04 §14). Source identities join through SPIRE k8s selectors (`k8s:ns`, `k8s:sa`, `k8s:pod-uid`, `k8s:pod-label`, `k8s:container-image`, Sigstore `k8s:image-signature:*`) and PodCertificateRequest where available (GA in v1.37, the newest minor, so absent on most managed clusters; pod, service account and node name and uid; 24 h default lifetime); elsewhere the join key is ours, because Entra, Google and AWS agent identities do not interoperate (g04). Baseline is Kubernetes 1.29 (CRD CEL validation stable, matching agent-sandbox); OLM bundle for OpenShift with documented SCC exemptions; namespace-scoped install for tenants without cluster-admin.

### 11. Ephemeral CI mode

Hosted CI runners are root-capable ephemeral VMs (GitHub: passwordless sudo, fresh VM per job; GitLab.com: passwordless sudo, VM deleted after the job, 3 h cap), so a first job step restores the sensor package, pack store and intel base from the CI system's cache keyed by the pinned digest (downloading only on a miss, from the first working source in `updates.sources`) and installs the full sensor in the Protected profile; the exception is GitHub `ubuntu-slim`, an unprivileged container on a shared VM with a 15-minute job limit, where only proxy environment and hooks apply (g04 verification row 6). CI mode is the ordinary daemon with three differences: it enrols by federation instead of a stored token, it keeps no flight recorder beyond the job, and it flushes the spool and a signed going-down event in the CI system's post-job hook. The target is install-to-first-acknowledged-event under 15 seconds at p95 on a hosted runner. A job cancelled before the flush loses events after the last acknowledged batch; the server sees a session with no going-down event and records a `health.gap` for it rather than a clean end. Per CI system:

| CI | Install and flush points | Identity (OIDC) | Coverage |
|---|---|---|---|
| GitHub Actions | A first-step action with a `post` step (hosted); image-baked or the DaemonSet for ARC and self-hosted | `id-token: write` → `sub` `repo:ORG/REPO:...`, `job_workflow_ref`, run, job and attempt ids | Kernel tiers on hosted and self-hosted VMs; proxy and hooks on `ubuntu-slim` and container jobs |
| GitLab CI | A CI/CD component whose `before_script` installs and `after_script` flushes | `id_tokens` → `sub` `project_path:{group}/{project}:ref_type:...`, `project_path`, `pipeline_id`, `job_id`, `runner_environment` | Kernel tiers on hosted and self-hosted VMs |
| Buildkite | A plugin using the `environment` and `pre-exit` hooks (self-hosted and Linux hosted agents; not macOS hosted; on Agent Stack for Kubernetes hooks run in separate containers and exported variables do not cross containers, so the DaemonSet covers it) | `buildkite-agent oidc request-token --audience ...` → `sub` `organization:...:pipeline:...:ref:...:commit:...:step:...`, build, job and agent ids | Kernel tiers on self-hosted; hooks on hosted Linux where the plugin cannot install the sensor |

The device identity comes from the CI OIDC token through workload identity federation (D-36, 22 §4): the ephemeral device id is workload identity plus instance id (04 §3), the record expires after the job (22-14), update authority is `image` (the action pins a sensor version by digest), and a repeated id with a divergent chain is a clone finding (D-36). Session attribution inside the job uses the same scopes as an endpoint; an agent step started through `grdr run` is session-exclusive.

The recommended pattern for agents in CI is gh-aw's "stage, inspect, then externalise" (g04 §4): the agent runs in a job with a read-only token, under `grdr run` with egress limited to our proxy and the hosts in its egress profile, with MCP servers behind the broker; it writes its outputs to an artefact; a separate job without the agent inspects them, and only that job holds write credentials. The action and component ship this as a template. Self-hosted runners, ARC and private repositories need no licence check (P11).

### 12. Cloud agent runtimes and sandbox vendors through connectors

Cloud agent runtimes (AgentCore Runtime on its default microVM compute type, Foundry hosted agents, Vertex/Gemini Agent Runtime) and sandbox vendors (E2B, Daytona, Modal, Vercel, Cloudflare) give no customer kernel access, so they are reached through connectors, never a host sensor, and their instances never exceed AL1 (D-13, g04). The per-class record still shows the gateway's control over `llm.request` and `mcp.call` where egress is forced through it (07 §1). Four connector shapes (D-40 owns the connector framework; this document names the Linux-adjacent ones):

- **Inventory and audit ingest**: cloud audit logs (CloudTrail, VPC Flow Logs) and vendor OTLP (Foundry to Application Insights, Vertex to Cloud Trace), at provenance grade `reported` for audit logs and `claimed` for agent-emitted telemetry (04 §9).
- **Forced egress**: set the vendor's network policy so traffic reaches our gateway. Vercel `forwardURL` sends each request with an OIDC token carrying `sandbox_id`, which the gateway validates; Daytona's `outboundProxyUrl` points at the gateway. E2B (`allowOut`, `denyOut`) and Modal (CIDR and domain allow-lists) document no forwarding proxy, so the connector allows only the gateway's address and sets proxy variables inside the sandbox, which is a request (g04 §6).
- **Policy export**: compile our Cedar policy to AgentCore Policy (Cedar or Dogwood), and to `MCPRoute` rules or agentgateway CEL in-cluster, as compile-down targets under D-12's soundness rule.
- **In-guest, unverified**: AgentCore's Instances compute type runs a session on a dedicated EC2 managed instance in the customer's account and VPC for up to 14 days, with several agents per session and no isolation between them (g04 verification rows 7 and A). Customer permissions on the instance are restricted and whether a host sensor can be installed is not documented (L-04). If it can, the instance is an ordinary Linux endpoint and exceeds AL1 on that basis; attribution between its agents is `undetermined` unless their processes are separable.

Sandbox vendors expose no decision stream (E2B, Daytona and Docker document no audit feed; Modal writes blocks to sandbox stdout), which is the open "sandbox-telemetry contract" whitespace (g04); we consume what each offers and report the rest as `visibility: claimed` or `none`.

### 13. Packaging

Endpoint, x86_64 and arm64: signed `deb` and `rpm` repositories built with `nfpm` 2.48, a signed static musl tarball for other distributions, and, for the Protected profile, one systemd system unit for the daemon with socket units for its listeners (D-48, D-59; 24 section 3). The daemon runs as root with the binaries, policy, spool and socket directory root-owned and spawns the other processes of the one topology (D-20; 11 section 1), `grdr-engine` under its own account inside the sandbox 11 specifies. The User profile installs nothing privileged and runs the daemon as a `systemd --user` unit with no BPF and no fanotify: observation comes from procfs (`observed-user`), and only hooks and the T4 launcher can act. Install is silent, idempotent and offline-installable at default paths, with no enrolment secret on the command line (D-59); uninstall removes our pins and links and restores every journalled change (D-48). The prebuilt signed BPF object ships in the package. `grdr doctor` reports the probe result, the chosen tier per class, slot owners (§15) and overhead by program, in the manner of `mdatp diagnostic ebpf-statistics` (g05). A host with more than one human uid holding logind sessions is a multi-session host, which the Protected installer refuses unless it has per-logon-session listeners (D-59); build servers and nodes with no interactive sessions are not affected.

Kubernetes: the node sensor has its own Helm chart, separate from the server chart (D-59), with values selecting the tier (`daemonset`, `sidecarOnly`, `gvisorSink`); an OLM bundle for OpenShift; CRDs kept to policy and identity mapping; no mandatory webhook; and a namespace-scoped install for tenants without cluster-admin. CI: a GitHub Action, a GitLab component and a Buildkite plugin (§11), each pinning the sensor image by digest. The kernel programs are never shipped as a kernel module: the kernel will not export symbols without an in-tree user, and no path for out-of-tree tracers was agreed (h02, LWN 2026-10-14); CO-RE BPF only. Immutable hosts (Bottlerocket, Talos, COS, Fedora CoreOS) take the sensor only as a container or DaemonSet, or through the host's own extension mechanism where it has one (14 §11).

### 14. Kernel test matrix

Every release runs the matrix (D-64 owns the lab; this is the Linux slice). There is no money for lab hardware, so the matrix runs on free hosted CI runners for the public repository (tier A) and, optionally, self-hosted runners (tier B). Tooling is Apache-2.0 and free: `cilium/little-vm-helper` (prebuilt kernel and rootfs OCI images from `quay.io/lvh-images`, arm64 cross-build) and `danobi/vmtest` (one command per kernel), with `libbpf/ci` Actions (g05). GitHub Linux x64 runners expose `/dev/kvm` after a udev rule (tier A). arm64 cells run on the free hosted arm64 Linux runners where they expose KVM, which is unverified (g05 verification row 8); otherwise they run on an arm64 tier B runner where one is available, and cells no available machine can run are marked "requires hardware" and run when one is available (D-64).

The matrix cells, each a probe and enforce fixture: Ubuntu 22.04 (5.15), 24.04 GA (6.8) and one cloud flavour, 26.04 at 7.0.0-38 (no `bpf`) and at the current update (with `bpf`); Debian 13 (6.12); CentOS Stream 9 and 10; Amazon Linux 2023; Bottlerocket; Talos; WSL2 6.6.y and at least 6.18.54.1; a kernel with lockdown `confidentiality`; a kernel without BTF; x86_64 and arm64 for each where images exist. Per cell the fixture asserts:

- the probe's tier per class matches a live attempt (§ Test and evaluation strategy);
- a deny lands synchronously wherever the tier claims one;
- a fanotify hold does not stall the host when the listener stalls or dies, and pending events resolve within the 30-second cap;
- enforcement survives the daemon's death, and a map write, link detach and pin unlink from a root task outside the sensor are denied and raise tamper findings (T1 and T2 cells);
- overhead stays under the section 6 target of 3% on a kernel build (target; Tetragon's 2023 vendor figure of 1.68% for exec tracking is the public reference, h02);
- every program, including agent-written ones, passes the verifier (S-13, D-63).

gVisor cells use `seccheck`; Kata cells use a guest image. Agent-written BPF runs this verifier loop on every pull request that touches the crate, including on livepatched kernels and on kernels carrying other vendors' programs on the same hooks (Tetragon and Falco, both open source), because LLMs struggle with the verifier (h02). MDE's Linux documentation lists kernels on which it panicked or hung (g05 verification row 9); those kernels join the matrix when images are available.

### 15. Coexistence with other eBPF security agents

Coexistence is designed and tested (D-23, g05). The slot broker (03) probes each shared Linux slot at start, records owner and outcome in `HostProfile` and `grdr doctor`, and degrades per D-23: enforce, observe, or ingest the incumbent's telemetry (Tetragon over gRPC, Falco alerts) where our programs cannot attach.

- **BPF LSM programs on one hook run in sequence and see the previous program's return value** (g05 §Linux), so we combine deny-wins: our program never turns another program's denial into an allow, and adding our deny never needs another vendor's cooperation.
- **Trampoline-link budget**: all fentry, fexit, `fmod_ret` and LSM programs on one function share 38 links before v7.3, and 36 (x86-64) or 37 (arm64) from v7.3; stable backports may lower older trees, and an fsession program counts twice (g05 verification row 6). The probe counts links in use per function we need; we attach at most two programs per function (one observe, one enforce), and a full hook is reported as `hook-full` in `health.sensor` with the class dropped a tier, never by evicting anyone.
- **The audit netlink socket has one consumer**, and osquery's `--audit_persist` retakes it, so the sensor never uses it (g05 §Linux); Defender for Endpoint on Linux dropped AuditD as a provider and falls back to netlink process events where eBPF is unavailable (g05 verification row 9).
- **No exclusive slots**: no audit netlink, no legacy `tc` priorities (TCX or cgroup hooks only), no injection, no `LD_PRELOAD`, no rewriting of AppArmor or SELinux policy.
- **fanotify permission listeners** are ordered by class (pre-content, then content, then notification) with undefined order inside a class (g05 §Linux), so another product's permission listener adds latency to ours and ours to theirs; `grdr doctor` reports the measured added latency on marked paths.
- Other security products' processes, identified by the coexistence data in the content pack, are muted in our tracers to avoid feedback loops.

Each release ships a **coexistence pack**: our BPF program and map names, pinned paths, process paths, loopback ports, systemd unit names, and ready-made exclusion snippets for named incumbents, plus a **ceiling matrix** (OS, agent, incumbent → reachable assurance). The matrix is proven by an interference test against Defender for Endpoint on Linux, Falcon and at least one more incumbent before broad release (D-23). Licences for Falcon and the further incumbent come only through design partners or free vendor test programmes (D-64); until one is available, the matrix row for that incumbent is marked untested rather than claimed.

## Interfaces and contracts

- **`SensorBackend` port** (03, `grdr-ports`): the Linux back end implements `probe() -> HostProfile`, `apply(InterestSet)` (the bundle's process scope, path, host and port tables, D-05), `enforce(FloorTables)`, `expect(Expectation)` and `revoke(ExpectationId)`, and `events() -> stream`. The daemon owns session state, peer authentication and the spool; the back end only collects and enforces (D-20).
- **`Actuator` port** (03): `cgroup.kill`, freeze and thaw of a session scope, cutting a session's egress by emptying its `net_scope_policy` entry, and `pidfd_send_signal`; each verb is declared per tier so the console shows the effective action (D-30).
- **`SandboxBackend` port** (03): the T4 launcher of §7, with its conformance results per Landlock ABI.
- **`HostProfile`** (03, 04, D-60): the probe result: event classes with provenance grade, the tier per action class, session mechanism (cgroup scope), actuator verbs, slot owners. The engine derives achievable assurance and returns `not_evaluable` per rule rather than passing silently (D-60, 07).
- **Events**: the back end emits `process.start` and `.exit`, `action.exec`, `action.file.*`, `action.net.connect`, `action.elevate`, `action.config.change`, `session.link`, `inventory.device`, `health.sensor` (probe, tier and enforcement mode per hook, ring and listener loss counters), `health.coverage` and `health.gap`. The daemon stamps them with `source.channel` (`ebpf`, `fanotify`, `procfs`, `sandbox`; `seccheck`, which 04 adds under R-15, §10) and the provenance grade from 04's fixed table: `mediated` for a deciding LSM, cgroup or fanotify permission hook and for the launcher, `observed-kernel` for eBPF tracing and `seccheck`, `observed-user` for procfs (04 §9). The back end never sets its own provenance grade.
- **`expectation_map` and floor tables**: the daemon compiles expectations and grants (07 §9, 12) into BPF maps the LSM programs read; the compiled floor table is `grdr-fastpath`'s row set over fixed-layout inputs (12 §8), which is also the embedded fast path of D-41 L3.
- **Kubernetes**: the identity tuple and coverage ledger (§10) travel in the Kubernetes `workload` object that 04 adds under R-15 (cluster, namespace, service account, pod, container, image digest, owner, RuntimeClass, node). The controller reads `agents.x-k8s.io` CRs and SPIRE or PodCertificate identities.
- **CI**: the OIDC-to-device-id mapping is 22's workload identity federation; the action/component/plugin are packaging artefacts (§13).

## Behaviour by deployment shape

- **Standalone** (laptop or server): User or Protected profile (D-48); kernel observation, launch containment, `cgroup_sock` network enforcement (after its own review, R-40) and the rest of kernel enforcement (after the kernel review, D-63) in Protected; the User profile has procfs observation, hooks and the launcher only; sends nothing but update fetches (`grdr egress` asserts it, 03 C4); a per-session cgroup scope attributes; containment is opt-in per agent.
- **Platform self-hosted and SaaS**: the sensor enrols (22); the DaemonSet, sidecar and CI modes enrol by workload identity federation and report to the operator's server; the per-workload coverage ledger feeds the fleet view (P9); kernel enforcement is offered to operators only after the kernel review (D-19, D-63; `cgroup_sock` reviewed on its own per R-40). Self-hosting is the default; the hosted service requires revenue, sponsorship or donated cloud credits (D-63).
- **Embedded** (D-41): `SensorBackend` is the seam another EDR vendor uses: it supplies its own kernel telemetry and verbs through a `HostProfile` and takes our attribution and policy (L3 fast path), or it runs our sensor beside its own under §15. Embedded builds embed no trust roots and make no network call to Loonaro (D-60).

## Extension points

- **A new `SensorBackend`** (a vendor's eBPF sensor, a research tracer): implement the port, describe it with a `HostProfile`, pass the port test kit (`grdr-ports-testkit`, 03), ship in the contrib repository (P6). It never gates a release.
- **A new agent adapter's Linux specifics** (exec-wrapper pattern, housekeeping profile, protected-path set, containment mode) are pack data in the content repository (07 §4 and its extension points), not sensor code.
- **A new container runtime or CI system**: a sidecar overlay and an OIDC claim mapping, both data; `seccheck` consumers and CRI correlators are the only code, and they sit behind the same event contract.
- **Data-source adapters** consume, rather than duplicate, an existing node agent (Tetragon over gRPC, Falco alerts, KubeArmor, Sysmon-for-Linux via syslog) where present, adding agent attribution and policy, not a second set of hooks (10-research, g04).

## Security and privacy

- **The kernel programs are trust core** (D-63, 02 `trust-core.paths`): every change needs two independent passing evaluators on different models, a reference model, differential tests, the matrix and soak, and enforcement leaves the internal ring only with §6's kernel review. Agent-written BPF is gated by spike S-13 (loads across the matrix, zero mismatches against the model, the evaluators' review within one item's usage cap).
- **Self-protection on Linux** is prevent-against-user, detect-against-root (D-22), in the Protected profile only: root-owned binaries, policy, spool and socket directory; with kernel enforcement enabled, `lsm_task` denies kill, ptrace, BPF detach and writes to our paths to agent-lineage tasks, and denies BPF map and pin access to every task outside the sensor (§6). Against root the guarantee is detection: heartbeat gaps, the hash-chained spool and a signed going-down event (02 SR-10). An optional stricter BPF LSM lockdown of our paths against all non-sensor tasks ships in audit mode by default with a signed break-glass token (37).
- **Content captured from the kernel obeys the capture level** (D-51): default upload is `metadata`; paths, argv and destinations are keyed digests at `metadata` and travel as evidence spans only under a finding or content grant (04 §11). The sensor installs no input hooks and records no keystroke timing, screen or clipboard content (D-51). TLS uprobes are not used: on Claude Code's Bun binary with static BoringSSL the offsets must be found by byte pattern per build, and the captured plaintext carries bearer tokens (14 §9 and verification row 8), so content comes from hooks, the proxy and the gateway (D-16).
- **Humans in shared workloads.** `kubectl exec` processes are correlated through the Kubernetes audit log and CRI exec ids, and under gVisor through `is_exec_session`, so human activity in a pod is not attributed to the agent (06, g04). The audit `loginuid` and `sessionid` are the same for a person and an agent in one terminal, so they only mark new sessions such as an ssh login, never agent versus human (14 §10).

## Test and evaluation strategy

The oracle for each important property:

| Property | Oracle |
|---|---|
| The probe's tier matches real kernel capability | A live deny attempt per class on each matrix kernel with a test-only deny program (§14); the probe is wrong if a claimed tier cannot block or a disclaimed tier can |
| A deny is synchronous, not a race | An in-flight `write()`/`execve` after a kill versus after an LSM/fanotify deny; the LSM/fanotify path must block the operation (14 §2) |
| Enforcement survives loader death | Kill and restart the agent and the daemon mid-policy; from a root task outside the sensor attempt a map write, a link detach and a pin unlink; the pinned program must still deny, each attempt must fail and raise a tamper finding (R3) |
| Holds are safe | Stall, suspend and kill the fanotify listener with an opener held; the opener must resolve within 30 s, no task outside a session scope may wait, and listener death must show `on_failure: open` with a finding (§4, SR-15) |
| No in-kernel verifier blow-up | The real verifier across the matrix, including livepatched kernels and kernels with other vendors' programs on the same hooks (S-13, h02) |
| Coverage is honest per workload | A gVisor, Kata or Fargate pod running a denied action; the ledger must show `control: none` for that class, never a false green (§10, P9) |
| Overhead | A kernel build, `npm ci`, `cargo build` and a scripted agent loop spawning thousands of short processes, sensor on and off; target under 3% alone and under 2% added per incumbent (section 6 of the spine), with Tetragon's 1.68% as the public reference (h02, D-45) |
| Ephemeral start | Time from instance or job start to the first event acknowledged by the server on WSL2 and hosted GitHub and GitLab runners; target p95 under 15 s (§9, §11) |
| io_uring does not bypass | The same file and network action via io_uring; the LSM file/socket layer must still see and judge it (§8) |
| Containment composes | Each Tier 1 agent's own sandbox inside ours (S-11); a failure fixes that agent to `delegate`, which falls back to `wrap-tools` where its own sandbox cannot run on the host (D-21) |
| CI attribution | A malicious-package fixture in each CI; the event must carry the OIDC identity and the package+version (§11) |

The held-out suite (D-45) gates the kernel-enforcement release; `verify` runs the short matrix on every pull request, the full matrix nightly.

## Work breakdown

**E1 Capability probe.** I1.1 the probe of §1 (LSM list, lockdown, BTF, config hints, Landlock ABI, fanotify features, sysctls, cgroup ownership, arch, page size, trampoline links in use) with a no-op attach test per tier, writing `HostProfile` and `health.sensor`. *Accept:* on every tier A matrix cell the reported tier per class matches a live deny attempt with a test-only program; the code has no branch on distribution name or version string. I1.2 no `BPF_PROG_TYPE_LSM` load while `bpf` is absent from the active list. *Accept:* on Ubuntu 24.04 GA and WSL2 6.6.y the probe's load counter for LSM programs is zero and the record shows T2, T3 or T5 with the reason.

**E2 eBPF observe set.** *Requires:* the daemon. I2.1 `exec_trace`, `fork_exit_trace`, `cgroup_sock` (observe), `lsm_file` and `lsm_exec` (monitor) in `aya`, CO-RE, x86_64 and arm64, one ring per event class with drop counters. *Accept:* on every tier A cell, process, file and connect events carry lineage and the session tag; the signed object loads from the package with no kernel toolchain on the machine; a forced ring overflow shows in `health.sensor` drop counters and never as silence. I2.2 `ipc_edge` and the escape table of §8. *Accept:* each of `systemd-run`, a user timer, the Docker socket, ssh to localhost, tmux and a written git hook produces the `session.link` edge 06 expects, in a scripted fixture per escape.

**E3 Per-session cgroup scope.** I3.1 `grdr run` creates the scope (systemd transient scope, or a delegated cgroup without systemd) and tags the tree. *Accept:* a process in the scope with no matching tool call raises exactly one finding and a matched one none (07 E5.1). I3.2 adoption by pidfd hand-off from the hook at session start. *Requires:* the hook shim (D-14). *Accept:* the session tag survives double-fork, `setsid`, `nohup` and `sudo` in fixtures; attribution evidence is `session-container` at grade 3 (04 §9); an adopted session's pre-existing descendants are tagged, and moved into a nested scope only where SP-06-1 passed (06).

**E4 Enforcement tiers.** *Requires:* E1, E2, S-12, and the kernel review of D-63 before any of it leaves the internal ring. I4.1 T1 BPF LSM enforce reading `expectation_map` and floor tables; pins, in-kernel expectation expiry, `lsm_task` map and pin protection, link replacement on update; mode asserted per hook in the heartbeat. *Accept:* synchronous deny on every T1 cell; with the daemon killed, fail-closed classes still deny; a root map write, link detach and pin unlink from outside the sensor fail and raise tamper findings; a colliding pin path raises a finding, never a silent downgrade; an update causes zero denials in the update fixture (D-15). I4.2 T2 `fmod_ret` and kprobe-override variants. *Accept:* synchronous deny on Ubuntu 22.04 and 24.04 on x86_64 and arm64 without a reboot, or the cell is reported T3 with the reason (S-12). I4.3 T3: host-class network policy over the DNS interposer (the `cgroup_sock` address and port enforcement is I5.3), fanotify inode marks with the 30-second cap, the in-daemon watchdog and the kernel watchdog setting. *Accept:* connect, open, direct exec and read on marked paths are denied; a listener stall or kill leaves no host-wide stall over 1 s (02 target) and no wait outside session scopes (S-12); `file.write` and `file.delete` show `control: none` where only fanotify is present. I4.4 `uring_guard`. *Accept:* file and network actions issued through io_uring are judged by the LSM layer on T1 and T2 cells, and the Curing technique reproduced in a fixture is denied for contained sessions.

**E5 Launch sandbox.** I5.1 `grdr run` Landlock and seccomp launcher as the Linux `SandboxBackend`: ABI-gated profile of §7, no user-namespace dependency except the optional network fence, io_uring and namespace calls denied, unotify broker for UNIX sockets below ABI 9. *Accept:* the sandbox conformance suite (D-21) passes for every class the record claims at each ABI in the matrix, with `net.connect` claimed only where the `cgroup_sock` enforcement of I5.3 is enabled or the launcher added a network namespace whose only exit is the socket bridge to the proxy; the containment mode of each Tier 1 agent is set by S-11, and each agent either finishes the scripted task contained or is fixed to `delegate`, `wrap-tools` or request level with a stated reason. I5.2 `wrap-tools` through the hook rewrite and `delegate` verification at exec. *Accept:* a tool subprocess outside the agent's own sandbox in `delegate` raises a tamper finding within one second (target); on a host without `bwrap` or `socat`, and on one where unprivileged user namespaces are blocked, Claude Code's sandbox is not locked on, no `sandbox-bypass` is raised, and each Bash call runs under `grdr-run`, with a write outside the workspace denied. I5.3 `cgroup_sock` enforce in the Protected profile: `connect4/6` and `sendmsg4/6` deny by the session's address and port set, with launched trees allowed only the proxy. *Requires:* its own kernel review under D-63, separate from E4's (R-40). *Accept:* the review's findings are closed before the program leaves the internal ring; from a launched tree a direct connect to any address but the proxy is denied synchronously on every tier A cell; untagged processes are never filtered.

## Deviations from the spine and objections

No deviation. Three clarifications recorded for implementers, consistent with the spine, and one objection:

1. **fanotify cannot hold or deny writes.** D-19 lists "fanotify marks on the protected-path set only" as a tier; this document states that fanotify has no permission event for `file.write` or `file.delete` (14 §3), so those classes need T1 or T2 and are `control: none` where only T3 is present. It narrows no spine claim; it makes P9 honest.
2. **AL4 on Linux is per host.** Section 7 of the spine says "AL4 on Linux requires kernel enforcement and its review". Because of (1), AL4 holds only on hosts where T1 or T2 attaches; an Ubuntu 22.04 or 24.04 host reaches it only if S-12 passes there.
3. **Kill and AppArmor are not tiers.** The research ladder (14) includes generated AppArmor or SELinux profiles and kill-then-freeze; D-19's order does not, and this document keeps them out (§6).

One objection, now settled: **AL3 on Linux through launch containment has no network boundary without kernel enforcement.** Resolved by R-40, which chose the first option below: `cgroup_sock` is reviewed on its own (E5 I5.3). The second option is kept as the fallback where that program is absent (§7). As originally raised: section 7 of the spine promises AL3 through launch containment, and AL3 needs `scoped-boundary` on `net.connect`. Landlock matches ports, not addresses, and a namespace-based fence fails under Ubuntu 24.04's user-namespace restriction, so the only destination boundary for a launched tree is the cgroup network programs of §5, which are kernel enforcement and require the kernel review (D-19, D-62, D-63). Either `cgroup_sock` is reviewed on its own, apart from the other enforce programs (it is the smallest enforce program and holds no state but the session's address set), or Linux reaches AL3 through launch containment only where unprivileged user namespaces are available and the launcher adds a network namespace with the proxy as its only route. The record of the original objection is kept for the reasoning.
